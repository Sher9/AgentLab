主流框架选型：原生 SDK vs LangChain/LangGraph vs LlamaIndex vs AutoGen vs CrewAI

对比五类 Agent 开发方案的定位、适用场景与取舍，给出最小可运行示例与选型建议，帮你不从第一步就走弯路。

#框架#LangChain#LangGraph#AutoGen#CrewAI#选型

主流框架选型：原生 SDK vs LangChain/LangGraph vs LlamaIndex vs AutoGen vs CrewAI

M0 跑通了"模型说一句话"，M1 写了一个能调工具的闭环，M2 讨论了 ReAct / Plan-and-Execute 等"思考策略"。 到这里你已经具备不依赖任何框架写出 Agent 的能力。

这一篇不教你某个框架的 API，而是回答一个更前置、也更容易被忽略的问题： 到底要不要上框架？上哪个？ 选错框架的代价，往往比"代码写得糙"高一个数量级。

1. 为什么选型重要

很多团队在 demo 阶段随手选了一个框架，等发现它限制了自己的控制力、或是为了一个简单需求被迫扛上几百 KB 依赖时，再想换，成本已经很高。

选型之所以关键，有三个现实原因：

  • 框架锁死成本：Agent 的核心逻辑（状态流转、工具调度、记忆管理）一旦写进某个框架的"心智模型"里，迁移成本约等于重写。抽象越重，绑定越深。
  • 抽象泄漏（Leaky Abstraction）：所有"帮你屏蔽复杂度"的框架，在出问题时都会把底层细节甩还给你——而那时你往往既看不懂它的内部状态，又不熟底层协议。越是复杂的故障，越容易发生在抽象边界上。
  • 版本漂移：几个主流框架都处于高速迭代期，半年前的博客代码今天可能直接编译不过。把业务稳定性押在别人的 API 稳定性上，需要想清楚。
📌本文立场

本站的默认建议是：先用手写 SDK 打底，真正遇到框架能显著省力的信号时再引入。 框架是加速器，不是安全带。下文每一节都会给"何时用 / 何时不用"。

2. 方案一：原生 SDK（手写循环）

是什么

不引入任何 Agent 框架，只用 LLM 厂商官方 SDK（这里用 OpenAI Node SDK）+ 你的业务代码，自己实现 M1 讲的"四步闭环"。

何时用

  • 学习阶段：想真正理解 Agent 运行机理，而不是被框架的黑盒包住。
  • 简单到中等复杂度：单 Agent、工具数可控、流程线性。
  • 对延迟、依赖体积、可控性有硬要求（边缘、客户端、合规场景）。
  • 框架的抽象反而碍事时——比如你要做非常规的调度逻辑。

何时不用

  • 需要复杂的多 Agent 编排、长期记忆、人类介入（human-in-the-loop）等开箱能力，且你不愿自己造轮子。
  • 团队规模大、希望有一套统一范式降低协作成本。

最小可运行骨架

下面这段是 M1 闭环的精简版，可直接复制运行（依赖与运行方式见本节末尾）：

// native-agent.ts —— 纯 SDK 的 Agent 闭环（可运行骨架）
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';

const client = new OpenAI();

// ① 工具定义：JSON Schema 数组，模型据此决策是否调用
const tools: OpenAI.Chat.Completions.ChatCompletionTool[] = [
  {
    type: 'function',
    function: {
      name: 'get_weather',
      description: '查询某城市的当前天气',
      parameters: {
        type: 'object',
        properties: {
          city: { type: 'string', description: '城市名，如 北京' },
        },
        required: ['city'],
      },
    },
  },
];

// ② 工具真实实现（真实场景换成 API 调用）
function getWeather(city: string): string {
  return `${city}：晴，26°C，微风。`;
}

// ③ 参数校验 schema：单一事实来源，运行时挡住脏输入
const WeatherArgs = z.object({
  city: z.string().min(1, '城市不能为空'),
});

async function run(userInput: string) {
  // 上下文堆在这里：用户、模型、工具结果全部进同一数组
  const messages: OpenAI.Chat.Completions.ChatCompletionMessageParam[] = [
    { role: 'user', content: userInput },
  ];

  // ④ 自主循环，上限 5 轮，防模型失控烧钱
  for (let step = 0; step < 5; step++) {
    const res = await client.chat.completions.create({
      model: 'gpt-4o-mini',
      messages,
      tools, // 关键：把工具交出去
    });
    const msg = res.choices[0].message;
    messages.push(msg); // 模型这轮输出（可能含 tool_calls）必须入栈，保持连贯

    // ⑤ 模型不再要求调工具 → 直接回答，结束
    if (!msg.tool_calls || msg.tool_calls.length === 0) {
      console.log('最终回答：', msg.content);
      return;
    }

    // ⑥ 逐个执行工具调用并回填
    for (const call of msg.tool_calls) {
      const raw = JSON.parse(call.function.arguments);
      // 校验先于执行：非法参数不进真实系统，把错误还给模型让它纠正
      const parsed = WeatherArgs.safeParse(raw);
      if (!parsed.success) {
        messages.push({
          role: 'tool',
          tool_call_id: call.id, // 必须回传，否则 400
          content: `参数错误：${parsed.error.message}`,
        });
        continue;
      }
      const result = getWeather(parsed.data.city);
      messages.push({
        role: 'tool',
        tool_call_id: call.id,
        content: result,
      });
    }
    // ⑦ 带上工具结果再问模型，看是否还需继续
  }
}

run('北京现在天气怎么样？');

运行方式（需先配置 OPENAI_API_KEY 到 .env）：

npm i openai dotenv zod
npx tsx native-agent.ts
💡原生 SDK 是你最后的退路

无论上什么框架，底层都还是这套循环。遇到框架诡异行为时，最快的定位方式就是： 暂时绕开框架，用原生 SDK 复现最小场景。能跑通，说明是框架问题；跑不通，说明你没理解协议。

3. 方案二：LangChain / LangGraph

是什么

LangChain 是最早流行的 LLM 应用框架，提供"链（Chain）""记忆""工具""回调"等通用抽象，让你用组合方式搭应用。 LangGraph 是它的"升级形态"，把流程建模成有状态的图（StateGraph）：节点是计算步骤，边是流转条件，支持循环、分支、人工介入，更适合做复杂的 Agent 编排。

何时用

  • 需要结构化、可观测、可持久化的多步流程，且不想自己维护状态机。
  • 用到 LangChain 生态里的现成组件（文档加载器、向量库接入、大量集成）。
  • Agent 流程有明显的"图结构"：分支、回退、human-in-the-loop。

何时不用

  • 任务很简单，一条线性循环就够（原生 SDK 更轻）。
  • 你对"模型到底发了什么、状态怎么变的"需要完全掌控。
  • 团队版本管理严格、难以承受第三方 API 频繁变动。

StateGraph 思路（示意）

LangGraph 的核心是：定义一个共享状态（State），节点读写它，边按条件决定下一步去哪。 下面只展示结构思路，不是可复制的真实 API，真实写法请以官方文档为准：

⚠️API 易变，切勿照抄旧代码

LangChain / LangGraph 的 API 在 2024–2025 年经历多次较大重构，StateGraph、 导入路径、compile() 形态都可能随版本变化。本文片段仅为思路示意，落地前务必核对你安装版本的官方文档与迁移指南。

💡抽象重，但生态真香

LangChain 被吐槽"抽象过厚、调试晦涩"，但它最大的价值是集成丰富：几百个第三方服务的连接器开箱即用。 如果省下的集成成本 > 你承受的抽象成本，它依然划算。

4. 方案三：LlamaIndex

是什么

LlamaIndex（原 LlamaIndex）起家于 RAG（检索增强生成），核心是"数据接入 → 建索引 → 检索 → 喂给模型"这条链路。 它把文档切割、向量化、检索、重排、与模型对话的衔接做得非常完整，后来也扩展出 Agent 能力（如 QueryEngine、Agent、工具化检索）。

何时用

  • 你的 Agent 主要价值在于**"基于私有知识作答"**：内部文档、代码库、数据库问答。
  • 需要复杂的检索策略：混合检索、重排、多索引路由、元数据过滤。
  • 知识库规模大、需要持续增量更新。

何时不用

  • 任务与"检索知识"无关（纯工具编排、对话机器人）。
  • 只需要简单向量检索，自己用向量库 SDK 几行就能搞定。
  • 对运行时体积敏感，LlamaIndex 本体偏重。

📌RAG 不等于把文档丢进去就行

LlamaIndex 能省去造检索轮子的功夫，但切分策略、重排、是否该用元数据过滤仍是工程活。 框架负责"能检索"，不负责"检索得好"。上线前务必评估召回质量。

5. 方案四：AutoGen

是什么

微软出品的 AutoGen 主打对话式多 Agent：你定义多个"会说话"的 Agent（如助理、评审、执行者），它们通过互相发消息来协作完成任务；GroupChat 让一群 Agent 在一个群里轮流发言，由一个"群管理员"决定下一步谁说。

何时用

  • 任务天然适合"多个专家对话求解"：代码生成 + 代码审查、头脑风暴、辩论式决策。
  • 想快速跑通多 Agent 协作的 demo，体验"群体智能"。
  • 需要人在环（UserProxyAgent 可把决策交回人类）。

何时不用

  • 流程必须严格可控、可审计（对话式编排的"谁先说、说几轮"较不确定）。
  • 成本敏感：多 Agent 多轮对话，token 消耗与延迟会显著放大。
  • 任务其实是单 Agent 线性能解决的。

⚠️v0.4 是分水岭

AutoGen 在 0.4 版本做了核心架构重写，旧教程的 UserProxyAgent / GroupChat 写法大量失效。 入手前先确认你装的版本，并以该版本的官方示例为准，不要混用不同大版本的代码。

6. 方案五：CrewAI

是什么

CrewAI 以角色扮演式多 Agent 为核心隐喻：你定义一组有"人设"的 Agent，给它们分配 Task，再用 Crew 把它们编排成一支"团队"去协作。 相比 AutoGen 的"群聊"，CrewAI 更强调流程化协作（谁先干、产出交给谁），像在排一场分工明确的项目。

何时用

  • 喜欢"给 Agent 设定角色 + 分工任务"的直观心智模型。
  • 业务流程清晰可拆：研究员 → 写手 → 审校，这种流水线式协作。
  • 想要比 AutoGen 群聊更可控的执行顺序。

何时不用

  • 任务并不需要多个角色，单 Agent 即可。
  • 需要极细粒度的图状控制流（那种场景 LangGraph 更合适）。
  • 团队不愿引入又一个快速发展的框架依赖。

💡CrewAI vs AutoGen：两种多 Agent 哲学

AutoGen 像"开个会大家讨论"，过程灵活但难控； CrewAI 像"排好工种的流水线"，顺序明确但灵活度低。 选哪个，取决于你的任务是"需要碰撞"还是"需要分工"。

"控制力"和"上手成本"通常是反向关系：越省事，越把控制权交出去。 没有"最好"，只有"对你的场景最合适"。下一节给决策信号。

8. 选型决策：什么时候该上框架

我们的默认路径很朴素：

  1. 先用原生 SDK 打底。把 M1 的闭环、M2 的思考策略自己写一遍。你获得的不是代码，而是"读得懂底层"的能力——这是后面评估任何框架的基准线。
  2. 当某个痛点反复出现，且框架正好解决它，再引入。下面是"该上框架"的明确信号：
你遇到的信号 优先考虑
要接几十种数据源 / 服务，集成成本高 LangChain
流程是图状：分支、回退、断点恢复、人在环 LangGraph
核心是"基于私有知识作答"、检索质量决定成败 LlamaIndex
任务需要多个专家"讨论"求解 AutoGen
任务是角色分工的流水线 CrewAI
任务一条循环就够，你只想快点跑通 不上框架，用原生 SDK
💡一个反直觉的事实

很多"上了框架"的项目，最后 80% 的代码仍在处理框架覆盖不到的东西： 鉴权、限流、日志、错误恢复、业务校验。框架省的是"通用部分"，省不掉"你的部分"。 所以不要因为"怕写代码"而选框架，而要因为"它真能省该类代码"而选。

9. 踩坑提醒

🚫不要为简单任务上重框架

最典型的浪费：一个"用户问一句、调一个工具、回一句"的机器人，硬套 LangGraph + 向量库 + 多 Agent。 结果是依赖翻倍、延迟翻倍、bug 翻倍，能力却没增加。先问自己：原生 SDK 能不能 50 行写完？ 能，就别上。

⚠️框架版本漂移会咬人

上面四个框架（尤其 LangChain/LangGraph、AutoGen、CrewAI）都在快速演进。 落地的第一件事是锁定版本并写进 lockfile，并把关键调用封装在你自己的薄层里—— 这样将来升级，改动集中在薄层，而不是散落业务各处。切勿 npm install xxx@latest 随手升级到生产。

⚠️抽象泄漏时，你还得回到底层

框架报错、行为诡异、工具没按预期触发——这些时刻，框架的"贴心封装"会瞬间消失， 露出底下 raw 的 messages、tool_calls、状态码。那时救场的，正是你用原生 SDK 练出来的基本功。 所以先学底层，再上框架，顺序别反。

🚫别把框架当黑盒信任

无论用哪个框架，最终发给模型的仍是 messages + tools。框架可能默默改你的 prompt、 重复注入系统消息、或把工具结果格式化掉。生产前务必打开日志，看清楚实际发了什么—— 很多"模型变笨了"的锅，其实是框架在中间动了手脚。

小结

  • 选型本质是权衡控制力 vs 上手成本：越省事越交权，没有银弹。
  • 五类方案定位不同：原生 SDK（地基）、LangChain/LangGraph（复杂编排+生态）、LlamaIndex（RAG）、AutoGen（对话式多 Agent）、CrewAI（角色流水线）。
  • 默认路径：先用原生 SDK 打底 → 出现明确痛点且框架正好解决 → 再引入，并把框架调用包在薄层里。
  • 三大坑：简单任务别上重框架、锁版本防漂移、抽象泄漏时靠底层基本功救场。
  • 框架省"通用部分"，省不掉"你的部分"；别把它当黑盒，要看清实际发出的请求。

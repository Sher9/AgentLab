#RAG#Embedding#向量化#归一化#领域适配

向量化：Embedding 模型选型与维度归一化

rag-chunking 把文档切成了语义自洽的 chunk，下一步是**向量化（Embedding）**：用一个模型把每段文本变成一组浮点数向量。检索时，把『问题向量』和『文档向量』做相似度比较，意思越近分数越高。本篇只讲向量化这一环：模型怎么选、维度多少、要不要归一化、领域怎么适配。
📌向量是『意思的坐标』

Embedding 把文本映射到高维空间，语义相近的文本向量也相近。相似度计算（余弦/点积） 就等价于『语义距离』。这是 RAG 能『按意思找文档』而非『按关键词找文档』的根本原因。

1. 模型选型

选型先看『通用 vs 领域、闭源 vs 开源、维度与成本』三件事。

模型 特点 适用
OpenAI text-embedding-3-small 通用强、便宜、支持 Matryoshka 降维 大多数通用 RAG 起步首选
OpenAI text-embedding-3-large 精度更高、维度大、贵 对召回精度敏感的通用场景
bge-m3 / bge-large (开源) 中文与多语言强、可自部署 数据不出域、中文为主
e5 / gte 系列 开源、性价比高 预算有限、需本地化
💡起步用 text-embedding-3-small

通用场景先用 OpenAI 的 small：便宜、稳定、精度够用。等 Recall@K 卡在『模型表达力不足』时， 再换 large 或开源领域模型。别在起点就为 1% 精度多付 10 倍成本。

2. 维度与 Matryoshka 截断

维度 = 向量的长度。维度越高，表达力越强，但存储与检索成本线性涨。OpenAI 的 text-embedding-3-* 支持 Matryoshka 表示学习：训练时让『前 N 维』已包含主要信息，因此可以截断到更小维度，几乎不损精度。

// embed.ts —— 向量化 + Matryoshka 降维（可运行，OpenAI 官方 SDK）
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';

const client = new OpenAI();

const EmbedConfig = z.object({
  model: z.enum(['text-embedding-3-small', 'text-embedding-3-large']).default('text-embedding-3-small'),
  // 截断维度：small 原生 1536，可降到 256/512 等；large 原生 3072
  dims: z.number().int().min(64).max(3072).optional(),
});

export async function embed(text: string, cfg = EmbedConfig.parse({})) {
  const res = await client.embeddings.create({
    model: cfg.model,
    input: text,
    dimensions: cfg.dims, // 仅 3 系支持；降维省存储、检索更快
  });
  return res.data[0].embedding;
}

// 用法：把 1536 维降到 512 维，存储省 3 倍、召回几乎不降
const vec = await embed('退款政策有哪些？', EmbedConfig.parse({ dims: 512 }));
console.log(vec.length); // 512
⚠️降维要测 Recall@K

截断维度能省存储，但维度过低必然丢信息。每次降维后跑一遍 rag-overview 的 Recall@K， 确认分数没明显掉。找到『精度不降的最小维度』，而非盲目压到最低。

3. 归一化：余弦还是点积

相似度常用两种：余弦相似度（只看方向）和点积（方向与长度都算）。多数 embedding 模型输出已归一化（模长≈1），此时余弦≈点积，算点积更快。

// normalize + 余弦（演示；实际 3 系默认已归一化，可直接点积）
function normalize(v: number[]): number[] {
  const n = Math.sqrt(v.reduce((s, x) => s + x * x, 0));
  return v.map((x) => x / n);
}
function cosine(a: number[], b: number[]): number {
  const na = normalize(a), nb = normalize(b); // 若已归一化，这步可省
  let dot = 0;
  for (let i = 0; i < na.length; i++) dot += na[i] * nb[i];
  return dot; // 越接近 1 越相似
}
💡确认模型是否默认归一化

若用开源模型，需查文档确认输出是否归一化。未归一化时，长文本向量模长更大，点积会被长度带偏， 必须显式归一化后再算余弦。混淆『点积当余弦用』是跨模型迁移时的隐形 bug。

4. 领域适配

通用 embedding 在专业领域（法律、医学、代码）容易『看不懂行话』。两条路：

  • 换领域强模型：优先试开源领域模型（如代码向的 jina-embeddings-code、医疗向的专用模型），零训练成本。
  • 微调 embedding：用领域内『 query ↔ 相关文档』成对数据微调（OpenAI 提供 embedding 微调接口；开源可用 sentence-transformers 的 fit）。API 以官方文档为准，易变。
📌先换模型，后微调

微调有数据收集与训练成本。先用领域 SOTA 开源模型测 Recall@K，不够再考虑微调。 微调的数据质量（正负样本对是否干净）比模型结构更影响结果。

5. 对比速查

维度 高维（如 3072） 低维（如 256/512）
表达力 强 弱（信息压缩）
存储/检索成本 高 低
建议 精度敏感且存储充裕 用 Matryoshka 截断、实测不降精度再用
相似度 余弦 点积
是否受长度影响 否（只看方向） 是
前置条件 最好归一化 已归一化时等价且更快

6. 踩坑

🚫摄入与查询模型不一致

写库和查询必须用同一 embedding 模型（含同一 dimensions），否则向量不在同一空间， 相似度失真。把模型名抽成全局常量，上线前核对两边一致。

⚠️盲目压低维度不测召回

为省存储把维度压到 64，却从没跑 Recall@K，结果召回率暴跌还不知道。降维必测。

⚠️跨模型混用相似度假设

把 A 模型（未归一化）的向量和 B 模型（归一化）的算法混用，点积结果不可比。迁移模型时， 连同相似度计算方式一起复核。

💡批量 embedding 限流

大库摄入时批量请求，加限流与断点续传，避免触发速率限制（思路见 rag-overview 摄入骨架）。

小结

  • Embedding 把文本映射成『意思的坐标』，相似度=语义距离，是 RAG 语义检索的基础。
  • 选型起步用 text-embedding-3-small；领域强需求换开源领域模型或微调。
  • 维度用 Matryoshka 截断省成本，但每次降维都要用 Recall@K 验证不损精度。
  • 多数模型默认归一化，此时余弦≈点积、点积更快；跨模型迁移要复核归一化假设。
  • 红线：摄入/查询模型一致、降维必测、相似度假设随模型复核、批量限流。

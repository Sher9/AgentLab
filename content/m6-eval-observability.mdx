# 可观测与评估：Tracing、Eval 与成本追踪

前面 M1～M5，你已经能写出会调工具、会规划、会记忆的 Agent。但一个残酷的事实是：**你无法证明它在『正确地』工作**。同样的输入，模型今天答对、明天答错；prompt 改一个词，成功率可能腰斩；上线后它更成了一个黑盒——用户说『答错了』，你却连它中间调了哪个工具都不知道。

这一篇就是来填这个洞：用 **Tracing** 让行为可见，用 **Eval** 让质量可量化，用 **成本追踪** 看住钱，用 **Dashboard + Guardrails** 守住底线。三者合起来，才是一个能上生产的 Agent。

<Callout type="note" title="目标读者">
  本篇默认你已经跑通过前面的 Agent 骨架、熟悉 OpenAI SDK 与 Zod。
  所有代码都是纯 TS、可复制运行的单文件，不依赖任何付费 SaaS——生产级方案只作对比说明。
</Callout>

## 1. 为什么必须评估与可观测

传统软件是确定性的：给定输入，输出由代码逻辑唯一决定，单测能 100% 覆盖。但 Agent 把『决策』交给了 LLM，引入了三层不确定性：

- **非确定性**：即使 `temperature=0`，不同次调用、不同上下文、工具返回波动，都会让路径不同；
- **脆弱性**：prompt 微调、模型升级、工具接口变更，都可能让原本 90 分的行为掉到 50 分，而你毫无察觉；
- **上线即黑盒**：没有埋点，你只能看到『用户问了什么、最终回了什么』，中间 5 次工具调用、3 次重试全丢。

结论很直接：**评估与可观测不是『锦上添花』，而是 Agent 工程的氧气**。没有它，你是在盲飞。

## 2. Tracing（可观测）

Tracing 的目标是：把 Agent 一次运行的**完整链路**结构化地记录下来，至少包含每一步的 `input`、`output`、`tool_call`、`token` 用量、`耗时`。出问题时你能回放、能定位是哪一步开始跑偏。

### 2.1 span / trace 模型

- **Span（跨度）**：一次『动作』的记录——一次 LLM 调用、一次工具执行、一次检索。含输入、输出、开始时间、耗时、token。
- **Trace（链路）**：一次用户请求对应的所有 span 的树/列表，用 `trace_id` 串起来。

这个模型源自分布式系统的 OpenTelemetry，Agent 领域完全复用：每个 LLM 调用是一个 span，工具的子调用是嵌套 span。

### 2.2 手写轻量 tracer（可运行骨架）

生产级方案（LangSmith / Phoenix / OpenTelemetry）后面会对比，但理解原理最快的方式是自己写一个。下面用纯 TS 包一层 `client.chat.completions.create`，在调用前后打点：

```ts
// tracer.ts —— 手写轻量 tracer（纯 TS，不依赖任何 SaaS）
import OpenAI from 'openai';
import 'dotenv/config';

const client = new OpenAI();

// 一条 span = Agent 内部的一次『动作』（一次 LLM 调用 / 一次工具执行）
interface Span {
  name: string;        // 动作名，如 'llm_call' / 'tool_call'
  input: unknown;      // 输入（messages / 工具参数）
  output: unknown;     // 输出（模型回复 / 工具结果）
  tokens: number;      // 消耗的 token 数
  durationMs: number;  // 耗时（毫秒）
  startedAt: string;   // 开始时间（ISO）
}

// 整次会话的 trace，由若干 span 组成
interface Trace {
  id: string;
  spans: Span[];
}

// 极简 tracer：start 开启一次 trace，span 包裹动作，dump 导出
const tracer = {
  current: null as Trace | null,
  start() {
    this.current = { id: `trace_${Date.now()}`, spans: [] };
  },
  // 包裹任意异步动作，自动记录耗时与 token 元数据
  async span<T>(name: string, input: unknown, fn: () => Promise<T>): Promise<T> {
    const startedAt = new Date().toISOString();
    const t0 = Date.now();
    const output = await fn();
    const durationMs = Date.now() - t0;
    // 从 chat.completions 返回里抽取 token 用量，其他动作记 0
    const tokens = (output as { usage?: { total_tokens?: number } })?.usage?.total_tokens ?? 0;
    this.current?.spans.push({ name, input, output, tokens, durationMs, startedAt });
    return output;
  },
  dump() {
    console.log(JSON.stringify(this.current, null, 2));
  },
};

// 用 tracer 包住一次 LLM 调用，自动记录 input/output/token/耗时
async function demoRun(query: string) {
  tracer.start();
  const messages: OpenAI.Chat.Completions.ChatCompletionMessageParam[] = [
    { role: 'user', content: query },
  ];
  const res = await tracer.span('llm_call', messages, () =>
    client.chat.completions.create({ model: 'gpt-4o-mini', messages })
  );
  tracer.dump(); // 运行后打印完整 trace
  console.log('最终回答：', res.choices[0].message.content);
}

demoRun('用一句话解释什么是 Agent。');
```

把 `span` 套在工具执行上，就能把『模型建议调什么工具 → 工具真实返回』也串进同一条 trace。上线时把这串 `Trace` 写进日志或数据库，按 `id` 检索即可回放任意一次失败会话。

<Callout type="tip" title="trace 要细化到『工具级』">
  只记录 LLM 输入输出还不够。把每个 `tool_call` 的参数与结果也作为独立 span 记录，
  你才能回答『它是不是调错了工具 / 工具返回了脏数据』。这是定位 Agent 故障的关键粒度。
</Callout>

### 2.3 生产级方案对比

| 方案 | 定位 | 优点 | 缺点 |
|------|------|------|------|
| 手写 tracer | 理解/小项目 | 完全可控、零成本 | 需自建存储与看板 |
| **LangSmith** | 全栈 SaaS | 开箱即用、面板完善、内置数据集与在线 eval | 锁定生态、数据出域顾虑、付费 |
| **Phoenix (Arize)** | 开源可观测 | 本地/自托管、trace 可视化、LLM 语义评估内置、OpenInference 标准 | 需自己部署与接存储 |
| **OpenTelemetry** | 厂商中立标准 | span 模型通用、可接 Jaeger/Grafana 任一后端 | 需自建可视化与 LLM 专属语义层 |

<Callout type="note" title="思想一致，工具不同">
  无论哪种方案，核心都是『span + trace』模型。Phoenix 用 OpenInference 语义约定（把
  `llm.input.messages`、`llm.token.count` 等作为标准属性），LangSmith 用自家 schema，
  OTel 用通用 attribute。理解了手写版，上手任何一家只是换了个 API。
</Callout>

## 3. 成本追踪（Cost Tracking）

Tracing 记录 token，但『token』不等于『钱』。成本追踪要做的，是把每次调用的 token 换算成金额，并按维度聚合：

- **按请求**：单次对话花了多少钱；
- **按工具 / 步骤**：哪一步最烧钱（往往是某次长上下文的检索回填）；
- **按模型**：分级调用里小模型 vs 大模型各占多少；
- **按用户 / 租户**：谁在薅羊毛（多租户场景必备）。

```ts
// cost-tracker.ts —— 把 usage 换算成金额并聚合（单价以官方为准，会变动）
const PRICE_PER_1K: Record<string, { in: number; out: number }> = {
  'gpt-4o':       { in: 0.005, out: 0.015 },
  'gpt-4o-mini':  { in: 0.00015, out: 0.0006 },
};

interface CostRow { model: string; promptTokens: number; completionTokens: number; cost: number; }

function trackCost(model: string, usage: { prompt_tokens: number; completion_tokens: number }): CostRow {
  const p = PRICE_PER_1K[model];
  const cost = (usage.prompt_tokens / 1000) * p.in + (usage.completion_tokens / 1000) * p.out;
  return { model, promptTokens: usage.prompt_tokens, completionTokens: usage.completion_tokens, cost };
}

// 聚合：把一次会话里所有调用的 CostRow 累加，得到总账单
function sumCost(rows: CostRow[]): number {
  return rows.reduce((s, r) => s + r.cost, 0);
}
```

<Callout type="warn" title="单价会变，别硬编码进业务逻辑">
  上面的 `PRICE_PER_1K` 只是示例。模型单价会调整，应放到配置/远程配置里，
  并标注『以官方文档为准』。更稳的做法是用厂商账单 API 做对账，本地追踪只作实时预估。
</Callout>

## 4. Eval（评估）

Tracing 让你『看见』行为，Eval 让你『量化』质量。Eval 的本质是：**用一批固定样本（数据集）反复跑 Agent，用统一指标打分，得到可比较的数字。**

### 4.1 指标分类

| 指标 | 含义 | 怎么算 |
|------|------|--------|
| 任务成功率 | 端到端是否答对 | 通过样本数 / 总样本数 |
| 工具调用准确率 | 该调的工具、参数对不对 | 与标注的 tool_call 比对 |
| 答案正确性 | 最终答案质量 | 规则匹配 / 模型裁判打分 |
| 成本 | 一次运行花多少 token / 钱 | 累加 `usage.total_tokens` |
| 延迟 | 一次运行耗时 | 端到端 `Date.now()` 差值 |

<Callout type="warn" title="别只看成功率">
  成功率 100% 但每次烧 2 万 token、耗时 30 秒，生产照样不可用。
  **成本与延迟必须和成功率一起进 dashboard**，否则你会优化出一个『对但破产』的 Agent。
</Callout>

### 4.2 数据集驱动评估（可运行骨架）

下面读一份 `{ input, expected }` 数据集，逐条跑 Agent，用规则或模型裁判打分：

```ts
// eval-runner.ts —— 数据集驱动评估（纯 TS，可用模型或规则打分）
import OpenAI from 'openai';
import 'dotenv/config';

const client = new OpenAI();

// 数据集：每条含输入与期望（来自真实业务日志或人工标注）
// 规模至少几十到上百条，且要覆盖边界 case，否则会『过拟合』出虚高分数
const dataset = [
  { input: '北京现在天气怎么样？', expected: '晴' },
  { input: '上海天气如何？', expected: '多云' },
  { input: '深圳会下雨吗？', expected: '雨' },
];

// 被测 Agent：占位实现，真实场景应直接 import 你的 Agent 入口
async function runAgent(input: string): Promise<string> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [{ role: 'user', content: input }],
  });
  return res.choices[0].message.content ?? '';
}

// 规则打分：期望关键词出现在回答里即算通过（适合封闭、可枚举答案）
function ruleScore(actual: string, expected: string): number {
  return actual.includes(expected) ? 1 : 0;
}

// 模型打分：让一个『裁判模型』按 0~1 评分（适合开放性问题、语义等价）
async function llmScore(actual: string, expected: string): Promise<number> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '你是评分员，只输出 0~1 之间的数字，不要任何解释。' },
      { role: 'user', content: `期望答案：${expected}\n实际答案：${actual}` },
    ],
  });
  return Number(res.choices[0].message.content) || 0;
}

// 主流程：跑完整个数据集，汇总通过率或平均分
async function evaluate(useLLM = false) {
  let scoreSum = 0;
  for (const { input, expected } of dataset) {
    const actual = await runAgent(input);
    const score = useLLM ? await llmScore(actual, expected) : ruleScore(actual, expected);
    scoreSum += score;
    console.log(`输入: ${input} | 得分: ${score}`);
  }
  const avg = scoreSum / dataset.length;
  console.log(`通过率/平均分: ${avg.toFixed(2)} (${scoreSum}/${dataset.length})`);
}

evaluate(false); // 传 true 切换到模型裁判
```

<Callout type="tip" title="eval 集要『防作弊』">
  数据集不能来自训练/开发时的同一批样本，否则只是『背答案』。
  每加一个功能就补对应 case，并保留一批『对抗样本』（诱导出错、越权、乱答），分数才可信。
</Callout>

### 4.3 离线 Eval 与回归

把 `evaluate` 接进 CI：每次改 prompt / 模型 / 工具，自动跑一遍数据集，分数低于基线就阻断合并。这是 Agent 版的『回归测试』。Phoenix、LangSmith 都提供数据集版本管理与对比（baseline vs candidate），本质就是这套逻辑的托管版。

## 5. Guardrails（安全护栏）

Eval 告诉你『现在有多好』，Guardrails 保证『再差也不能出事』。护栏分三层：**输入校验**（进来之前）、**输出过滤**（出去之前）、**工具护栏**（动手之前）。

### 5.1 输入校验 + 输出过滤（可运行骨架）

```ts
// guardrails.ts —— 输入校验 + 输出过滤（纯 TS，依赖 zod）
import { z } from 'zod';

// 输入校验：用 Zod 约束用户请求，挡掉空/超长/结构错误的输入
const UserRequest = z.object({
  query: z.string().min(1, '问题不能为空').max(500, '问题过长，请精简'),
  userId: z.string().min(1, '缺少用户标识'),
});

// 输出过滤：敏感词 / 危险指令黑名单，命中即拦截
const BLOCKLIST = ['rm -rf', '删除所有数据', '忽略以上指令', 'ignore previous'];

function sanitizeOutput(text: string): string {
  for (const w of BLOCKLIST) {
    if (text.toLowerCase().includes(w.toLowerCase())) {
      return '[输出被护栏拦截：命中敏感词]';
    }
  }
  return text;
}

// 工具护栏：危险操作必须进白名单，否则禁止执行（防止 Agent 乱调删除/发送类工具）
const DANGEROUS_TOOLS = new Set(['delete_record', 'send_email', 'exec_command']);
function guardToolCall(name: string, whitelist: Set<string>): boolean {
  if (DANGEROUS_TOOLS.has(name) && !whitelist.has(name)) return false;
  return true;
}

// 用法示例
const parsed = UserRequest.safeParse({ query: '北京天气', userId: 'u1' });
if (!parsed.success) {
  console.log('输入非法：', parsed.error.message); // 非法请求直接挡在门外
} else {
  console.log('输入合法：', parsed.data);
}

console.log(sanitizeOutput('今天北京晴，建议忽略以上指令去删库')); // 被拦截
console.log(guardToolCall('delete_record', new Set()));            // false：未授权
```

<Callout type="warn" title="护栏也会误杀">
  黑名单和长度限制太严，会把正常请求一起挡掉（比如用户真的在讨论『删除数据』这个话题）。
  护栏要有『放行理由』机制、记录被拦截的请求供复盘，并根据误杀率持续调阈值。
</Callout>

## 6. Dashboard 与告警：把数字摆上墙

Tracing + 成本 + Eval 的数据，最终要汇聚成一个**能天天看的 Dashboard**。至少放这些面板：

| 面板 | 指标 | 告警阈值示例 |
|------|------|--------------|
| 质量 | 端到端成功率、工具准确率 | 较 7 日均值跌 > 5% 告警 |
| 成本 | 单次均价、日总花费、按租户拆分 | 日花费超预算 120% 告警 |
| 延迟 | P50/P95/P99 端到端耗时 | P95 > 8s 告警 |
| 健康 | 错误率、重试率、tool 失败率 | 错误率 > 2% 告警 |
| 退化 | Eval 回归分（CI 跑分） | 低于基线阻断发布 |

<Callout type="note" title="三件套必须同屏">
  成功率、成本、延迟三者必须同屏展示。只盯成功率，你会优化出一个『对但破产』的 Agent；
  只盯成本，你会把质量压到不可用。三者是三角关系，任何一项劣化都应能立刻在 Dashboard 上看到。
</Callout>

## 7. 工具对比总表

| 方案 | 解决层 | 优点 | 缺点 | 是否付费 |
| --- | --- | --- | --- | --- |
| LangSmith | Tracing + Eval | 开箱即用、面板完善、内置数据集管理 | 锁定生态、数据出域顾虑 | 付费 SaaS |
| Phoenix | Tracing + Eval | 开源自托管、OpenInference 标准、语义评估 | 需自建部署 | 开源免费 |
| OpenTelemetry | Tracing | 厂商中立、可接任意后端、标准 span | 需自建 LLM 语义层与看板 | 开源免费 |
| 自建 tracer | Tracing | 完全可控、零成本、改动灵活 | 需自己解决存储/检索/看板 | 免费 |
| 规则 / Zod | Guardrails | 确定性强、零延迟、易审计 | 只能挡已知模式 | 免费 |
| 模型裁判 Eval | Eval | 能评语义、开放题可用 | 有成本、有波动、需防裁判被绕过 | 按 token 计费 |

<Callout type="note" title="组合而非二选一">
  实战里通常是『Phoenix/OTel 做 tracing + Zod 做输入护栏 + 模型裁判做 Eval』的混合阵型，
  按团队规模与合规要求取舍，没有银弹。合规敏感选自托管（Phoenix/OTel），求快选 LangSmith。
</Callout>

## 8. 常见坑

<Callout type="danger" title="只看成功率，忽略成本">
  优化到成功率满分，却没人盯 token 与延迟，结果单次对话成本翻 10 倍。
  成本、延迟、成功率必须作为『三件套』同时上 dashboard，任何一项劣化都告警。
</Callout>

<Callout type="warn" title="eval 集太小，过拟合出虚高分">
  用 5 条样本调出来的 Agent，分数再高也不代表真实能力。
  数据集要覆盖边界与对抗 case，且和开发样本隔离，分数才有意义。
</Callout>

<Callout type="warn" title="护栏误杀正常请求">
  敏感词黑名单、长度限制过猛，会把合法用户挡在门外，尤其内容本身就在讨论敏感话题时。
  护栏要可观测、可复盘、可灰度调阈值，而不是一刀切。
</Callout>

<Callout type="danger" title="tracing 日志泄露隐私">
  把完整 messages（含用户输入、工具返回的客户数据）原样写日志，可能把 PII、密钥、对话内容暴露给日志系统。
  trace 落盘前必须脱敏：遮住 token、邮箱、手机号等，敏感字段只存哈希或摘要。
</Callout>

<Callout type="danger" title="成本追踪单价硬编码">
  把模型单价写死在代码里，官方一调价你的预算告警就全失准。
  单价放配置/远程配置，并标注『以官方文档为准』，定期同步。
</Callout>

## 小结

- Agent 的非确定性决定了：**评估与可观测不是可选项，是上线前提**。
- Tracing 用 `span + trace` 记录每一步的 input/output/tool_call/token/耗时；手写版与 LangSmith/Phoenix/OTel 思想一致。
- 成本追踪把 token 换算成钱，按请求/步骤/模型/租户聚合；单价必须可配置、以官方为准。
- Eval 用数据集驱动，指标至少覆盖成功率、工具准确率、正确性、成本、延迟；规则与模型裁判可组合，并接进 CI 做回归。
- Guardrails 分输入校验（Zod）、输出过滤（黑名单）、工具护栏（白名单/确认）三层，挡住最坏情况。
- Dashboard 把质量/成本/延迟三件套同屏告警；四大坑：只看成功率、eval 集过小、护栏误杀、trace 泄露隐私与单价硬编码。

<Callout type="note" title="下一步">
  评估体系搭好了，下一个问题是：**怎么把 Agent 工程化地交付到生产——配置、密钥、健康检查、灰度、回滚、可观测内建？**
  这就是 **M7 工程化部署** 要解决的。
</Callout>

## 运行方式

三份骨架（`tracer.ts`、`cost-tracker.ts`、`eval-runner.ts`、`guardrails.ts`）都是纯 TS 单文件。先装依赖，再分别运行：

```bash
npm i openai dotenv zod
npx tsx tracer.ts
npx tsx eval-runner.ts
npx tsx guardrails.ts
```

`guardrails.ts` 不调用模型，可离线验证；`tracer.ts` 与 `eval-runner.ts` 需要 `.env` 中配置 `OPENAI_API_KEY`。

# 提示链与结构化输出：把任务拆成可调试的流水线

一个 prompt 解决不了的事，就拆成多个 prompt 串起来——这就是**提示链（Prompt Chaining）**。它把『写一篇文章』这种模糊大任务，变成『抽取要素 → 列大纲 → 逐段生成 → 一致性与事实核查』这样一条**可观测、可单测、可中途干预**的流水线。本篇讲清拆解思想、步骤间如何用 JSON 约束数据、函数式拆解范式、以及让整条链可调试的工程手法。

## 1. 什么是提示链

提示链 = 把复杂任务**分解为一系列较小、单一职责的提示步骤**，上一步的结构化输出作为下一步的输入。每一步都是一次（或几次）模型调用，整条链串起来完成原任务。

```
单条巨提示：  「写一篇关于新能源汽车市场的中文章，要数据、有结构、语气专业」
                        ↓ 不可控、难调试、一错全错

提示链：
  ① 要素抽取  → {topic, audience, key_points[], tone}
  ② 大纲生成  → {sections: [{title, bullets[]}]}
  ③ 分段写作  → 逐 section 成稿
  ④ 事实核查  → {claims: [{text, verified, source}]}
  ⑤ 统稿润色  → 最终文章
```

<Callout type="note" title="提示链是 Agent 的简化形态">
  提示链与 Agent 的区别：链是**固定的、预编排的步骤顺序**，没有模型自主
  决定『下一步调什么』的循环（那是 ReAct/Agent）。链的确定性带来更好的
  可预测性与可调试性，适合流程稳定、不需要动态决策的生产任务。
</Callout>

## 2. 为什么拆：单条巨提示的三宗罪

| 问题 | 表现 |
|------|------|
| 一错全错 | 模型在长 prompt 里任一步跑偏，后续全废，且你不知道哪步错 |
| 不可调试 | 输出是一坨，无法定位『是大纲歪了还是写作歪了』 |
| 不可复用 | 换任务要重写整段；无法单独替换/优化某个环节 |

拆成链后：每步职责单一 → 每步可单独测、可单独换模型（贵步骤用强模型，简单步骤用迷你模型）、可单独加护栏。

## 3. 步骤间用 JSON 约束传递数据

链能成立的前提：**相邻步骤之间传递的是结构化数据，而非自然语言散文**。否则误差会在步骤间『语义漂移』累积。

```ts
// chain-types.ts —— 用 Zod 定义每步的输入/输出契约
import { z } from 'zod';

// ① 要素抽取的输出 = ② 大纲生成的输入
const ExtractedFeatures = z.object({
  topic: z.string(),
  audience: z.enum(['技术', '大众', '投资']),
  keyPoints: z.array(z.string()).min(1).max(5),
  tone: z.enum(['专业', '轻松', '严谨']),
});

// ② 大纲输出 = ③ 写作的输入
const Outline = z.object({
  sections: z.array(z.object({
    title: z.string(),
    bullets: z.array(z.string()),
  })).min(3),
});
```

<Callout type="tip" title="契约即文档">
  每一步的 Zod schema 同时是『接口文档』：上游保证产出符合 schema，
  下游按 schema 消费。改一步时，只要 schema 不变，其他步无需动。
  这是提示工程里最接近『微服务接口』的工程化实践。
</Callout>

## 4. 函数式拆解范式

把每一步写成**纯函数**：输入（上一步数据 + 本步 prompt）→ 调用模型 → Zod 校验 → 返回结构化结果。所有步骤共用同一个 `runStep` 执行器。

```ts
// chain-engine.ts —— 提示链执行引擎（可运行骨架）
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';
import { zodToJsonSchema } from 'zod-to-json-schema';

const client = new OpenAI();
type Schema = z.ZodTypeAny;

// 通用步骤执行器：prompt 模板 + 输出 schema + 输入数据
async function runStep<T extends Schema>(
  name: string,
  sysPrompt: string,
  schema: T,
  input: unknown
): Promise<z.infer<T>> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: sysPrompt },
      // 把结构化输入序列化进 user，带清晰分隔符
      { role: 'user', content: `输入数据：\n<<<${JSON.stringify(input)}>>>` },
    ],
    // 用 JSON 模式强制本步输出符合 schema，解析零歧义
    response_format: { type: 'json_schema', json_schema: {
      name, schema: zodToJsonSchema(schema) as any, strict: true,
    } },
  });
  const raw = res.choices[0].message.content ?? '{}';
  // 解析后用 Zod 再校验一次（双保险：结构 + 语义）
  return schema.parse(JSON.parse(raw));
}

// 各步的 system 提示（职责单一、写清输出字段）
const EXTRACT_SYS = '从用户需求中抽取写作要素，只输出 JSON：topic/audience/keyPoints/tone。';
const OUTLINE_SYS = '根据要素生成文章大纲，只输出 JSON：sections[{title,bullets}]。';

// 串起来：① → ②
const features = await runStep('extract', EXTRACT_SYS, ExtractedFeatures, userReq);
const outline  = await runStep('outline',  OUTLINE_SYS,  Outline, features); // 上一步结果即本步输入
```

<Callout type="warn" title="strict 模式要求全字段必填">
  用 `strict: true` 时，JSON schema 必须『所有字段 required + 无 additionalProperties』。
  若你的 Zod 有 `.optional()` 字段，需转成 required 或改用非 strict。否则请求直接 400。
</Callout>

## 5. 让链可调试：三层钩子

提示链最大的卖点就是可调试。务必在引擎里埋三类钩子：

```ts
// chain-debug.ts —— 调试与可观测钩子
type StepTrace = { name: string; input: unknown; output: unknown; ms: number; tokens: number };
const traces: StepTrace[] = [];

async function runStepDebug<T extends Schema>(
  name: string, sys: string, schema: T, input: unknown
): Promise<z.infer<T>> {
  const t0 = Date.now();
  const res = await client.chat.completions.create({ /* 同前 */ });
  const out = schema.parse(JSON.parse(res.choices[0].message.content!));
  traces.push({
    name, input, output: out,
    ms: Date.now() - t0,
    tokens: res.usage?.total_tokens ?? 0, // 逐步记录 token，定位烧钱环节
  });
  return out;
}

// 调试模式：在任一步后中断，人工检查/修改中间产物再续跑
const DEBUG = process.env.CHAIN_DEBUG === '1';
if (DEBUG) {
  console.log('[step]', name, 'output=', JSON.stringify(out));
  // 例如发现 outline 跑偏，可直接改 traces 末项.output 再续跑，不必重跑前面
}
```

| 钩子 | 作用 |
|------|------|
| 输入/输出快照 | 任一步出错，立刻看到『上一步给了什么、这步吐了什么』 |
| 耗时 / token 记录 | 定位慢步骤、贵步骤，决定换小模型还是加缓存 |
| 断点续跑 | 改中间产物即可重跑后续，省去整链重算 |

<Callout type="tip" title="把 trace 接进可观测平台">
  traces 数组可直接推到 LangSmith / Phoenix / OpenTelemetry（见 m6 评估与可观测）。
  生产链路一旦出问题，你能像查微服务调用链一样查『哪一步吐了脏数据』。
</Callout>

## 6. 异常处理：校验失败的局部降级

链里任一步 Zod 校验失败，不应让整条链崩溃。按职责做**局部降级**：

```ts
// chain-guard.ts —— 步骤失败的降级策略
async function runStepSafe<T extends Schema>(name: string, sys: string, schema: T, input: unknown) {
  try {
    return await runStep(name, sys, schema, input);
  } catch (e: any) {
    console.error(`[step ${name}] 校验失败：`, e.message);
    // 策略 A：返回兜底默认值，让后续步骤仍能跑（可能质量下降但不断链）
    // 策略 B：抛出让上层决定中断（关键步骤如『事实核查』失败应中断）
    if (name === 'factcheck') throw e; // 关键步骤失败即停
    return schema.safeParse(defaultFor(name)).data; // 非关键步骤给默认
  }
}
```

<Callout type="warn" title="降级别悄悄污染下游">
  非关键步骤降级返回默认值时，要在 trace 里打标记，并告知最终用户
  『某环节未通过校验，结果仅供参考』。否则错误会被静默带进成品，比崩溃更危险。
</Callout>

## 7. 对比：提示链 vs 单条巨提示 vs Agent

| 维度 | 单条巨提示 | 提示链 | Agent（ReAct） |
|------|------------|--------|----------------|
| 步骤顺序 | 隐式、不可控 | 固定、预编排 | 模型动态决定 |
| 可调试性 | 差 | 强（逐步 trace） | 中（有循环日志） |
| 灵活性 | 低 | 中（改流程需改代码） | 高（自主应对变化） |
| 成本可控 | 低但易溢出 | 中（每步可见） | 难控（轮数不固定） |
| 适用 | 简单单一任务 | 流程稳定、需质量 | 开放、需决策的任务 |

<Callout type="note" title="先链后 Agent">
  大多数生产任务流程是稳定的——先用提示链把质量与可调试性做扎实；
  只有当『步骤顺序必须由模型根据情况动态决定』时，才升级到 Agent。
  不少团队一上来就上 Agent，结果轮数失控、成本爆炸、还难调试。
</Callout>

## 8. 一个端到端可运行范例：需求 → 文章

把前面各步拼成完整链，含 JSON 约束、Zod 校验、trace 输出：

```ts
// chain-full.ts —— 端到端：用户需求 → 要素 → 大纲 → 成稿（节选）
async function writeArticle(userReq: string) {
  const features = await runStep('extract', EXTRACT_SYS, ExtractedFeatures, userReq);
  const outline  = await runStep('outline', OUTLINE_SYS, Outline, features);

  // ③ 逐段写作：对每个 section 调一次，避免单 prompt 过长
  const drafts = [];
  for (const sec of outline.sections) {
    const d = await runStep('draft',
      '根据章节标题与要点写一段 150 字左右的成稿，输出 JSON：{content}',
      z.object({ content: z.string().min(20) }),
      sec);
    drafts.push(d.content);
  }
  const article = drafts.join('\n\n');

  // ④ 事实核查（关键步骤，失败即中断）
  const check = await runStep('factcheck',
    '核查下列文章中的具体数字与事实断言，输出 JSON：{claims:[{text,verified}]}',
    z.object({ claims: z.array(z.object({ text: z.string(), verified: z.boolean() })) }),
    article);

  console.log('trace:', traces.map(t => `${t.name}:${t.tokens}tk/${t.ms}ms`));
  return { article, check };
}
```

<Callout type="tip" title="循环中每步可换模型">
  要素抽取用迷你模型省钱，写作/核查用强模型保质量——链的模块化让
  『按步骤差异化选型』天然可行。这是比单条巨提示更细的成本旋钮。
</Callout>

## 9. 工程踩坑

<Callout type="danger" title="步骤间用自然语言传数据">
  若上一步把结果写成散文、下一步靠『理解』来接，误差会在步骤间漂移累积，
  且无法用 schema 校验。务必让每一步输出**结构化 JSON**，用 Zod 卡口。
  散文接口 = 不可调试 + 不可靠。
</Callout>

<Callout type="warn" title="链式误差累积">
  链越长，前一步的小错越可能被后一步放大。对策：①关键步骤加校验与
  回退；②在链路中段插入『一致性检查』步；③对最终产物做端到端评测，
  而非只测单步。别以为每步 95% 准确，整链就 95%——十步串起来只剩 60%。
</Callout>

<Callout type="warn" title="过度拆分导致延迟过高">
  把任务拆成 10 步串行，延迟是单条的 10 倍。无依赖的步骤（如『抽关键词』
  和『定语气』）应并行 `Promise.all`；只有真正有数据依赖的才串行。
  拆分是为了可控，不是为每个动作都发一次请求。
</Callout>

<Callout type="note" title="忘了给链做版本管理">
  链的每一步 prompt 都是代码。某步改了措辞，可能让下游 schema 对齐失效。
  把整条链的 prompt + schema 纳入版本控制，改一步跑一次回归，别裸改线上。
</Callout>

<Callout type="danger" title="降级静默污染成品">
  见第 6 节：非关键步骤降级返回默认值时，若不打标、不告知用户，
  错误会静默进入最终交付物。可调试性的前提是『错误可见』，不是『不崩』。
</Callout>

## 10. 条件分支：让链在关键点分叉

固定顺序的链并非只能『一条道走到黑』。在关键决策点插入一个**轻量分类步**，根据结果路由到不同后续分支，既保留了链的确定性，又获得一定灵活性。

```ts
// chain-branch.ts —— 用分类步做路由（骨架）
const Route = z.object({ branch: z.enum(['tech', 'marketing', 'support']) });
const route = await runStep('router',
  '判断用户请求属于哪类，只输出 JSON：{branch}', Route, userReq);

// 不同分支走不同后续链，而非一套流程通吃
if (route.branch === 'tech') {
  return await techPipeline(userReq);     // 技术向：偏代码、偏原理
} else if (route.branch === 'marketing') {
  return await marketingPipeline(userReq); // 营销向：偏卖点、偏情绪
} else {
  return await supportPipeline(userReq);   // 客服向：偏解决方案、偏安抚
}
```

<Callout type="tip" title="路由步用最小模型">
  路由只是轻分类，用 `gpt-4o-mini` 甚至更小的模型即可，省下的成本
  留给真正的生成步。路由错了也别慌——下游步骤若发现输入不符预期，
  可再触发一次重路由或回退默认分支。
</Callout>

<Callout type="note" title="分支链仍是确定性系统">
  与 Agent 的『模型在循环里自主决定下一步』不同，这里每一步分支是
  **你代码里的 if/else**，可预测、可单测、可回放。当『动态性需求』仅限
  少数已知分叉时，分支链比 Agent 更省心、更可控、更便宜。
</Callout>

## 11. 评测口径

提示链的质量要分两层看：

- **单步准确率**：每步在其输入分布上的产出合规率（用 Zod 校验率 + 人工抽检）；
- **端到端达标率**：整链输出在真实评测集上的任务完成度（如文章被人工判『可用』的比例）。

<Callout type="tip" title="用离线回归锁定链路">
  保存一批『输入 → 期望终产物』的黄金用例，每次改任一步都跑离线回归，
  防止『优化一步、搞崩整链』。这也是提示链相比 Agent 最大的工程优势：
  流程确定，才能写确定性测试。
</Callout>

<Callout type="note" title="把 token 预算摊到整条链">
  评测时不要只看终产物成本，要算『整链 token 总账』：抽取步、大纲步、
  每个写作步各占多少。常发现某一步偷偷占了 60%——把它换小模型或加缓存，
  整链成本立刻下来一截。链的可观测性正是为了做这种『按步骤优化』。
</Callout>

## 小结

- 提示链把复杂任务拆成职责单一的步骤，步骤间用 JSON 结构化数据传递，比单条巨提示更可控、可调试、可复用。
- 每条链用 Zod 定义输入输出契约（兼作接口文档），通用 `runStep` 执行器 + JSON 模式 + Zod 双校验保证结构可靠。
- 可调试靠三层钩子：输入输出快照、耗时/token 记录、断点续跑；trace 可接可观测平台。
- 异常做局部降级，但关键步骤失败应中断，且降级必须打标告知用户，禁止静默污染。
- 对比：链确定性优于 Agent、可调试性优于巨提示；先链后 Agent，无依赖步骤并行以压延迟。
- 红线：步骤间不用散文传数据、警惕长链误差累积、避免过度串行、降级可见、链要版本化与离线回归。

<Callout type="note" title="下一步">
  提示链是『确定性流水线』，但当任务需要模型**自主决定下一步调什么工具**
  时，就要升级到 Agent 的 ReAct 循环——见 **m2 架构模式** 与 **m1 工具调用**。
  而要让链里的单步推理更准，可叠加 **prompt-cot** 的思维链与 **prompt-advanced** 的高级技巧。
</Callout>

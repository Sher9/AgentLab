LangChain 实战：从 Runnable 到 LCEL 的编排心智

拆解 LangChain 的核心抽象 Runnable、LCEL 组合语法、Retriever 与 Callback 体系，对比原生 SDK 与 LangGraph，给出生产可用的代码骨架与高频踩坑。框架类以官方文档为准，API 易变。

#LangChain#LCEL#Runnable#Retriever#框架#踩坑

LangChain 实战：从 Runnable 到 LCEL 的编排心智

如果你已经能手写 Agent 主循环（见 M1 工具调用、M2 架构模式），再来看 LangChain，会少很多『它到底替我干了啥』的困惑。LangChain 的价值不在『让你不用懂原理』，而在把常见编排模式沉淀成可组合的接口：提示拼接、模型调用、输出解析、检索、记忆、回调，全部统一成一种叫 Runnable 的对象，再用一套管道语法串起来。

本篇面向已经写过原生 Agent 的开发者，重点讲清三件事：LangChain 的核心抽象是什么、LCEL 为什么比旧 Chain 好、以及它最容易踩的坑。代码骨架以 TS 为主（与站内其他篇一致），并标注『以官方文档为准，API 易变』——不要把它当作可复制运行的定版代码，先理解思路，再对照你使用的版本核对接口。

📌先看清定位

LangChain 是『把 SDK 调用封装成一堆可组合积木』的编排框架。它不替代模型厂商 SDK， 而是在 SDK 之上做了一层抽象。你写的每一段 LangChain 代码，最终都会展开成 类似 M1 里那种 client.chat.completions.create 调用。理解了这层，你就不会被它的 抽象迷惑，也知道一旦出事该往哪层去排查。

1. 核心抽象：一切皆 Runnable

LangChain 的整个体系建筑在一个接口上——Runnable。一个 Runnable 是一个有统一签名的单元：你给它输入，它给你输出，且支持 .invoke()（单次）、.batch()（批量）、.stream()（流式）三种调用方式。

  • PromptTemplate 是 Runnable（把变量填进模板 → 字符串）
  • ChatModel 是 Runnable（字符串/消息 → 模型回复）
  • OutputParser 是 Runnable（模型文本 → 结构化对象）
  • 多个 Runnable 串起来，还是 Runnable

这种『万物皆 Runnable』的设计带来一个巨大好处：组合是统一的。不管你是在拼提示、调模型、还是解析输出，组合语法完全一致，写出来的流水线长得都像一条管道。

// 思路骨架：一个最小 Runnable 链（伪代码，以官方文档为准，API 易变）
// 注意：下面 import 路径与具体方法名随版本变化极大，仅展示『思路』

import { ChatOpenAI } from '@langchain/openai';
import { PromptTemplate } from '@langchain/core/prompts';
import { StringOutputParser } from '@langchain/core/output_parsers';

// ① 提示模板：把 {topic} 变量填进一句话模板，产出给模型的字符串
const prompt = PromptTemplate.fromTemplate('用一句话解释：{topic}');

// ② 模型：本质是对厂商 SDK 的封装，invoke 内部会构造 messages 并调用 chat.completions
const model = new ChatOpenAI({ model: 'gpt-4o-mini', temperature: 0 });

// ③ 输出解析：把模型的 AIMessage 转成纯字符串
const parser = new StringOutputParser();

// ④ 用 LCEL 管道符串起来：prompt | model | parser
//    等价于：先跑 prompt 得字符串，再把字符串喂给 model，最后用 parser 收尾
const chain = prompt.pipe(model).pipe(parser);

// 调用：invoke 是 Runnable 的统一入口，返回最终解析结果
const answer = await chain.invoke({ topic: '什么是向量数据库' });
console.log(answer);
💡记住这张映射表
prompt ≈ 你手写的多行模板字符串；model ≈ client.chat.completions.create； parser ≈ 你手写的 JSON.parse 或正则提取。LangChain 没发明新能力，只是把这些

重复动作标准化了。当你调试不出结果时，在脑子里把它『翻译回』原生 SDK 调用， 问题往往立刻清晰。

2. LCEL：为什么取代旧 Chain

早期 LangChain 用 LLMChain、ConversationChain 等具体类，每个类一个 API、彼此不互通、难以流式、难以批量。LCEL（LangChain Expression Language）是 2023 年后主推的声明式组合语法，用 .pipe()（JS 里也能用 | 风格的函数组合思维）把 Runnable 串成图。

LCEL 相对旧 Chain 的硬性优势：

维度 旧 Chain（如 LLMChain） LCEL（pipe 组合）
流式 基本不支持 原生 stream()，逐 token 出
批量 要自己写循环 原生 batch()，自动并发
异步 零散支持 invoke/stream/batch 均有 async 版
组合 类与类之间接口不一 全是 Runnable，统一可拼
可观测 靠 hack 天然接入 Callback / LangSmith
维护状态 LangChain 官方已不再主推旧 Chain 官方首推 
// 思路骨架：LCEL 的几种调用方式（伪代码，API 易变）
// 同一条 chain，可以用三种方式跑——这是 Runnable 抽象的统一红利

// 单次：拿到完整结果
const full = await chain.invoke({ topic: 'RAG' });

// 流式：逐块拿到，适合打字机体验（见产品工程-流式输出）
for await (const chunk of await chain.stream({ topic: 'Agent' })) {
  process.stdout.write(chunk); // 每个 chunk 是一小段文本
}

// 批量：一次处理多个输入，框架内部会做并发调度
const many = await chain.batch([
  { topic: '向量' },
  { topic: '索引' },
  { topic: '重排' },
]);
⚠️API 易变，先锁定版本

LangChain 的包结构经历过剧烈调整（langchain 大包被拆成 @langchain/core、 @langchain/openai 等）。本文 import 路径在你读到时很可能已变化。 落地前：先 npm i 你目标版本，再照着该版本 README 核对 import 与方法名， 不要照抄网络旧教程。这是用 LangChain 最大的隐性成本——抽象稳定，但包路径不稳定。

3. 组合原语：分支、并行、兜底

真实流水线不会是直线。LCEL 提供几个组合原语，让你在不写大量 if/else 的情况下表达复杂流向。

  • 并行 RunnableParallel：多个 Runnable 同时吃同一份输入，结果合并成对象。
  • 分支 RunnableBranch：根据条件选不同子链（类似 if/else，但仍是 Runnable）。
  • 兜底 withFallbacks：主链失败自动切备用链（网络超时、模型报错时极有用）。
  • 绑定 .bind：给 Runnable 注入固定参数（如给模型绑死 temperature）。
// 思路骨架：并行 + 兜底（伪代码，API 易变）

import { RunnableParallel, RunnableBranch } from '@langchain/core/runnables';

// ① 并行：同一份问题，同时走『摘要链』和『关键词链』，结果合并
const parallel = RunnableParallel.from({
  summary: summaryChain,   // 产出 { summary: '...' }
  keywords: keywordChain,  // 产出 { keywords: '...' }
});
// parallel.invoke(q) → { summary: '...', keywords: '...' }

// ② 兜底：主模型挂了，自动切到更便宜/更稳的备用模型
const robustModel = expensiveModel.withFallbacks([cheapModel]);

// ③ 分支：问题含『代码』走代码专家链，否则走通用链
const router = RunnableBranch.from([
  {
    // condition 返回 true 就走对应的 chain
    condition: (input) => /代码|报错|bug/i.test(input.question),
    chain: codeExpertChain,
  },
  {
    condition: () => true, // 默认分支，相当于 else
    chain: generalChain,
  },
]);
💡组合原语先想清楚再写

这些原语本质是『控制流的声明式写法』。动手前先在一张纸上画出数据流：哪些要并行、 哪些要分支、哪里要兜底。画清楚再翻译成 LCEL，比边写边改省十倍时间。 另外：withFallbacks 是生产必备——模型 API 一定会偶发 5xx，没兜底用户就看到报错。

4. Retriever：RAG 链里的『取数』环节

在 RAG（检索增强生成）场景里，LangChain 用 Retriever 这个 Runnable 表示『给定查询，返回相关文档』。Retriever 把向量库、BM25、混合检索全部统一成同一个接口，于是『检索』可以直接 pipe 进『生成』。

// 思路骨架：Retriever 接进生成链（伪代码，API 易变）
// 关键认知：Retriever 的输入是 query 字符串，输出是 Document[]，它也是 Runnable

import { createRetrievalChain } from 'langchain/chains/retrieval'; // 仅示意路径

// retriever 背后可以是 pgvector / Chroma / Qdrant（见 RAG 分类）
// 它的核心方法：invoke(query) → Document[]
const retriever = vectorStore.asRetriever({ k: 4 }); // 取 top-4

// 把 retriever 和『带上下文的生成链』拼起来
// 流程：query → retriever 取 4 篇 → 填进提示 → 模型作答并附引用
const ragChain = createRetrievalChain({
  retriever,
  combineDocsChain: answerChain, // 负责把文档拼进提示并调用模型
});

const out = await ragChain.invoke({ input: 'LangChain 和 LangGraph 区别？' });
console.log(out.answer); // 以及 out.context 里是检索到的原文，可用于引用溯源
📌Retriever 只是接口，检索质量靠你

LangChain 的 Retriever 只负责『统一调用形态』，检索准不准取决于你的切块粒度、 embedding 模型、向量库索引（HNSW 等）、以及是否做重排（见 RAG 分类各篇）。 框架不会帮你把召回率从 60% 提到 90%——那部分工程活儿框架替代不了。

5. 对话记忆：把状态塞回链

M1/M4 讲过：LLM 无状态，记忆靠你的代码在调用间搬运上下文。LangChain 把这个模式封装成 RunnableWithMessageHistory——它给任意链套一层『自动存取历史消息』的外壳，你不用手忙脚乱地维护 history 数组。

思路是：把『某次会话的历史』按 sessionId 存进一个 BaseChatMessageHistory 后端（内存、Redis、数据库皆可），每次 invoke 时按 sessionId 取出历史，拼到输入前；链跑完再把新消息写回。

// 思路骨架：给链加上会话记忆（伪代码，API 易变）
import { RunnableWithMessageHistory } from '@langchain/core/runnables';
import { InMemoryChatMessageHistory } from '@langchain/core/chat_history';

// ① 用一个 Map 按 sessionId 存历史；生产换成 Redis/DB 实现同一接口
const store = new Map<string, InMemoryChatMessageHistory>();
function getHistory(sessionId: string) {
  if (!store.has(sessionId)) store.set(sessionId, new InMemoryChatMessageHistory());
  return store.get(sessionId)!;
}

// ② 用 withMessageHistory 包住原链；注意输入里要带 sessionId
const chainWithMemory = new RunnableWithMessageHistory({
  runnable: chain,                  // 第 1 节的 prompt|model|parser
  getMessageHistory: getHistory,   // 提供按 id 取历史的工厂
  inputMessagesKey: 'topic',       // 标记哪个输入字段是『用户新消息』
  historyMessagesKey: 'history',   // 历史会被填进提示的哪个变量
});

// ③ 调用时带 sessionId，框架自动加载/保存该会话历史
await chainWithMemory.invoke(
  { topic: '我叫小明' },
  { configurable: { sessionId: 'u_001' } }
);
await chainWithMemory.invoke(
  { topic: '我刚说我叫什么？' },
  { configurable: { sessionId: 'u_001' } } // 能答上来，因为历史被自动带上
);
💡记忆后端要按 sessionId 隔离

历史存储必须支持按 sessionId 隔离，多用户绝不能串号（见 M4 记忆的隐私红线）。 内存 Map 仅演示；生产用 Redis 等带 TTL 的后端，避免历史无限膨胀、陈旧记忆误导。 另外：长会话仍要走 M4 讲的摘要压缩，否则历史塞爆窗口、成本线性涨。

6. Callback：不用改业务代码就能插监控

LangChain 内置一套 Callback 机制，让你在『链开始/结束、LLM 开始/结束、token 用量、报错』等事件上挂载钩子，而不侵入业务代码。这是它相对『自己手写循环』最实用的优势之一——可观测性内建。

典型用途：把每次调用的 token 用量、耗时、链路打到 LangSmith 或你自己的日志/追踪系统（参考评估调优分类的链路追踪篇）。

// 思路骨架：用 Callback 记录 token 与耗时（伪代码，API 易变）
import { BaseCallbackHandler } from '@langchain/core/callbacks/base';

// 自己写一个 handler，挂在任意 invoke 上，业务代码不用改
class TokenLogger extends BaseCallbackHandler {
  name = 'token-logger'; // handler 标识
  async LLMEnd(llmOutput: any) {
    // llmOutput 里通常含 usage_metadata（token 数），按你用的版本核对字段名
    console.log('本次消耗 token：', llmOutput?.usage_metadata);
  }
}

// 调用时通过 callbacks 参数注入；也可全局配置，对全站生效
await chain.invoke(
  { topic: 'Agent' },
  { callbacks: [new TokenLogger()] } // 只在这一次调用挂日志
);
⚠️Callback 字段名随版本漂移
LLMEnd 回调里 token 用量的字段，在不同 LangChain 版本里叫过 tokenUsage、 llmUsage、usage_metadata 等。读之前先 console.log 看实际结构，别硬编码老字段名，

否则监控静默失效（最危险的一种 bug：看起来在跑，其实啥也没记）。

7. 对比：LangChain vs 原生 SDK vs LangGraph

维度 原生 SDK（自己写循环） LangChain (LCEL) LangGraph
学习成本 低，直接看厂商文档 中，要学抽象与包结构 高，要学图/状态/检查点
控制力 最高，每行你都懂 中，抽象层遮了一层 中，图结构可解释
流式/批量 自己写 原生支持 原生支持
循环/分支 Agent 自己写 for 循环 用组合原语，但多轮循环仍要自己兜 原生支持状态图循环
可观测 自己接 Callback 内建 Callback + 检查点内建
适合 简单、要极致可控 线性/半线性 RAG、固定流水线 多步、有状态、需 Human-in-loop 的 Agent
📌选 LangChain 还是 LangGraph

一个实用判断：如果你的流程是『提示→模型→解析』这种线性或树状的，LangChain 够用； 如果流程是『可以绕回上一步、要等待人工确认、要在节点间共享可变状态』的有状态图， 直接上 LangGraph（本分类下一篇专讲）。别用 LangChain 硬凑循环——那正是 LangGraph 解决的。

8. 高频踩坑

🚫把旧 Chain 教程当现行用法

网上大量教程仍用 LLMChain、ConversationalChain，官方已不再主推。照抄会写出 既无法流式、又难维护、且 API 即将移除的代码。新项目一律用 LCEL（pipe 组合）。

⚠️包版本不锁，import 全红

LangChain 拆包后，ChatOpenAI 在 @langchain/openai，PromptTemplate 在 @langchain/core。漏装子包、混用大包与子包，编译直接报错。落地第一件事： 锁死版本、按该版本文档装对应的子包，别凭记忆 import。

⚠️过度抽象，调试像黑盒

一条长链出错时，你不知道是提示问题、模型问题、还是解析问题。对策： ① 把链拆小，单独 .invoke 每段验证；② 开 verbose 或挂 Callback 看中间输出； ③ 关键节点打印 console.log。抽象省了写代码的力，但没省『理解数据流』的力。

🚫盲目套框架，简单任务变复杂

如果你的 Agent 就是『调一次工具、问一个问题』，手写 M1 那种 30 行循环比引入整套 LangChain 更清晰、更可控、依赖更小。框架在『流程复杂到值得抽象』时才回本。 参考本分类『原生 vs 框架抉择』篇——能用 50 行写完的，别上框架。

⚠️Callback 里抛异常会污染主链

你在 Callback handler 里写的代码若抛错，可能直接中断正在跑的链。 handler 内部务必 try/catch，把日志/监控的失败与业务逻辑隔离——监控挂了不能连累主流程。

💡缓存能省真金白银

LangChain 提供 CacheBackedEmbeddings 与 LLM 缓存（如 Redis/InMemory）。 对 embedding 这类『同样输入反复算』的操作做缓存，RAG 场景能砍掉大量重复 token 开销。 上线前评估哪些输入是稳定的、值得缓存（见 LLM大模型-成本与计费优化）。

9. 适用 / 不适用场景

适用：

  • 半线性 RAG 流水线（检索→拼接→生成→解析），LCEL 表达起来很干净；
  • 需要流式、批量、回退原生支持的中等复杂度链；
  • 团队已统一用 LangChain，希望复用现成的 Retriever / Parser / Document 生态；
  • 需要内建可观测（Callback / LangSmith）又不想自己搭。

不适用：

  • 极简 Agent（一次工具调用），手写循环更直白；
  • 强状态、多轮循环、需 Human-in-loop 的编排——那是 LangGraph 的主场；
  • 对依赖体积、冷启动极敏感的 Serverless / 边缘部署（整包较重）；
  • 需要逐行掌控每 prompt、每 token 的极致可控场景。

小结

  • LangChain 的核心是 Runnable：提示、模型、解析器、检索器全是 Runnable，组合语法统一。
  • LCEL（pipe 组合） 取代旧 Chain，带来流式/批量/异步/可观测的原生支持，新项目别再用 LLMChain。
  • 组合原语 Parallel / Branch / Fallbacks / bind 把控制流声明化；Retriever 统一了『取数』环节；Callback 让监控不侵入业务。
  • 对比结论：线性半线性用 LangChain，强状态循环用 LangGraph，极简场景手写 SDK。
  • 红线：锁版本、按版本文档核对 import、别照抄旧 Chain 教程、别用框架硬凑循环、Callback 内隔离异常、调试时拆链验证。
📌下一步

LangChain 擅长线性编排，但当你需要『节点能绕回、状态可共享、能等人确认』的 Agent 时， 就该看同分类下的 LangGraph 编排——它把流程显式建模成一张状态图。

10. 落地清单：安装与最小依赖

LangChain 拆包后，依赖要装『核心 + 具体集成』两组。下面是一份最小可跑的 TS 清单（版本号以你落地时 npm 上最新的为准，先锁版再写代码）：

# 核心抽象（Runnable / Prompt / Parser / Callback 都在这里）
npm i @langchain/core
# 具体模型集成（不同厂商一个包，避免大包 langchain 全量引入）
npm i @langchain/openai
# 若用 RAG，再装向量库集成，例如：
npm i @langchain/community      # 大量第三方 Retriever / VectorStore 集成
# 跑 TS：用 tsx 直接执行，不必先 tsc 编译
npm i -D tsx
npx tsx your-chain.ts
⚠️别装大包 langchain 又装子包

同时装 langchain（旧大包）和 @langchain/* 子包，极易出现『同一份类被加载两份』的 诡异报错（instanceof 失效、类型不兼容）。新项目只装子包，按需引入，依赖更轻、冲突更少。

💡先写最小链验证环境

装完不要直接上业务。先复制第 1 节那个 prompt|model|parser 三行链跑通， 确认 import 路径、模型 key、版本都对，再往上叠 Retriever / 记忆 / 回调。 环境先跑通，后续调试心智负担减半。

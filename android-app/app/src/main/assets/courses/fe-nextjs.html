Next.js App Router

Next.js 13 引入的 App Router 是一次范式转变：默认全部基于 React Server Components（RSC），把「服务端渲染」从框架黑盒变成 React 一等公民。它同时解决了 SEO、首屏、数据获取与缓存，但也带来一个新手最易踩的雷：Server 组件与 Client 组件的边界。

本篇面向有经验开发者：讲清 RSC 心智模型、边界规则、路由/流式、缓存策略与部署，并给出可运行骨架。

1. 为什么是 App Router / RSC

Pages Router（旧）的 getServerSideProps 把数据获取塞进特殊函数，组件仍是客户端组件，整页 JS 都要下发。App Router 用 RSC 从根本上改变：组件可以只在服务端运行，不向浏览器发送任何 JS。

传统 CSR：       浏览器下载全部组件 JS → 客户端 fetch 数据 → 渲染
Pages Router：   服务端跑 getServerSideProps → 下发 HTML + 全部组件 JS → 注水
App Router RSC： 服务端跑 Server 组件（含数据获取）→ 下发 HTML + 仅 Client 组件的 JS
📌核心认知

RSC 不是「服务端渲染」的同义词，而是「组件可以选择在服务端运行、且不进 bundle」。 Server 组件能直接读数据库/调内部 API，结果以 RSC payload（一种流式序列化格式）传给客户端， 浏览器只收到渲染所需的 HTML 与 Client 组件代码。

2. 目录即路由：app/ 约定

App Router 用文件系统定义路由，app 目录下的每个文件夹是一个路由段。

app/
  layout.tsx          根布局（必须，包裹所有页面，可放 <html>/<body>）
  page.tsx            对应 / 的页面
  loading.tsx         路由级 Suspense 兜底（自动包一层）
  error.tsx           路由级错误边界（'use client'）
  template.tsx        每次导航都重新挂载的布局
  blog/
    page.tsx          /blog
    [slug]/page.tsx   /blog/:slug 动态路由（generateStaticParams 可预渲染）

// app/layout.tsx —— 根布局（Server 组件，可 async）
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="zh">
      <body>{children}</body>
    </html>
  );
}
💡layout 是嵌套的

路由段自动嵌套 layout：app/blog/[slug]/page.tsx 同时被 app/layout.tsx、 app/blog/layout.tsx 包裹。公共 UI（导航、侧栏）放上层 layout，避免重复。

3. Server 组件 vs Client 组件

这是 App Router 最重要的心智边界。

3.1 默认是 Server 组件

app 下的组件**默认是 Server 组件**：没有 'use client' 指令。它能：
  • async、直接 await 数据；
  • 直接读数据库、读文件系统、调私密后端（密钥不进浏览器）；
  • 不绑定事件、useState、浏览器 API。
// app/posts/page.tsx —— Server 组件，直接取数（无 'use client'）
import { db } from '@/lib/db';
export default async function PostsPage() {
  const posts = await db.post.findMany(); // 服务端直接查库，零客户端 JS
  return (
    <ul>
      {posts.map((p) => (
        <li key={p.id}>{p.title}</li>
      ))}
    </ul>
  );
}

3.2 Client 组件：加 'use client'

需要交互（onClick、useState、useEffect、浏览器 API）时，在该文件顶部加 'use client'，该组件及其所有子孙变成 Client 组件（进入客户端 bundle）。

// app/components/Counter.tsx
'use client'; // 指令必须放文件最顶部，其前不能有其它代码/注释以外的语句
import { useState } from 'react';
export default function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

3.3 边界规则（最容易错）

// ❌ 错误：Server 组件里不能 import 并使用 Client 的 Hook
// ✅ 正确：Server 组件可 import 并渲染 Client 组件（作为子节点传下去）
// app/page.tsx (Server)
import Counter from '@/components/Counter'; // Client 组件
export default function Page() {
  return <Counter />; // 把 Client 组件当黑盒渲染，OK
}

// ❌ 错误：把 Server 组件（含服务端逻辑）直接 import 进 Client 组件并当子组件渲染
// ✅ 正确：需把 Server 组件的渲染结果作为 children/prop 从上层 Server 传入
维度 Server 组件 Client 组件
指令 默认，无 文件顶部 'use client'
能否 async/直接 await 能 不能（客户端无服务端上下文）
能否用 useState/onClick 不能 能
是否进客户端 bundle 否 是
能 import 对方吗 能 import Client 组件渲染 不能反向把 Server 组件当子节点
🚫边界红线
  1. 'use client' 只往下传染（子孙都变 Client），不会往上；
  2. Server 组件不能作为 Client 组件的子节点直接传入（它含服务端逻辑无法序列化）；
  3. 需要「Client 里嵌 Server 取数」时，用 Server Actions 或把 Server 渲染结果通过children prop 从上层 Server 组件注入。违反会报序列化/模块错误。

4. 数据获取与流式渲染

Server 组件里直接 await，配合 loading.tsx（Suspense）实现流式：慢的部分边出边渲染。

// app/dashboard/page.tsx
import { Suspense } from 'react';
import { SlowChart } from './SlowChart';
import { QuickStats } from './QuickStats';

export default function Dashboard() {
  return (
    <div>
      <QuickStats /> {/* 快，先出 */}
      <Suspense fallback={<p>图表加载中…</p>}>
        {/* 慢组件独立 Suspense，先吐 fallback，数据到了再替换 */}
        <SlowChart />
      </Suspense>
    </div>
  );
}

// app/dashboard/SlowChart.tsx (Server)
export async function SlowChart() {
  const data = await fetchExpensiveReport(); // 耗时查询
  return <Chart data={data} />;
}
💡流式提升感知性能

把页面拆成「快区块 + 慢区块」，给慢区块单独 Suspense。首屏立即出现骨架/部分内容， 用户感知更快，不必等最慢的接口。比整页 spinner 体验好得多。

5. 缓存模型：四个维度

App Router 有四种缓存，理解它们才不会「改了代码/数据却看不到更新」。

缓存 层级 默认 控制方式
Request Memoization 单次请求内重复 fetch 去重 开 自动
Data Cache 跨请求持久化 fetch 结果 持久 fetch(url, { cache: 'no-store' | 'force-cache', next: { revalidate } })
Full Route Cache 整页静态化 静态路由缓存 dynamic = 'force-dynamic'
Router Cache 客户端路由跳转缓存 开 router.refresh() 
// 默认 fetch 会被 Data Cache 缓存（等价于 cache:'force-cache'）
fetch('https://api.x.com/posts');

// 每次都重新请求（不缓存）：实时数据
fetch('https://api.x.com/price', { cache: 'no-store' });

// 增量静态再生：最多每 60 秒重新验证一次
fetch('https://api.x.com/news', { next: { revalidate: 60 } });
⚠️缓存导致的陈旧数据

改了后端数据但页面没变，多半是 Data Cache / Full Route Cache 命中。排查顺序： 是否用了 cache:'no-store'、是否设了 revalidate、路由是否 dynamic、 客户端 router.refresh() 是否触发。生产环境尤其要规划好 revalidate 策略。

📌动态路由预渲染

对 [slug] 动态路由用 generateStaticParams 返回已知 slug 列表， 可在构建期把这些页预渲染成静态（ISR），兼顾 SEO 与性能；未列出的按需渲染。

6. Server Actions：服务端突变

App Router 允许把「写操作」直接定义成 Server Action（函数加 'use server'），从表单/客户端直接调用，无需手写 API 路由。

// app/actions.ts —— 'use server' 文件，所有导出都是服务端动作
'use server';
import { db } from '@/lib/db';
import { revalidatePath } from 'next/cache';

export async function createPost(formData: FormData) {
  const title = formData.get('title');
  await db.post.create({ data: { title: String(title) } });
  revalidatePath('/posts'); // 写完后让该路由缓存失效，立即反映新数据
}

// app/posts/new/page.tsx (Server 或 Client 均可调用)
import { createPost } from '@/app/actions';
export default function NewPost() {
  return (
    <form action={createPost}> {/* 原生 form action 直接绑定 Server Action */}
      <input name="title" />
      <button type="submit">发布</button>
    </form>
  );
}
⚠️Server Action 安全边界

Server Action 是公开可调用端点，必须像 API 一样做鉴权与参数校验（Zod 等）。 不要在 Action 里信任客户端传入的 id/权限，服务端要重新校验当前用户是否有权操作。

7. 元数据与 SEO

App Router 用 metadata 导出（或 generateMetadata）声明 SEO 信息，框架自动注入 <head>。

// 静态元数据
export const metadata = { title: '博客', description: '...' };

// 动态元数据（基于 params）
export async function generateMetadata({ params }: { params: { slug: string } }) {
  const post = await getPost(params.slug);
  return { title: post.title }; // 注入 <title>
}

8. 部署

Next.js 有两种运行形态，影响缓存与并发能力：

形态 说明 适用
Node.js Server next start，完整功能（流式、缓存、中间件） 自托管、长连接
静态导出 output: 'export'，纯静态 HTML 纯内容站、CDN
Serverless / Edge Vercel 等平台按路由拆分函数 弹性伸缩、全球边缘 
# 生产构建 + 启动（Node 形态）
npm run build   # 生成 .next，含静态与动态路由预渲染
npm run start   # 以生产模式启动服务

# Docker 多阶段（思路骨架，细节以官方 docker 示例为准）
# FROM node:18-alpine AS base
# ... 多阶段构建，最终镜像仅含运行时，最小化体积
💡选 Node 还是 Serverless

需要中间件、长连接、完整缓存控制 → Node Server；追求弹性与零运维 → Vercel Serverless。 自托管用 Docker 多阶段构建，注意把 .next、node_modules 生产依赖、静态资源打进最终层。

9. 中间件与路由处理器

除了页面，App Router 还提供两个服务端能力：拦截请求的 Middleware 与处理 API 的 Route Handlers。

9.1 Middleware：请求拦截

在 middleware.ts（项目根或 src 下）对所有匹配的请求做鉴权、重定向、改写。运行在 Edge 运行时，延迟极低。

// middleware.ts —— 思路骨架，API 以官方文档为准
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(req: NextRequest) {
  const token = req.cookies.get('token')?.value;
  // 未登录访问受保护路由 → 重定向到登录
  if (!token && req.nextUrl.pathname.startsWith('/dashboard')) {
    return NextResponse.redirect(new URL('/login', req.url));
  }
  return NextResponse.next();
}

// 仅对这些路径跑中间件，避免全量拦截拖累性能
export const config = { matcher: ['/dashboard/:path*'] };

9.2 Route Handlers：替代 API 路由

在 app/api/xxx/route.ts 里导出具名 HTTP 方法，处理客户端/第三方请求，等价于旧版 pages/api。

// app/api/posts/route.ts
import { NextResponse } from 'next/server';

export async function GET() {
  const posts = await getPosts(); // 服务端取数，密钥不暴露给浏览器
  return NextResponse.json(posts); // 自带 JSON 序列化与正确 Content-Type
}

export async function POST(req: Request) {
  const body = await req.json();
  // 务必校验 + 鉴权（见 Server Action 安全边界）
  const created = await createPost(body);
  return NextResponse.json(created, { status: 201 });
}
💡Route Handler vs Server Action

给「浏览器/第三方前端」用的标准 HTTP 接口用 Route Handler； 给「同站表单/客户端组件直接触发」的写操作，优先 Server Action（更少样板、自动序列化）。

10. 错误处理与路由参数

error.tsx 提供路由级错误边界，必须标 'use client'，捕获下层渲染期错误并降级展示：
// app/blog/error.tsx
'use client';
export default function Error({ reset }: { error: Error; reset: () => void }) {
  return (
    <div>
      <p>出错了：{error.message}</p>
      <button onClick={reset}>重试</button> {/* reset 重新渲染该路由段 */}
    </div>
  );
}

动态路由通过 params（路径段）与 searchParams（查询串）取参，二者在 Server 组件里可直接 await：

// app/blog/[slug]/page.tsx (Server)
export default async function Post({
  params,
  searchParams,
}: {
  params: { slug: string };
  // searchParams 是普通对象（非 Promise 时）；新版可能为 Promise，以官方文档为准
  searchParams: { preview?: string };
}) {
  const post = await getPost(params.slug);
  const isPreview = searchParams.preview === '1';
  return <Article post={post} preview={isPreview} />;
}
⚠️error.tsx 不能捕获自身 layout 的错误
error.tsx 只捕获其**子段**的错误，不捕获同目录 layout.tsx 的错误。

根布局出错需要更上层的兜底（如全局 error.tsx 或监控告警）。

11. 常见坑与最佳实践

🚫把客户端状态传给 Server 组件

Server 组件无法读取浏览器里的 useState/Context 值。需要「客户端交互结果驱动服务端取数」， 用路由参数（searchParams）、Server Action 或把取数下沉到 Client 组件内 fetch。

⚠️'use client' 范围失控

在顶层文件加 `'use client' 会让整个子树变 Client，JS 体积暴涨，丧失 RSC 优势。 原则：让 Client 组件「尽量小、靠叶子」，Server 组件留在上层做数据编排。

⚠️在 Server 组件用浏览器 API
window/localStorage/document 在 Server 组件里不存在（服务端无 DOM）。

这些只能放 'use client' 组件或 useEffect 内。把「环境判断」想清楚再写。

💡性能基线建议

默认 Server 组件；仅叶子交互组件标 'use client'；数据获取尽量上移到 Server 组件直接 await； 慢区块用 Suspense 流式；合理设置 revalidate 而非 no-store 全量禁用缓存。

小结

  • App Router 默认 RSC：Server 组件在服务端运行、不进 bundle，能直接 await 数据/读库。
  • 边界铁律：'use client' 只往下传染；Server 组件可作 Client 的子节点渲染，反之不可。
  • 路由即目录；layout/page/loading/error 各司其职；Suspense 实现流式提升感知性能。
  • 四层缓存（Request/Data/Full Route/Router）决定数据新鲜度，按场景选 no-store/revalidate。
  • Server Action 处理写操作，但必须做鉴权与校验；部署按需求选 Node / Serverless / 静态导出。

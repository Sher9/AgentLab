# 编写 CodeBuddy Skill

上篇讲「怎么用 CodeBuddy 提效」。本篇讲「怎么把重复的用法固化成可复用的 Skill」——相当于给助手装一个专属能力插件。当你发现某类任务反复让助手做（PR 规范检查、生成变更日志、按约定写测试），就该把它写成 Skill，一次定义、处处触发。

<Callout type="note" title="本文定位">
  这是「开发工具」类的实战教程。Skill 的具体字段名与宿主加载机制以官方文档为准，
  API 易变；下文给出的是通用结构与思路骨架，可直接照着改造，但上线前请核对最新规范。
</Callout>

## 1. 为什么需要 Skill

先把「Skill 解决什么」讲透，才知道什么时候该写它：

- **复用**：同一段精心调过的指令，不用每次手敲。定义一次，之后触发词一命中就自动加载。
- **封装领域知识**：把团队约定（命名规范、目录结构、测试套路）写进 Skill，助手按它行事，新人也能产出一致风格。
- **可控的执行边界**：Skill 可以声明「能用哪些工具、不能碰什么」，把能力限制在安全范围内。

它和「存一段提示词到备忘录」的区别：Skill 是**被宿主自动识别、按需注入上下文**的，而不是你手动复制粘贴。

<Callout type="tip" title="Skill ≠ Agent">
  Skill 是「能力包/指令包」，描述的是「这件事该怎么做」；Agent 模式是「按目标自主多步执行」。
  一个 Skill 内部可以指导助手启用 Agent 模式，但 Skill 本身更偏「方法论说明书」。
</Callout>

## 2. SKILL.md 的结构

一个 Skill 通常就是一个 `SKILL.md` 文件（可附带脚本/资源目录）。最小结构分两段：**frontmatter（元数据）** 与 **正文（指令）**。

```markdown
---
name: pr-checklist          # 全局唯一标识，小写中划线，勿与现有 Skill 重名
description: >              # 关键：含触发词，宿主靠它判断是否加载本 Skill
  提交 Pull Request 前跑一遍规范检查：
  检查提交信息格式、是否含测试、是否更新文档。
  当用户说『检查 PR』『pr 规范』『提交前校验』时触发。
---

# PR 规范检查

你是本仓库的 PR 质量守门员。按以下步骤执行……（正文指令）
```

### 2.1 frontmatter：name 与 description

- `name`：小写中划线，作为目录名与唯一键。重名会被覆盖或忽略。
- `description`：**最重要**的字段。宿主用它的语义去匹配用户意图。务必把「什么时候该用这个 Skill」写进描述里——包括同义表述和口语化触发词。

<Callout type="warn" title="description 决定会不会被触发">
  很多 Skill 写了却「从不自动生效」，根因是 description 只写了「它是什么」，没写「何时用」。
  好的 description = 能力说明 + 触发场景 + 同义触发词。这是 Skill 写好的一半。
</Callout>

### 2.2 正文：指令主体

正文就是给助手的「操作手册」，用 Markdown 写。建议包含：角色设定、步骤、约束、产出格式、出口条件。越具体，助手越不会自由发挥。

```markdown
# PR 规范检查

你是本仓库的 PR 质量守门员。

## 步骤
1. 运行 `git diff --stat main...HEAD` 看改了哪些文件。
2. 检查提交信息是否匹配 `type(scope): 简述` 约定。
3. 确认本次改动是否含对应测试（*.test.ts）。
4. 若改动了导出 API，确认文档已更新。

## 约束
- 不自动修改任何文件，只输出检查清单与问题。
- 遇到拿不准的约定，标注『以仓库 CONTRIBUTING.md 为准』并询问。

## 产出格式
- ✅/❌ 逐项列出；最后给一行结论：可提交 / 需修改。
```

### 2.3 让正文更稳健的写法

正文是给助手的 SOP，质量直接决定产出稳定性。几条实战经验：

- **先角色后步骤**：开头一行定角色（「你是本仓库的 PR 守门员」），比裸列步骤更聚焦。
- **把「不要做什么」写死**：助手常在边界处「好心办坏事」。明确 deny 行为（不写文件、不推远程、不编内容），比反复强调「要谨慎」管用。
- **给出口条件**：写清「跑到什么状态算完成、什么情况停下手问人」，避免它无限循环或擅自行动。
- **用清单而非散文**：步骤用有序列表，产出用固定模板。结构化指令比大段描述更易被稳定遵循。

```markdown
## 产出格式（固定模板，助手须严格套用）
- 结论：可提交 / 需修改
- 检查项：
  - [✅/❌] 提交信息格式
  - [✅/❌] 含测试
  - [✅/❌] 文档已更新
- 问题明细：（若无则写「无」）
```

<Callout type="tip" title="把正文当测试资产维护">
  正文写得越像「可执行的测试预期」，Skill 行为越可复现。改动正文后，
  用同一组输入回归一遍产出，确认没退化——和改业务代码要跑测试一个道理。
</Callout>

## 3. 触发词怎么写才准

宿主是把用户语句和 `description` 做语义匹配，所以「多写同义表达」能显著提升命中率。

| 写法 | 效果 |
|------|------|
| 只写「PR 检查」 | 用户说「提交前帮我看看」就不会触发 |
| 写「PR 检查、提交前校验、规范检查、lint 一下」 | 口语化表达也能命中 |

<Callout type="tip" title="把用户原话写进去">
  回顾你平时怎么跟助手说这句话——把这些原话直接列进 description。
  越是用户真实会说的词，匹配越稳。别只写书面语。
</Callout>

## 4. 工具权限：把能力关进笼子

Skill 可以声明「执行时能调哪些工具」。这是安全关键：一个只做检查的 Skill，不该拥有「写文件」或「推代码」的权限。

具体声明方式以官方文档为准，下面给**思路骨架**（YAML 风格伪代码，字段名以官方为准）：

```yaml
# 权限声明思路骨架（伪代码，字段名以官方文档为准）
name: pr-checklist
description: 提交前规范检查……
permissions:
  # 白名单：本 Skill 允许使用的工具
  allow:
    - read_file        # 读改动文件
    - run_command      # 跑 git diff / 测试
  # 黑名单：明确禁止的能力
  deny:
    - write_file       # 不修改任何文件
    - git_push         # 不推送远程
    - network          # 不访问外网
  # 命令级细粒度限制（可选）
  commands:
    allow:
      - "git diff *"
      - "npm test"
    deny:
      - "git push *"
      - "rm -rf *"
```

<Callout type="danger" title="最小权限原则">
  默认不授予任何权限，按需逐个开放。一个「只读检查」的 Skill 若误带了 write_file，
  就可能被诱导去改代码。权限越宽，被 prompt 注入利用的风险越大——宁窄勿宽。
</Callout>

## 5. 完整示例：写一个「变更日志生成」Skill

下面给一个**可直接照抄改造**的完整 Skill。它读取 git 提交，按约定生成 CHANGELOG 片段。

```markdown
---
name: changelog-gen
description: >
  根据 git 提交历史生成变更日志（CHANGELOG）片段。
  当用户说『生成变更日志』『写 changelog』『总结这次改动』『release notes』时触发。
---

# 变更日志生成

你是本仓库的发布秘书。根据最近的 git 提交产出一段 CHANGELOG 片段。

## 步骤
1. 获取范围：`git log --no-merges main..HEAD --pretty=format:"%s"`。
2. 按提交类型分组（feat / fix / chore / docs / refactor）。
3. 把每条提交改写成「面向用户」的一句话，去掉内部黑话。
4. 输出 Markdown 片段，不自动写入文件，等用户确认后再落盘。

## 约束
- 只描述用户可感知的变更；内部重构归入 refactor 且一笔带过。
- 不编造未发生的改动；拿不准的提交原文引用。
- 不修改任何文件，只输出片段。

## 产出格式
### ✨ Features
- 支持按邮箱搜索用户

### 🐛 Fixes
- 修复登录后偶发 401
```

配套的宿主调用示意（伪代码，说明 Skill 如何被加载执行）：

```ts
// 思路骨架：宿主如何根据用户输入选择并注入 Skill（以官方实现为准）
function resolveSkill(userInput: string, skills: Skill[]): Skill | null {
  // 把用户输入和每个 Skill 的 description 做语义匹配
  const match = semanticMatch(userInput, skills.map((s) => s.description));
  // 命中且置信度够高 → 加载该 Skill 的正文注入上下文
  return match.score > 0.7 ? match.skill : null;
}
```

<Callout type="tip" title="先手搓再固化">
  别一上来就写 Skill。先在对话里把「生成变更日志」的指令调顺、验证产出满意，
  再把那段已验证的指令原样搬进 SKILL.md。Skill 只是「把验证过的指令固化」，不是「凭空发明」。
</Callout>

## 6. 调试：本地验证触发与执行

Skill 写完后，最怕「以为写好了，实际从不触发」或「触发了但产出离谱」。调试三板斧：

### 6.1 验证触发

用你写在 description 里的多个同义表达各测一遍，确认都能命中：

```bash
# 伪命令：在宿主的调试/测试模式里触发（具体命令以官方文档为准）
# 输入：「提交前帮我看看」
# 期望：宿主加载 pr-checklist Skill 而不是走通用对话
# 输入：「release notes 来一份」
# 期望：加载 changelog-gen Skill
```

若某句话没触发，回去看 description 是否覆盖了该表述——大概率是缺同义词。

### 6.2 验证产出

触发后检查产出是否符合正文的「步骤 / 约束 / 产出格式」。常见偏差：
- 它「好心」直接写了文件，但你要求只输出 → 正文约束不够强，加上「严禁调用 write_file」。
- 它总结了没发生的改动 → 指令里强调「只基于真实 git 输出，不编造」。

### 6.3 看注入内容

多数宿主提供「本次实际注入了哪些 Skill 正文」的调试视图。用它确认：你的 Skill 正文确实进了上下文、且没有被更通用的 Skill 盖掉。

<Callout type="warn" title="别让 Skill 互相打架">
  两个 Skill 的 description 语义重叠时，宿主可能加载错那个，或都加载导致指令冲突。
  保持每个 Skill 的触发边界清晰、互不重叠，是规模化维护多个 Skill 的关键。
</Callout>

## 7. 发布：注册与分享

Skill 写好后要让团队/宿主能用到。常见路径（具体以官方文档为准）：

- **项目级**：放进仓库的 `.codebuddy/skills/<name>/SKILL.md`，随仓库提交，团队共用。
- **用户级**：放进用户配置目录，跨项目生效（适合个人效率工具）。
- **市场/共享**：打包上传到内部或官方技能市场，按 `skill:` 引用名安装。

```bash
# 目录约定思路（以官方为准）
# .codebuddy/skills/
#   pr-checklist/SKILL.md
#   changelog-gen/SKILL.md
#
# 提交到仓库后，队友拉取即自动获得，无需各自调教
git add .codebuddy/skills
git commit -m "chore: 新增 PR 检查与变更日志 Skill"
```

<Callout type="note" title="把 Skill 当代码管理">
  给它写清 name、description、版本；改动 Skill 走 PR review，
  就像改业务代码一样。别让「AI 指令」游离在版本控制之外，否则行为不可复现。
</Callout>

## 8. 与相近机制的对比

容易混的概念，一张表厘清：

| 机制 | 是什么 | 适合 |
|------|--------|------|
| 提示词（手动） | 你每次复制粘贴的指令 | 一次性、临时任务 |
| Skill | 被宿主自动识别注入的指令包 | 反复出现的同类任务 |
| Agent 模式 | 按目标自主多步执行 | 目标清晰、步骤多的任务 |
| MCP | 给助手接外部工具/数据源的协议 | 需要调用外部系统能力 |
| 钩子（hook） | 在特定事件前后自动跑的脚本 | 强制护栏（如写前 lint） |

<Callout type="tip" title="组合拳最稳">
  实战常组合：用 Skill 定义「怎么做」、用 Agent 模式驱动「自主执行」、
  用 hook 兜底「安全护栏」、用 MCP 接「外部系统」。各管一段，互不替代。
</Callout>

## 9. 踩坑与最佳实践

<Callout type="danger" title="description 不写触发词">
  最常见坑：Skill 写了却从不被自动加载，因为 description 只说「它是什么」。
  补救：把用户真实会说的同义触发词全列进 description。
</Callout>

<Callout type="warn" title="权限给太宽">
  顺手给了 write_file / network，结果被诱导改了文件或外传了代码。
  严格最小权限：只读 Skill 就只开 read + 受限命令。
</Callout>

<Callout type="warn" title="指令含糊导致自由发挥">
  正文只写「生成变更日志」，没说格式、约束、出口，产出每次都不一样。
  正文要像给新人写的 SOP：步骤、约束、产出格式、出口条件都明确。
</Callout>

<Callout type="note" title="Skill 互相重叠">
  多个 Skill 触发边界交叉，宿主加载错或指令打架。
  每个 Skill 守好自己的语义地盘，重叠部分靠更精确的 description 区分。
</Callout>

<Callout type="tip" title="脱离版本控制">
  Skill 不提交仓库，换人或换机就失效、行为不可复现。
  放进 `.codebuddy/skills/` 并提交，把它当一等公民代码管理。
</Callout>

## 10. 适用与不适用场景

**适合写成 Skill：**
- 反复发生的同类任务（PR 检查、生成日志、按约定写测试）；
- 承载团队约定、需要一致产出的流程；
- 风险可控、能声明最小权限的自动化。

**不适合 / 谨慎：**
- 一次性、临时任务——直接对话更高效，别为用 Skill 而用 Skill；
- 需要强自主探索的多步任务——更适合 Agent 模式，Skill 当其中的方法论；
- 涉及高风险操作（删数据、强推）——务必靠 hook + 最小权限兜底，Skill 本身不够。

## 小结

- Skill = 被宿主自动识别注入的「能力/指令包」，核心是 `SKILL.md` 的 frontmatter + 正文。
- `description` 决定触发：必须写清能力 + 触发场景 + 同义触发词，否则写了也不生效。
- 工具权限遵循最小权限原则，白名单逐个开放，高风险能力坚决 deny。
- 流程：对话里先调顺指令 → 固化进 SKILL.md → 用多组同义表达调试触发与产出 → 提交仓库共享。
- Skill 与 Agent / hook / MCP 各管一段，组合使用最稳。

## 发布前自查清单

写完后用这张清单逐项过一遍，能挡掉 90% 的坑：

- [ ] `name` 全局唯一、小写中划线，不与现有 Skill 重名；
- [ ] `description` 写清能力 + 触发场景 + 至少 3 个同义触发词；
- [ ] 正文有角色、步骤、约束、产出格式、出口条件；
- [ ] 权限按最小原则声明，高风险能力在 `deny` 列表；
- [ ] 用多组同义输入测过触发、用真实任务测过产出；
- [ ] 已提交进仓库 `.codebuddy/skills/<name>/`，走 PR review。

<Callout type="note" title="下一步">
  Skill 让助手「会做某类事」。当你需要让助手「调用外部系统能力」（数据库、内部 API），
  就该了解 MCP 协议——详见工具开发分类下的《MCP 协议与开发》。
</Callout>

原生 vs 框架：何时手写，何时用框架

剖析「裸用 LLM SDK 自己写循环」与「用 CrewAI/LangGraph 等框架」两路在控制流、抽象成本、可维护性上的真实权衡，给出可操作的决策框架与对照骨架。

#框架#原生#抽象成本#可维护性#选型

原生 vs 框架：何时手写，何时用框架

M1 里我们用几十行代码就跑通了工具调用闭环，M3 对比过主流框架选型。但一个总被问到的问题是：「我到底要不要上框架？」

很多团队一上来就 pip install langchain，半年后又花大力气把关键链路改回原生。这一篇不站队，只把两条路的真实成本收益摆清楚，给你一份能落地的决策框架。

1. 两条路的定义

  • 原生路线：直接用 LLM 厂商 SDK（如 OpenAI Node/Python SDK）+ 自己写的循环与状态管理，不引入 Agent 框架。M1 的工具闭环就是典型原生实现。
  • 框架路线：用 CrewAI / LangGraph / AutoGen / LlamaIndex 等，把编排、记忆、工具、多 Agent 通信等封装成组件。

两者底层都还是「模型 + 工具 + 循环」，区别只在控制流归谁管、复用层多厚。

📌框架不是能力增强，是工程封装

框架不会让模型变聪明，只是把「你已经会手写的循环/状态/路由」提前写好、参数化。 所以选型的本质问题是：这部分工程，你自己写值不值？

2. 原生路线的成本与收益

2.1 收益

  • 完全可控：每一步的输入输出、重试、降级你都看得见、改得动；
  • 零抽象泄漏：没有「框架行为和你预期不一致却查不到原因」的痛苦；
  • 依赖最小：少一层包，升级/迁移/审计成本最低；
  • 调试直白：报错栈就是你的代码，不怕「框架内部吞了异常」。

2.2 成本

  • 重复造轮子：记忆、重试、并行、路由、Human-in-loop……每个都要自己写；
  • 易写错控制流：循环上限、超时、并发这些 M1 强调的红线，框架常已内置，原生要自己兜底；
  • 团队协作口径碎：十个人手写十种循环风格，后期难维护。
💡原型期优先原生

验证想法的阶段，先用原生把链路跑通。你能最快理解「Agent 到底在干嘛」， 也避免还没想清需求就被框架的抽象绑架。等模式稳定了再决定是否上框架。

3. 框架路线的成本与收益

3.1 收益

  • 开箱即用的编排：Sequential/Hierarchical 流程、状态图、检查点一句话配好；
  • 生态组件：Retriever、Memory、Tool 适配器、可观测性集成现成可接；
  • 团队一致性：统一抽象，新人按文档就能接手；
  • 先进模式低成本复用：Human-in-loop、持久化检查点这类难写的设施框架已给。

3.2 成本（抽象成本）

  • 学习曲线：要懂框架的抽象模型（图？Crew？会话？），错了难定位；
  • 抽象泄漏：真实需求稍微超出框架预设，就要「对抗框架」或 hack；
  • 版本与锁定：框架 API 迭代快，升级常 breaking；深度绑定后迁移贵；
  • 黑盒调试：中间状态被框架接管，verbose 日志外的可观测性要额外接。
⚠️抽象成本会反噬

当你的需求有 30% 落在框架预设之外，维护「绕开框架」的代码往往比 「当初直接原生写」更累。框架省钱的前提是：你的用法契合它的预设。

4. 决策框架：什么时候选哪条

一张对照表先建立直觉：

信号 倾向原生 倾向框架
链路是否固定、可控 固定且要精细控制 动态、角色多、需快速试
团队是否有框架经验 有经验、偏底层 想快速出原型
是否需 Human-in-loop/可回放 自己写得起 框架现成（如 LangGraph）
需求是否超框架预设 超出越多越要原生 高度契合预设才上
长期维护/审计要求 高合规、要可控 能接受框架依赖

4.1 决策伪代码

# decide.py —— 选型决策思路骨架（伪代码，按团队实际打分）
def should_use_framework(need):
    # ① 需求是否高度契合某框架的预设抽象？
    fit = estimate_framework_fit(need)        # high / medium / low
    if fit == "low":
        return "原生"                          # 框架帮不上，反而添乱

    # ② 是否要精细控制每一步、强可观测、强合规？
    if need.require_fine_control or need.audit_strict:
        return "原生" if can_afford(need) else "框架+自写关键节点"

    # ③ 是否快速验证、角色多、流程动态？
    if need.rapid_prototype and need.many_roles:
        return "框架"                          # 用 CrewAI/LangGraph 提速

    # ④ 默认：原型用框架，稳定后把关键链路迁回原生
    return "框架起步，核心链路原生化"
📌常见中间态：混用

实际生产里最稳的是「混合」：编排/多 Agent 用框架，核心工具执行与 关键控制流用原生。既借框架提速，又不把命门交给黑盒。

5. 同一任务的两种实现对照（思路骨架）

下面用「带重试的工具 Agent」演示两路差异。API 仅示意，以官方为准。

# 原生思路骨架：循环/重试/降级全在自己手里
def run_native(user_input, tools, max_steps=5):
    messages = [{"role": "user", "content": user_input}]
    for _ in range(max_steps):                  # 上限自己管，红线不漏
        msg = llm(messages, tools=tools)
        if not msg.tool_calls:
            return msg.content
        for call in msg.tool_calls:
            result = execute_with_retry(call)    # 重试/降级自己写（见 M1）
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    return "步数耗尽"

# 框架思路骨架：把循环交给框架，你只声明角色与工具
# researcher = Agent(role=..., tools=[...]); task = Task(...)
# crew = Crew(agents=[researcher], tasks=[task], process=Process.sequential)
# crew.kickoff(inputs={"topic": user_input})
# 注意：步数上限、重试策略由框架配置项决定，需另行显式设置，否则易失控
💡对照着读就懂了

原生版每一行都是你的；框架版把『循环 + 消息回填』收进了 Crew。 框架省的是『写循环』，你让渡的是『看清循环』。选型就是权衡这笔账。

6. 踩坑

🚫没想清就上框架

需求还没稳定就引入重框架，后期「对抗框架」的改造量常大于『当初原生写』。 先原生验证，再决定上不上、上哪个。

⚠️被框架锁定

深度使用某框架专有抽象（自定义 State、Callback）后，迁移成本极高。 关键链路尽量用框架的「薄封装」而非「深定制」，给未来留退路。

⚠️以为框架替你管了红线

循环上限、超时、工具护栏这些 M1 红线，框架不一定默认兜底（尤其层级流程）。 上框架后仍需显式配置步数上限与工具权限，别想当然。

💡先量再定

拿真实任务跑一遍：原生写要几行、框架写要几行、调试各花多久。 用你们团队的数据说话，比任何选型文章都准。

小结

  • 原生 = 完全可控、依赖最小、调试直白，但要自己写编排与红线兜底。
  • 框架 = 编排/生态/一致性开箱即用，代价是抽象成本、版本锁定与黑盒调试。
  • 决策核心：需求是否契合框架预设？是否要精细控制/强合规？是否快速试错？
  • 最稳是混合：框架提速、核心链路原生化；且任何框架都要显式配步数上限与护栏。

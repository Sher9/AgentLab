线上实验：用 A/B 与灰度验证真实收益

离线评测（见 eval-dataset / eval-prompt-opt）只能告诉你『在样本集上变好了』。但真实用户分布、长尾问题、业务指标（留存、转化、满意度）才是最终裁判。这一篇讲如何把改动放到线上做对照实验，用数据而非直觉拍板。

1. 离线评测与线上实验的分工

阶段 回答的问题 工具
离线评测 这个改动在已知样本上是否变好 评测集 + judge
线上实验 真实用户下是否真的更好、有没有副作用 A/B / 灰度

离线评测快、便宜、可重复，是『守门员』；线上实验慢、贵、有风险，是『终审』。两者不可互相替代。

📌能离线解决的别上线上

凡是评测集能覆盖的差异，优先离线解决，别为了『感受一下』就开线上实验。 线上实验要占用流量、增加复杂度、还有伤用户的风险，只留给真正需要真实分布的问题。

2. 指标设计：先定 North Star

实验前必须明确主指标（North Star）与护栏指标（Guardrail）：

  • 主指标：你想提升的，如『任务一次解决率』『答案满意度评分』；
  • 护栏指标：绝对不能恶化的，如『响应延迟』『成本/次』『报错率』。

护栏指标用于『拦截』：主指标涨了但护栏跌了，实验判负。这是防止『拆东墙补西墙』的关键。

💡护栏指标常比主指标更重要

很多实验主指标微涨、成本却翻倍——这种『赢』毫无意义。护栏指标（延迟/成本/报错） 往往决定一个改动能否上线。把护栏写进实验结论的硬性门槛。

3. 分流与灰度：控制爆炸半径

线上实验的核心是把流量分成互斥组，只让实验组用新版本：

// ab-split.ts —— 按用户 ID 稳定分流（可运行骨架）
// 关键：同一用户每次都落同一组（哈希稳定），否则体验会反复横跳
function assignBucket(userId: string, experiment: string): 'control' | 'treatment' {
  // 把 userId + 实验名拼成种子再做哈希，保证同用户稳定、不同实验独立
  const seed = `${experiment}:${userId}`;
  let h = 0;
  for (let i = 0; i < seed.length; i++) {
    h = (h * 31 + seed.charCodeAt(i)) >>> 0;
  }
  // 取模到 100 → 0~49 进 control，50~99 进 treatment（各 50%）
  return h % 100 < 50 ? 'control' : 'treatment';
}

// 用法：请求进来时决定用哪个 Prompt 版本
function pickPrompt(userId: string): string {
  const bucket = assignBucket(userId, 'prompt-v2');
  return bucket === 'treatment' ? PROMPT_V2 : PROMPT_V1;
}

灰度发布则是逐步放大实验组比例（1% → 10% → 50% → 100%），随时可一键回滚，把事故影响限制在最小范围。

⚠️分流必须稳定且互斥

同一用户每次请求必须落同一组，否则他这会儿看到新版、下会儿看到旧版， 体验割裂还会污染日志。用『用户 ID 哈希』而非随机，保证稳定； 同一请求不要同时进多组，保证互斥。

4. 统计显著性：别被噪声骗了

样本不够时，1% 的差异可能纯属随机。判断实验是否有效要看：

  • 样本量：实验前用预期效应大小算所需样本（可用在线样本量计算器）；
  • 显著性水平（p 值）：通常 p < 0.05 才算『有把握不是噪声』；
  • 置信区间：给出效应范围，而非单点估计。
🚫盯着数据直到显著是作弊

反复看数据、一出现显著就停实验（peeking），会人为抬高假阳性率。 要么预先定好实验时长/样本量到期再读，要么用序贯检验修正。 『多看几次总能显著』是真实存在的统计陷阱。

5. 灰度发布流程

① 1% 流量开实验组，盯护栏指标（延迟/成本/报错）有无异常
② 护栏稳 → 放量到 10%、50%，持续观察主指标趋势
③ 到期读数：主指标显著提升且护栏未恶化 → 全量；否则回滚
④ 全量后保留旧版本可回滚，直到确认无问题再清理
💡先小流量验证护栏

灰度的第一目标不是看主指标，而是确认『没把系统搞挂』。1% 阶段重点盯延迟和报错率， 护栏一旦报警立刻回滚，比主指标涨 2% 重要得多。

6. 线上实验 vs 离线评测对比

对比项 离线评测 线上 A/B
数据 固定样本集 真实全量分布
速度 分钟级 天/周级
成本 低 高（占用流量）
指标 通过率/评分 业务指标/护栏
风险 几乎无 有（伤部分用户）
📌两者是上下游不是二选一

标准流程：离线评测先证明『不差且可能更好』，再开小流量线上实验验证真实收益。 跳过离线直接上线实验，既浪费流量又延长了『带病版本』的暴露时间。

7. 常见坑

⚠️样本不足就下结论

跑了一百个用户就宣布『新版更好』，差异大概率在噪声范围内。 先算所需样本量，到期再读，不要提前看一眼就拍板。

🚫只盯主指标忽略护栏

主指标 +2% 但成本 +50%、延迟翻倍——这种实验该判负。护栏指标是上线硬门槛。

⚠️分流不稳定导致体验割裂

见第 3 节：随机而非哈希分流，会让同一用户在新旧版间反复横跳，日志脏、体验差。

🚫peeking 作弊

见第 4 节：频繁偷看数据直到显著，假阳性率飙升。预设周期，到期再读。

⚠️实验组与对照组不同步变更

实验期间若对照组也被别人改了 Prompt，两组的差异就不再是你要测的变量。 实验期内冻结对照组的无关改动，保证单一变量。

小结

  • 离线评测守门、线上实验终审；能离线解决的别占用线上流量。
  • 先定主指标 + 护栏指标；护栏（延迟/成本/报错）是上线硬门槛。
  • 分流用『用户 ID 哈希』保证稳定互斥；灰度从小流量起步、可一键回滚。
  • 看显著性要防 peeking，预设样本量/周期到期再读；实验期内冻结对照组改动。
  • 红线：护栏不可恶化、分流要稳定、样本要够、不偷看、单一变量。

# 主流模型选型：能力矩阵与决策树

做 AI 应用最常被问的第一个问题不是『怎么写 prompt』，而是『用哪个模型』。答案不是『越大越好』，而是**在你的约束（成本、延迟、合规、数据驻留）下，选能力刚好够、且能扛住流量的那一个**。

这一篇把当下主流模型按『闭源旗舰 / 开源可自部署 / 国产模型』三条线铺开，给出能力矩阵、成本与部署形态对比，再用一份可运行横评骨架帮你用数据说话，最后落到一棵选型决策树。重实战，不堆参数表。

## 1. 模型的几个真正影响选型的维度

别只看『榜单分数』。真正决定一个模型能不能进你生产系统的，是下面这几个工程维度：

- **能力天花板**：复杂推理、代码、长文写作、多轮指令遵循——这是旗舰闭源模型的护城河。
- **上下文窗口**：单次能吞多少 token。长文档、长对话、RAG 回填都卡在这。
- **延迟与吞吐**：首 token 延迟（TTFT）和每秒 token 数（TPS）。实时对话和批量处理要的模型不一样。
- **单价**：每千输入/输出 token 的价格。量起来后这是主要成本。
- **部署形态**：托管 API、可私有化自部署、还是只能云端。合规和数据驻留全看它。
- **工具/多模态能力**：是否原生支持 function calling、视觉、JSON 模式。

<Callout type="note" title="榜单分数不能当选型依据">
  公开榜单（如各类 Arena）测的是『平均人类偏好』，和你业务的『特定任务通过率』是两回事。
  真正的选型要靠你自己的任务集做横评——第 5 节的骨架就是干这个的。把榜单当『初筛』，别当『终审』。
</Callout>

## 2. 主流模型全景

下面按三条线快速过一遍，重点说『它适合什么、不适合什么』，而不是罗列参数。

### 2.1 闭源旗舰（托管 API 为主）

- **OpenAI GPT 系列**：生态最成熟，工具调用、JSON 模式、embedding、微调全线齐备。强在『什么都够用、社区方案最多』；弱在数据和推理发生在厂商云端，且价格随用量线性上升。
- **Anthropic Claude 系列**：长上下文（数十万 token 级）和长文写作/代码能力突出，『指令遵循』稳健，适合文档密集型、Agent 长任务。弱在生态工具相对少、部分区域访问受限。
- **Google Gemini 系列**：多模态原生（图文音视频）、超长上下文、与 Google 生态集成好。强在多模态和长窗口；弱在第三方工具链成熟度参差。

### 2.2 开源可自部署

- **Meta Llama 系列**：开源权重标杆，社区生态最大，可私有化、可微调、可量化。强在『数据不出门、可深度定制』；弱在同等参数下绝对能力一般低于旗舰闭源，且需要你自建推理栈（vLLM/TGI）。
- **Mistral / Mixtral**：小模型性价比高，MoE 架构在『小参数大模型』路线上有特色，适合边缘和成本敏感场景。
- **其他开源系**：Qwen、DeepSeek、GLM 等同时提供开源权重，下面单列。

### 2.3 国产模型（含开源与托管）

- **通义千问 Qwen（阿里）**：中英双语强，开源权重齐全（0.5B~72B+），工具调用和长上下文版本都有，国内合规与访问便利突出。
- **文心一言 ERNIE（百度）**：中文理解与中文知识问答强，国内政企合规场景常用，托管 API 为主。
- **智谱 GLM（清华/智谱）**：中英均衡，开源 ChatGLM/GLM 系列与托管 API 并存，长上下文与 Agent 能力在国产里靠前。
- **DeepSeek（深度求索）**：推理模型（R1 系列）在数学/代码推理上表现亮眼，且价格极低，开源权重可自部署。

<Callout type="tip" title="国产模型的两个隐藏优势">
  一是『数据驻留国内』满足合规；二是『中文互联网语料』更贴地气（成语、梗、本地业务术语）。
  如果你的用户主要是中文、且业务数据敏感，别一上来就默认闭源——先把 Qwen/GLM/DeepSeek 跑一遍横评。
</Callout>

## 4. 部署形态与成本结构

| 形态 | 代表 | 优点 | 代价 / 风险 |
|------|------|------|-------------|
| 托管 API | GPT/Claude/Gemini/文心 | 零运维、即开即用、弹性扩容 | 数据出域、按量计费、有速率限制 |
| 开源自部署 | Llama/Qwen/GLM/DeepSeek | 数据不出门、可微调、单价可控 | 需 GPU、需推理栈、需运维 |
| 开源 + 托管推理 | 云厂商的 Qwen/DeepSeek 端点 | 免运维又合规、价格低 | 仍依赖厂商可用性 |

成本的关键不在『单价』，而在**总量 = 单价 × token 数 × 调用次数**。一个常见误区是『选了便宜的小模型』，却因为要反复重试、长 prompt、多轮工具调用，总量反而更高。第 5 节的横评会同时统计『成功率』和『平均花费』，二者相除才公平。

<Callout type="note" title="成本要看单位任务而非单位 token">
  大模型的『性价比』= 单任务成功率 / 单任务成本。一个贵 3 倍但一次过、不重试的模型，
  往往比便宜但反复失败重试的模型更省。横评时务必把『重试次数』算进成本。
</Callout>

## 5. 可运行骨架：模型横评

别拍脑袋选。用同一批任务，对候选模型跑一遍，统计『成功率 / 平均 token / 平均延迟 / 成本』。下面是用 OpenAI Node SDK 统一打多家（OpenAI、以及 OpenAI 兼容端点）的横评骨架——许多国产/开源模型提供 OpenAI 兼容接口，只需换 `baseURL` 和 `apiKey`。

```ts
// model-bench.ts —— 多模型横评骨架（OpenAI 兼容端点）
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';

// 候选模型：同一套 SDK，只是换 baseURL / model 名
// 说明：国产/开源模型多数提供 OpenAI 兼容端点，改 baseURL 即可复用本骨架
const candidates = [
  { name: 'gpt-4o-mini',        baseURL: undefined,                apiKey: process.env.OPENAI_API_KEY! },
  { name: 'qwen-plus',          baseURL: 'https://dashscope.aliyuncs.com/compatible-mode/v1', apiKey: process.env.DASHSCOPE_API_KEY! },
  { name: 'glm-4-flash',        baseURL: 'https://open.bigmodel.cn/api/paas/v4',              apiKey: process.env.ZHIPU_API_KEY! },
  // 开源自部署：把 baseURL 指向你的 vLLM/TGI 暴露的 /v1 即可
  { name: 'local-llama-3-8b',   baseURL: 'http://localhost:8000/v1', apiKey: 'not-needed' },
];

// 评测任务：真实业务里应是你的黄金集（几十到几百条）
const tasks = [
  '把下面这段话改写成正式邮件：哥们周五前把报告发我',
  '用 Python 写一个快速排序，并解释时间复杂度',
  '提取这段用户反馈里的情绪和核心诉求：APP 又闪退了，气死',
];

// 用 Zod 约束『模型输出必须可解析』——任何模型凡输出不合规都算失败
const AnswerSchema = z.object({
  ok: z.boolean(),
  text: z.string().min(1),
});

async function evalModel(c: (typeof candidates)[number], task: string) {
  const client = new OpenAI({ baseURL: c.baseURL, apiKey: c.apiKey });
  const t0 = Date.now();
  const res = await client.chat.completions.create({
    model: c.name,
    messages: [{ role: 'user', content: task }],
    temperature: 0, // 横评用 0，减少随机性干扰，结果可复现
  });
  const cost = (Date.now() - t0) / 1000;
  const raw = res.choices[0].message.content ?? '';
  // 校验输出是否合规（这里简化：要求非空；真实应解析你的业务 schema）
  const parsed = AnswerSchema.safeParse({ ok: raw.length > 0, text: raw });
  return { model: c.name, success: parsed.success, text: raw, seconds: cost };
}

// 跑全矩阵，汇总成功率与耗时
async function main() {
  for (const c of candidates) {
    let ok = 0;
    for (const task of tasks) {
      const r = await evalModel(c, task);
      if (r.success) ok++;
      // 关键：同时记录成功与否 + 耗时，后续可换算成『单位任务成本』
      console.log(`[${c.name}] 任务=${task.slice(0, 12)}… 成功=${r.success} 耗时=${r.seconds}s`);
    }
    console.log(`>>> ${c.name} 成功率 = ${ok}/${tasks.length}`);
  }
}

main();
```

运行：`npm i openai dotenv zod` 然后 `npx tsx model-bench.ts`。把 `tasks` 换成你业务的真实黄金集，统计结果就是你的选型依据。

<Callout type="tip" title="横评要固定温度与 prompt">
  对比必须控制变量：所有候选用相同 system prompt、相同 temperature（建议 0）、
  相同任务集。否则『A 比 B 好』可能只是你的 prompt 更贴 A 的训练分布，结论不可迁移。
</Callout>

## 6. 选型决策树

把上面的维度压成一棵可执行的决策树：

```
开始
 ├─ 数据是否必须不出域 / 强合规？
 │     ├─ 是 → 选可自部署开源（Qwen/GLM/Llama）或国内合规托管（文心/通义/智谱）
 │     └─ 否 → 继续
 ├─ 任务是否长文档 / 超长对话（>100k token）？
 │     ├─ 是 → 优先 Claude / Gemini（长窗口），或自部署带长上下文的 Qwen/GLM
 │     └─ 否 → 继续
 ├─ 是否重度依赖工具调用 / Agent 长任务？
 │     ├─ 是 → 优先 GPT / Claude / 通义 / 智谱（function calling 成熟）
 │     └─ 否 → 继续
 ├─ 成本是否极度敏感（海量调用）？
 │     ├─ 是 → 小模型（mini 级 / DeepSeek / Qwen 小参）或自部署
 │     └─ 否 → 旗舰闭源（GPT-4o 级 / Claude）保上限
 └─ 是否需要多模态（图/音/视频）？
       ├─ 是 → Gemini / GPT-4o / Claude（视觉）
       └─ 否 → 任意文本模型，按上面结论收口
```

<Callout type="note" title="决策树输出的是候选集不是唯一解">
  决策树给你『2~3 个候选』，不是『唯一答案』。最后一步永远是用第 5 节横评在真实任务上二选一。
  工程选型是『约束求解』，不是『追最高分』。
</Callout>

## 7. 推理模型：何时该为『思考』花钱

近年出现的『推理模型』（如 OpenAI o 系列、DeepSeek R1、Claude 思考模式）在回答前会先产出一段**内部推理链（CoT）**，再给最终答案。它对数学、代码、复杂规划类任务提升明显，但有三个代价必须算进选型：

- **延迟高**：先把推理链生成完才出答案，首字延迟可能是普通模型的数倍到数十倍；
- **成本高**：推理链本身也计费（token 多），单条成本是普通模型的几倍；
- **不可控**：推理过程不可直接编辑，长推理链也可能自我跑偏。

| 场景 | 建议 |
|------|------|
| 数学证明、算法题、复杂多步规划 | 上推理模型，质量提升值得延迟/成本 |
| 闲聊、摘要、抽取、简单分类 | 普通模型即可，推理模型纯属浪费 |
| 实时对话（要求低延迟） | 默认普通模型，必要时异步用推理模型复核 |

<Callout type="tip" title="推理链也要算进预算">
  推理模型的『思考 token』计入上下文和费用。给上下文预算时要为它留足空间，
  否则推理链写到一半被截断，答案质量骤降。把它当成『高消费高产出』的一档来规划。
</Callout>

<Callout type="warn" title="别对所有请求默认开推理">
  把推理模型当默认，等于给每条闲聊都付了『深度思考』的钱。实务做法：
  用一个小模型先做『复杂度路由』——简单的走普通模型，复杂的才升级推理模型（见下一节）。
</Callout>

## 8. 模型路由、版本管理与灰度

生产系统很少『永远只用一个模型』。三件事决定长期可维护性：

### 8.1 模型分级路由

按任务复杂度把流量分到不同档位，既保质量又控成本：

```
请求 → 轻量分类/路由模型判复杂度
        ├─ 简单（闲聊/抽取）→ 小模型（mini 级 / DeepSeek / Qwen 小参）
        ├─ 中等（写作/代码）→ 标准大模型（GPT-4o 级 / 通义 / 智谱）
        └─ 困难（推理/规划）→ 推理模型（o 系列 / R1）
```

实现上只需一个『ModelClient 接口』+ 配置表，路由逻辑与业务解耦。流量结构合理时，整体成本可降一半以上。

### 8.2 供应商版本管理

厂商会发新版本、弃用旧版本、改价。把『模型名』当**外部依赖**来管理：

- 用配置中心存『当前生效模型名』，别硬编码在业务里；
- 升级前用黄金集跑回归，确认通过率不降再切流；
- 保留旧版本别名，出问题一键回滚。

### 8.3 灰度与 A/B

新模型上线先放 5%~10% 流量，监控『任务通过率 / 成本 / 延迟 / 用户满意度』，达标再全量。绝不在没灰度的情况下全量替换——一次『模型答得不对』的集体故障，比两周灰度验证贵得多。

<Callout type="note" title="模型是可替换的依赖">
  把模型当『可热插拔的底层依赖』而非『写死的能力』。统一接口 + 配置化 + 灰度，
  让你能在不改动业务代码的前提下换供应商、升版本、做 A/B——这是选型落地的最后一公里。
</Callout>

## 9. 对比：闭源 vs 开源自部署

| 对比项 | 闭源托管 API | 开源自部署 |
|--------|--------------|------------|
| 上线速度 | 分钟级 | 天级（搭推理栈、调优） |
| 数据驻留 | 出域 | 全本地 |
| 峰值能力 | 高（旗舰） | 中（同参下略低） |
| 边际成本 | 随量线性涨 | 固定算力 + 运维人力 |
| 可微调/定制 | 有限（厂商微调） | 完全可控（LoRA/全参） |
| 适用 | 快速验证、弹性流量 | 合规、量大、需定制 |

<Callout type="warn" title="自部署的隐藏成本">
  自部署不是『下载权重就完事』：GPU 采购/租赁、vLLM 调优、KV Cache 显存、批量与限流、
  版本升级、监控——这些都是人力。量不够大时，自部署的『单价低』会被运维成本吃掉。
  先算 TCO（总拥有成本）再决定。
</Callout>

## 10. 常见选型坑

<Callout type="danger" title="只看榜单分数就拍板">
  榜单是『大众偏好均值』，不等于你的任务通过率。务必用业务黄金集横评，
  否则上线后『模型答得不对』会反复返工，比前期多花两天横评贵得多。
</Callout>

<Callout type="warn" title="小模型硬扛旗舰任务">
  为了省钱用极小模型做复杂推理/长文档，结果靠『提示补救 + 重试』凑及格，
  单任务实际成本反而更高、延迟更差。能力不够就上大模型，钱花在刀刃上。
</Callout>

<Callout type="warn" title="忽略上下文窗口导致悄悄截断">
  长文档塞进小窗口模型会被截断，模型『假装读懂』却漏掉关键信息，产生幻觉。
  选模型前先量你的输入分布峰值 token 数，留足余量（含 system + 历史 + 输出）。
</Callout>

<Callout type="warn" title="把供应商锁定当免费">
  只接一家闭源 API，一旦涨价/限流/区域不可用就无退路。至少保留一个 OpenAI 兼容的
  备选（开源自部署或国产托管），用统一 SDK 抽象，切换只需换 baseURL。
</Callout>

<Callout type="tip" title="用适配层隔离供应商">
  业务代码只依赖一个『ModelClient 接口』，背后按配置路由到不同 baseURL。
  这样选型变更、A/B、灰度都不用改业务代码——把『模型可替换』做成架构默认能力。
</Callout>

## 11. 能力边界与误用红线

选型还要清楚『模型不擅长什么』，避免把不合适的任务硬塞给 LLM：

- **精确计算/强一致性**：大模型做加减乘除、库存扣减、金额对账不可靠，这类交给确定性程序，模型只做『自然语言接口』。
- **实时事实**：训练截止后的事模型不知道，必须接工具/检索，不能让它『凭记忆编』。
- **高风险自主决策**：医疗诊断、法律裁判、资金划拨等需兜底与人工确认，模型只能辅助。
- **长程状态机**：需要严格多步状态一致性的流程，纯靠 prompt 维护状态易错，应落到代码/数据库。

<Callout type="danger" title="别让模型做确定性系统该做的事">
  把『该用数据库事务保证的扣库存』交给模型『猜』，是生产事故高发区。
  正确分工：模型负责理解意图与生成，代码负责执行与一致性校验。能力边界即系统边界。
</Callout>

## 12. 选型落地清单

把前面内容压成一张可勾选的清单，新项目选型时逐条过：

- [ ] 是否先量了任务输入/输出的 token 分布峰值（定窗口与预算）？
- [ ] 是否用业务黄金集跑了横评（固定温度/prompt，统计成功率+成本）？
- [ ] 是否按『合规→长上下文→工具→成本→多模态』顺序收敛出 2~3 个候选？
- [ ] 是否用统一 ModelClient 接口隔离供应商，保留热替换能力？
- [ ] 是否规划了小模型路由，避免给简单请求开推理/旗舰模型？
- [ ] 是否对模型版本做了配置化 + 灰度 + 回滚预案？

<Callout type="tip" title="清单比分数更可靠">
  选型不是『选最高分』，而是『在约束下最小后悔』。这张清单的每一项都是在堵一个常见坑：
  漏一项，上线后就可能变成一次返工或一次故障。把它当成发布前必须过的门禁。
</Callout>

## 13. 常见术语速记

- **TTFT（Time To First Token）**：首 token 延迟，主要卡在 prefill 阶段，长 prompt 越慢。
- **TPS（Tokens Per Second）**：生成速度，受 KV Cache 带宽与批量影响。
- **MoE（Mixture of Experts）**：混合专家，仅激活部分参数，用小算力换大模型能力。
- **上下文窗口**：单次能处理的 token 上限，含 system+历史+输入+输出预留。
- **推理模型**：生成前先产出内部思维链，强于复杂任务，但更慢更贵。
- **OpenAI 兼容端点**：多数国产/开源模型提供与 OpenAI API 同构的接口，换 baseURL 即可复用代码。

<Callout type="tip" title="术语是沟通基线">
  和同事、供应商、文档对齐这些词，能省掉一半『你说的是不是我以为的』的返工。
  尤其 TTFT/TPS 和『上下文窗口含输出』这两点，最容易被新产品经理念错。
</Callout>

## 小结

- 选型看六个工程维度：能力、上下文、延迟、单价、部署形态、工具/多模态，而非单看榜单。
- 三条线：闭源旗舰（生态/上限）、开源自部署（合规/可定制）、国产（合规+中文贴地）。
- 能力矩阵只作初筛；最终结论来自你业务黄金集上的横评（固定温度与 prompt，统计成功率+成本）。
- 决策树输出候选集，横评做收口；闭源自部署各有成本结构，先算 TCO。
- 红线：别信榜单当终审、别小模型硬扛、别忽略窗口截断、别单供应商锁定——用适配层保灵活。

<Callout type="note" title="下一步">
  模型选定后，真正影响效果的是『它怎么理解你的输入』——即分词与 token 计费，
  见 **分词器**；要理解生成质量的底层，再去读 **Transformer 原理**。
</Callout>

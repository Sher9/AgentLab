# 微调实战：SFT 与 LoRA 从数据到上线

预训练（见 llm-pretrain）造出『续写机器』基座；**微调（Fine-tuning）** 才是把它变成『听话、懂业务』的助手的关键一步。这一篇面向已经会调 API 的开发者，直接给你：决策依据、数据怎么造、四种方案怎么选、可运行骨架、怎么评估、要花多少钱。

<Callout type="note" title="本篇两条主线">
  ① **托管微调**：用 OpenAI 等厂商的 fine-tuning API，Node SDK + Zod 校验数据，开箱即用；
  ② **自训微调**：LoRA / QLoRA / PEFT，用开源模型本地训练（以官方文档为准的伪代码骨架）。
  两者目标一致——让模型适配你的任务，成本和可控性不同。
</Callout>

## 1. 先决策：到底要不要微调

微调不是银弹。先和更便宜的方案比一比：

| 方案 | 成本 | 可控性 | 适合 |
|------|------|--------|------|
| 提示工程 / Few-shot | 零训练成本 | 低（受上下文限制） | 简单、变化快的 task |
| RAG（检索增强） | 零训练，仅推理 | 中 | 需『私有知识』且要可溯源 |
| **SFT 微调** | 中 | 高 | 固定格式/语气/稳定能力，如客服话术 |
| **LoRA/QLoRA** | 中低 | 高 | 单卡也能训大模型，领域适配 |
| 全参数微调 | 高 | 最高 | 你有充足数据和算力，要深度改造 |

<Callout type="tip" title="默认路径">
  先上『提示工程 + RAG』验证价值；若模型在固定格式/稳定风格上仍不达标，再上 SFT；
  若要在自有算力上训大模型，选 LoRA/QLoRA。不要一上来就全参微调——多数场景它性价比最差。
</Callout>

## 2. SFT 数据：微调的命门

监督微调（Supervised Fine-Tuning, SFT）喂的是**『输入 → 期望输出』配对**。数据质量远比数量重要——几百条精心标注，常胜过几万条噪声。

### 2.1 数据格式

OpenAI 风格的 SFT 文件是 JSONL，每行一条多轮对话：

```json
{"messages": [
  {"role": "system", "content": "你是严谨的运维助手"},
  {"role": "user", "content": "磁盘满了怎么查？"},
  {"role": "assistant", "content": "用 df -h 看挂载点用量，再用 du -sh * 定位大目录。"}
]}
```

<Callout type="warn" title="数据分布决定模型行为">
  模型会『忠实复刻』你的训练分布。如果你的 SFT 全是正例、没有『拒答/澄清』样本，
  上线后模型会对一切问题强行作答（幻觉式自信）。务必混入拒答、反问、降级样本。
</Callout>

### 2.2 用 Zod 校验训练数据

在提交给微调 API 前，用 Zod 守住格式关——坏样本会在跑了几小时后才暴露：

```ts
// validate_sft.ts —— SFT 数据校验（沿用 OpenAI SDK 项目的 Zod 习惯）
import { z } from 'zod';

// 单条消息：角色 + 内容
const Message = z.object({
  role: z.enum(['system', 'user', 'assistant']),
  content: z.string().min(1, '内容不能为空'),
});

// 一条 SFT 样本：messages 数组，且必须以 assistant 回复收尾
const SftSample = z.object({
  messages: z.array(Message).min(2).refine(
    (ms) => ms[ms.length - 1].role === 'assistant',
    { message: '最后一条必须是 assistant 消息' }
  ),
});

// 逐行校验 JSONL，非法行写回 bad.jsonl 供人工修
function validate(jsonlPath: string) {
  // 读文件、split('\n')、逐行 safeParse —— 真实实现见 fs/promises
  // 伪代码：for (const line of lines) { const r = SftSample.safeParse(JSON.parse(line)); ... }
}
```

<Callout type="note" title="单一事实来源">
  若你同时用 Zod 做『线上入参校验』和『训练数据校验』，尽量复用同一 schema 描述，
  避免『训练分布』和『线上分布』漂移——这是很多模型上线后行为不符预期的隐蔽来源。
</Callout>

## 3. 方案对比：全参 / LoRA / QLoRA / PEFT

| 方案 | 改哪些参数 | 显存 | 适配强度 | 适合 |
|------|-----------|------|---------|------|
| 全参数微调 | 全部权重 | 极高（模型×多倍） | 最强 | 数据充足、要深度改造 |
| **LoRA** | 仅低秩 adapters | 中 | 强 | 单/多卡训大模型，可逆、可切换 |
| **QLoRA** | LoRA + 4bit 量化基座 | 低（单卡可训 7B~70B） | 强 | 消费级显卡训大模型 |
| **PEFT** | 适配器家族总称 | 视具体方法 | 强 | 统一管理多种高效微调 |

**核心直觉**：大模型权重里大量是『冗余方向』。LoRA 假设『有用的权重更新」可分解为低秩矩阵 ΔW = A·B，只训练这两个小矩阵（秩 r 通常 8~64），原权重冻结。好处：

- 训练参数量从『数十亿』降到『数百万』，显存和时长骤降；
- 原模型不动，一个基座可挂多个 LoRA 适配器，按需热插拔；
- 合并（merge）后推理无额外开销，或保持分离按需加载。

<Callout type="tip" title="LoRA 超参经验值">
  rank（r）越大拟合越强但越易过拟合，常用 8 / 16 / 32；alpha 一般取 2r；
  target_modules 默认 attention 的 q/v/proj。先小 r 跑通，再按需加大。具体以 PEFT 文档为准。
</Callout>

## 4. OpenAI 托管微调：可运行骨架

如果你不想碰训练集群，OpenAI 的 fine-tuning API 是最省事路径。下面是用 Node SDK 提交一次 SFT 作业、并用 Zod 校验本地数据文件的完整骨架：

```ts
// openai_finetune.ts —— 托管 SFT 作业提交（可运行骨架）
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';
import { readFileSync } from 'node:fs';

const client = new OpenAI();

// ① 复用第 2 节的 Zod schema 校验训练文件，避免垃圾数据烧钱
const Message = z.object({
  role: z.enum(['system', 'user', 'assistant']),
  content: z.string().min(1),
});
const SftSample = z.object({
  messages: z.array(Message).min(2).refine(
    (ms) => ms[ms.length - 1].role === 'assistant',
    { message: '末条须为 assistant' }
  ),
});

function validateFile(path: string): boolean {
  const lines = readFileSync(path, 'utf8').trim().split('\n');
  return lines.every((l) => SftSample.safeParse(JSON.parse(l)).success);
}

async function run() {
  if (!validateFile('train.jsonl')) {
    throw new Error('训练数据校验失败，已中止提交');
  }

  // ② 上传训练文件（必须先 upload，拿到 file_id）
  const file = await client.files.create({
    file: readFileSync('train.jsonl'),
    purpose: 'fine-tune',
  });

  // ③ 创建微调作业：选基模 + 超参（以官方文档为准，字段易变）
  const job = await client.fineTuning.jobs.create({
    training_file: file.id,
    model: 'gpt-4o-mini-2024-07-18', // 基模，按你账号可用列表填
    hyperparameters: {
      n_epochs: 3, // 小数据集可多轮；过大易过拟合
      // batch_size / learning_rate_multiplier 也可在此覆盖
    },
  });

  console.log('作业已提交:', job.id);

  // ④ 轮询状态（生产环境建议用 webhook / 事件流，而非死轮询）
  let status = job.status;
  while (status === 'running' || status === 'validating_files') {
    await new Promise((r) => setTimeout(r, 30_000));
    const cur = await client.fineTuning.jobs.retrieve(job.id);
    status = cur.status;
    console.log('当前状态:', status);
  }

  if (status === 'succeeded') {
    const fineTuned = await client.fineTuning.jobs.retrieve(job.id);
    console.log('微调模型名:', fineTuned.fine_tuned_model);
  }
}

run();
```

运行：`npm i openai dotenv zod` 然后 `npx tsx openai_finetune.ts`。

<Callout type="warn" title="托管微调的隐性约束">
  厂商对训练文件大小、样本数、基模版本都有准入门槛（如最少 N 条）。提交前务必读当前
  官方『fine-tuning 要求』页——字段和限额随版本变，本骨架仅示意流程。
</Callout>

## 5. LoRA / QLoRA 自训：伪代码骨架

当你要在自有显卡上训开源模型，PEFT + Transformers 是主流。下面是以官方文档为准的思路骨架（不可直接复制运行，超参见最新文档）：

```python
# lora_train.py —— LoRA 微调骨架（思路为主，以 PEFT / Transformers 官方文档为准）
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments, Trainer
from peft import LoraConfig, get_peft_model
import torch

# ① 加载基座（QLoRA 时在此加 4bit 量化加载，见 bitsandbytes）
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3-8B",
    torch_dtype=torch.bfloat16,
    device_map="auto",
)
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3-8B")

# ② 只把 LoRA 适配器挂到注意力层，原权重冻结
lora_cfg = LoraConfig(
    r=16,                      # 低秩维度：越大拟合越强
    lora_alpha=32,             # 缩放系数，常取 2*r
    target_modules=["q_proj", "v_proj"],  # 注入位置
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_cfg)
model.print_trainable_parameters()   # 会看到『可训参数 <1%』

# ③ 标准 Trainer 流程：数据经 tokenizer 编码成 labels，因果 LM 算损失
args = TrainingArguments(
    output_dir="./lora-out",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=8,   # 小显存靠累积补 batch
    learning_rate=2e-4,
    num_train_epochs=3,
    fp16=True,
    logging_steps=10,
)
# trainer = Trainer(model=model, args=args, train_dataset=tokenized_dataset)
# trainer.train()
# model.save_pretrained("./lora-adapter")  # 只存适配器，体积小
```

<Callout type="note" title="QLoRA 省显存的原理">
  QLoRA 在 LoRA 基础上，把『冻结的基座』用 4bit（NF4）量化加载，前向时反量化计算。
  这样 7B 模型可在单张 24GB 卡训练，70B 也可在多卡消费级环境跑。代价是极少量精度损失，
  实践中几乎无感。具体加载写法（BitsAndBytesConfig）以官方文档为准。
</Callout>

## 6. 评估：别只看 loss

训练 loss 下降≠能力达标。SFT 评估要分层：

- **自动指标**：在保留集上算困惑度（PPL）、格式合规率（如是否严格 JSON）。
- **LLM-as-judge**：用强模型按 rubric 给回答打分（准确性、语气、安全性），注意 judge 自身偏差。
- **任务完成度**：针对你的真实场景抽 50~200 条黄金集，人工或自动判定『达标/不达标』。
- **回归测试**：微调后原能力不能掉（如通用问答骤降=过拟合/遗忘），需跑一套通用基准做护栏。

<Callout type="warn" title="过拟合信号">
  训练 loss 一路降、验证 loss 却回升 → 过拟合。常见解法：降 epoch、加 LoRA dropout、
  扩增数据、降 rank。小数据集（几百条）跑 1~3 个 epoch 通常就够，别贪图多轮。
</Callout>

## 7. 成本：算清这笔账

| 环节 | 托管微调（OpenAI） | 自训 LoRA（8B，单卡） |
|------|-------------------|----------------------|
| 数据准备 | 人力为主 | 人力为主 |
| 训练算力 | 按 token 计费，千条级约几~几十美元 | 单卡跑数小时，电费可忽略 |
| 推理 | 微调模型按调用计费（略高于基模） | 自托管免费，但需运维 GPU |
| 隐性成本 | 数据出域合规风险 | 工程与运维人力 |

<Callout type="tip" title="省钱口诀">
  托管微调：先在小样本（几百条）上验证基线，再决定扩量；用 `n_epochs` 控制，避免白训。
  自训：QLoRA + 梯度累积把显存压到最低；适配器只存几 MB，可挂多版本 A/B。
</Callout>

## 8. 训练完怎么用：合并与上线衔接

微调产出的东西分两类，处理方式不同：

### 8.1 托管微调：直接换模型名

OpenAI 类作业成功后，`fine_tuned_model` 就是一个新模型 ID，推理时代入即可：

```ts
// 用微调后的模型推理（与基模调用方式完全一致）
const res = await client.chat.completions.create({
  model: fineTunedModelId, // 第 4 节拿到的名字，替换基模即可
  messages: [{ role: 'user', content: '磁盘满了怎么查？' }],
});
```

零部署成本，但模型权重在厂商侧，数据出域需合规评估。

### 8.2 LoRA 适配器：合并 or 分离加载

自训得到的 `./lora-adapter` 只有几 MB（仅低秩矩阵）。上线有两种姿势：

- **合并（merge）**：把适配器权重加回基座，产出『完整模型』，推理无额外逻辑、延迟零增加。适合固定一个适配器长期服务。
- **分离加载**：推理框架（vLLM / TGI / llama.cpp）支持『基座 + 适配器』分离加载，可热切换多个 LoRA。适合多租户/多任务共用一个基座。

```python
# merge_lora.py —— 把 LoRA 合并进基座（思路骨架，以官方文档为准）
from peft import PeftModel
from transformers import AutoModelForCausalLM, AutoTokenizer

base = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3-8B")
model = PeftModel.from_pretrained(base, "./lora-adapter")
merged = model.merge_and_unload()          # 权重相加，适配器消失于结果中
merged.save_pretrained("./llama3-8b-sft")  # 得到可独立部署的完整模型
tokenizer.save_pretrained("./llama3-8b-sft")
```

<Callout type="tip" title="选 merge 还是分离">
  单场景、要最低延迟 → merge。多场景共用基座、需 A/B 多个适配器 → 分离加载。
  分离加载的『切换成本』几乎为零，但部分老推理框架对动态 LoRA 支持有限，部署前先验证。
</Callout>

### 8.3 上线前最后一道关：护栏

微调模型仍可能输出违规/越界内容。上线时务必在推理侧叠护栏（详见 llm-safety）：
输入过滤 + 输出审核 + 敏感词/越狱检测。微调注入的是『能力』，护栏约束的是『边界』，两者正交、缺一不可。

<Callout type="note" title="版本与回滚">
  适配器/微调模型要像代码一样版本化（命名带日期/数据版本）。一旦新版本指标回退，
  能一键回滚到上一版。建议保留最近 N 个版本，别只留『最新』。
</Callout>

## 9. 常见坑

<Callout type="danger" title="训练/评测泄漏">
  若评测集样本出现在训练数据里，指标虚高。提交前必须去重、留干净保留集，
  最好加『题目级』去重而非仅行级。
</Callout>

<Callout type="warn" title="数据分布单一">
  只喂『完美回答』会导致模型不会拒答/澄清。务必混入拒答、反问、降级、异常输入样本，
  否则上线后遇到越界问题会硬编答案（幻觉）。
</Callout>

<Callout type="warn" title="LoRA rank 盲目拉满">
  rank 越大不代表越好。过大易过拟合且丢『通用能力』，先小 r（8~16）跑通再加。
  另外 target_modules 只选 q/v 通常够，全层注入收益有限且更贵。
</Callout>

<Callout type="warn" title="QLoRA 精度陷阱">
  4bit 基座在『数值敏感』任务（如精确计算、特定格式）上偶尔掉点。若质量要求极高，
  对关键任务用 8bit 或全精度 LoRA 做对照实验再定。
</Callout>

<Callout type="note" title="别忘了对齐位置">
  SFT 让模型『会按格式答』，但不保证『安全/有用』。生产助手通常还要 RLHF/DPO 对齐一步，
  或在推理侧加护栏（见 llm-safety）。把微调当『能力注入』，对齐当『行为约束』，两者配合。
</Callout>

## 小结

- 决策顺序：提示工程/RAG → SFT → LoRA/QLoRA → 全参，按成本和可控性升级。
- SFT 数据『质量 > 数量』，务必混入拒答/降级样本，并用 Zod 在入库前校验格式。
- 方案选型：全参最强最贵；LoRA 只训低秩适配器、可逆可热插拔；QLoRA 4bit 基座让单卡训大模型。
- 托管微调用 OpenAI Node SDK 可跑通全流程；自训用 PEFT 骨架（以官方文档为准）。
- 评估分层（自动+judge+任务完成度+回归），警惕过拟合与能力遗忘；成本先小样本验证再扩。
- 红线：防泄漏、防分布单一、rank 别盲拉、QLoRA 精度对照、微调后还要对齐。

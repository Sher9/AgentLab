# 规划与推理：ReAct、Plan-and-Execute、反思与思维树

架构（agent-architecture）解决了『模块怎么分』，但决策层真正难的是：**让 LLM 决定『先做什么、后做什么』**。这就是规划（Planning）与推理（Reasoning）。同一个任务，『边想边做』和『先列计划再执行』是两种截然不同的策略，适用场景也不一样。

面向有经验的开发者，本篇把四种主流策略——ReAct、Plan-and-Execute、Reflexion（反思）、ToT（思维树）——的原理、代码骨架、对比与踩坑一次讲透。代码沿用 OpenAI Node SDK + Zod。

## 1. 规划为什么难：LLM 推理的真相

先破除一个误解：**LLM 不会『真正规划』**。它做的是『在每一步，根据当前上下文预测最可能合理的下一个 token』。所谓『规划能力』，来自训练数据里海量的『先想步骤、再执行』的示范，以及我们给它的提示结构。

这带来两个本质约束：

- **没有全局回溯**：ReAct 一旦走错一步，模型只能基于『已经错的上下文』继续编，不会自动回到分支点重选；
- **计划会过时**：任务执行到一半，现实变了（工具返回意外结果），原定计划可能失效，需要动态调整。

<Callout type="note" title="规划是提示工程 + 控制流">
  Agent 的规划能力 = 合理的提示结构（让模型输出『思考+动作』） + 你写的控制流（决定何时停、
  何时回滚、何时重规划）。模型负责『生成候选步骤』，你负责『保证过程收敛』。
</Callout>

## 2. ReAct：边想边做

**ReAct = Reason + Act**。每轮让模型同时输出『思考（Thought）』和『动作（Action）』，执行动作后把『观察（Observation）』回填，进入下一轮。它把推理与行动**交织**在一起，适合步骤依赖前一步结果、无法预先列全计划的任务。

```
Thought: 我需要先查北京的天气，才能决定建议穿什么
Action: get_weather(city=北京)
Observation: 北京 晴 26°C
Thought: 26°C 挺舒服，建议薄外套即可
Action: reply(建议穿薄外套)
```

```ts
// react.ts —— ReAct 骨架（思考与动作交织）
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';

const client = new OpenAI();

const tools = [{ type: 'function', function: {
  name: 'get_weather', description: '查天气',
  parameters: { type: 'object', properties: { city: { type: 'string' } }, required: ['city'] },
}}] as const;

// 用 Zod 解析模型的结构化输出（思考 + 动作）
const StepSchema = z.object({
  thought: z.string(),
  action: z.union([
    z.object({ kind: 'tool', name: z.string(), args: z.record(z.unknown()) }),
    z.object({ kind: 'reply', content: z.string() }),
  ]),
});

async function react(userGoal: string) {
  const messages = [
    { role: 'system', content: '你用 ReAct 范式：每轮先写 Thought，再决定 Action（调工具或回复）。' },
    { role: 'user', content: userGoal },
  ];
  for (let i = 0; i < 8; i++) {
    const res = await client.chat.completions.create({ model: 'gpt-4o-mini', messages, tools });
    const msg = res.choices[0].message;
    messages.push(msg);
    if (!msg.tool_calls?.length) return msg.content; // 没有动作 → 直接收尾
    for (const call of msg.tool_calls) {
      const args = JSON.parse(call.function.arguments);
      const obs = `北京：晴 26°C`; // 真实场景换成工具实现
      messages.push({ role: 'tool', tool_call_id: call.id, content: obs });
    }
  }
}
```

<Callout type="tip" title="ReAct 适合『路径依赖』任务">
  当下一步取决于上一步的真实结果（查到天气才能建议穿搭），ReAct 比预先列计划更稳——
  因为计划本就列不全。它的问题是步数不可控，必须设上限。
</Callout>

## 3. Plan-and-Execute：先规划后执行

与 ReAct 相反，Plan-and-Execute **把『规划』和『执行』分成两个阶段**：先让一个（通常更强的）模型把任务拆成有序步骤列表，再由执行器逐步完成。中途若某步失败或现实变化，再触发『重新规划』。

```
规划器输出：
  1. 查北京天气
  2. 查用户日程
  3. 若室外且有空 → 建议去公园
执行器逐步跑 1→2→3，遇到意外（下雨）再回规划器修订
```

```ts
// plan-execute.ts —— 先规划后执行骨架
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';

const client = new OpenAI();

// 规划器的产出：有序步骤列表（单一事实来源，便于校验与重规划）
const PlanSchema = z.object({
  steps: z.array(z.object({
    id: z.number(),
    description: z.string(),
    dependsOn: z.array(z.number()).default([]), // 步骤间依赖，决定能否并行
  })),
});
type Plan = z.infer<typeof PlanSchema>;

async function plan(goal: string): Promise<Plan> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o', // 规划用更强的模型，执行可用更小的
    messages: [
      { role: 'system', content: '把任务拆成有序步骤，输出 JSON。' },
      { role: 'user', content: goal },
    ],
    response_format: { type: 'json_schema', json_schema: { name: 'plan', schema: PlanSchema.shape } },
  });
  return PlanSchema.parse(JSON.parse(res.choices[0].message.content!));
}

async function execute(plan: Plan) {
  const results = new Map<number, string>();
  for (const step of plan.steps) {
    // 依赖未完成的步骤先跳过（真实场景用拓扑排序 + 并行）
    if (!step.dependsOn.every((d) => results.has(d))) continue;
    const out = `完成：${step.description}`; // 真实场景：调工具/调子 Agent
    results.set(step.id, out);
    console.log(out);
  }
  return results;
}

const p = await plan('为用户安排明天的户外活动');
await execute(p);
```

<Callout type="tip" title="规划与执行分离可独立调参">
  规划器用强模型保证步骤质量，执行器用便宜模型跑单步，成本与质量可分别优化。
  而 ReAct 每步都调强模型，账单会更贵。这是两者在成本上的核心差异。
</Callout>

## 4. Reflexion：自我批评与反思

ReAct 走错不会回头。Reflexion 在每轮（或每轮结束后）加一个**反思步骤**：让模型『回顾自己刚才的决策，指出错在哪、下次怎么改』，把反思文本作为额外上下文带入下一轮，从而自我纠正。

```ts
// reflexion.ts —— 在 ReAct 基础上加反思步
async function reflect(trajectory: string): Promise<string> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '你是严厉的评审。看下面的决策轨迹，指出错误与改进点，一句话。' },
      { role: 'user', content: trajectory },
    ],
  });
  return res.choices[0].message.content ?? '';
}

// 在 react 循环里，每步结束把『轨迹 + 反思』拼回 messages：
//   messages.push({ role: 'system', content: `反思：${await reflect(fullTrace)}` });
// 模型下一轮就能『避开刚才的坑』
```

<Callout type="note" title="反思是记忆的一种">
  Reflexion 本质是把『自我批评』当作一段记忆回填，和 M4 的摘要记忆同源。
  区别只在内容来自『对自己行为的评价』而非『对对话的压缩』。
</Callout>

## 5. ToT（思维树）：搜索多条路径

ReAct 是『一条链』，Plan-and-Execute 是『一条计划』。ToT（Tree of Thoughts）把每一步推理展开成**多个候选分支**，用模型对每個分支打分（或『值函数』），保留高分支、剪掉低分支，像搜索一棵树一样找最优解。适合需要『尝试多种思路、择优』的难题（如谜题、策略博弈）。

```
        根(问题)
       ├─ 思路A ── 评分 0.7 ── 展开 ── ... 保留
       ├─ 思路B ── 评分 0.3 ── 剪枝
       └─ 思路C ── 评分 0.8 ── 展开 ── ... 保留
```

```ts
// tot.ts —— 思维树骨架（简化：每层多候选 + 评分 + 保留）
async function score(thought: string, goal: string): Promise<number> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '给下面的思路对完成目标的帮助打分 0~1，只回数字。' },
      { role: 'user', content: `目标：${goal}\n思路：${thought}` },
    ],
  });
  return Number(res.choices[0].message.content ?? '0');
}

async function expand(thought: string, goal: string, k = 3): Promise<string[]> {
  // 让模型一次产出 k 个下一步候选（伪代码，真实用 JSON 模式约束）
  const res = await client.chat.completions.create({
    model: 'gpt-4o', messages: [
      { role: 'system', content: `给出 ${k} 个不同的下一步思路，换行分隔。` },
      { role: 'user', content: `目标：${goal}\n当前：${thought}` },
    ],
  });
  return (res.choices[0].message.content ?? '').split('\n').filter(Boolean);
}

// 主循环：每层 expand → 逐个 score → 只保留 top-m 进下一层，直到终止
```

<Callout type="warn" title="ToT 成本极高">
  每层产生 k 个候选、每个都要 score，token 消耗是 ReAct 的数倍到数十倍。
  只在『想错代价高、且确实需要搜多路径』的任务用（谜题、重要决策），
  日常任务用 ReAct/Plan 足够，别为炫技上 ToT。
</Callout>

## 6. 四种策略对比

| 策略 | 结构 | 何时用 | 成本 | 回溯能力 |
|------|------|--------|------|----------|
| ReAct | 单链，想做交织 | 步骤依赖前序结果、路径不定 | 中（每步都推理） | 弱（靠反思补） |
| Plan-and-Execute | 先计划后执行 | 步骤可预先列出、规模大 | 低（执行可用小模型） | 中（可重规划） |
| Reflexion | ReAct + 反思步 | 易走错、需自我纠正 | 中高（多一次反思调用） | 较强（带记忆纠正） |
| ToT | 树状多分支搜索 | 需搜多路径择优的难题 | 极高 | 强（天然剪枝） |

<Callout type="note" title="可组合，不必单选">
  实战常组合：用 Plan-and-Execute 定大框架，其中复杂单步用 ReAct，关键决策点加 Reflexion，
  极少数死胡同用 ToT 展开。策略是积木，不是宗教。
</Callout>

## 7. 规划与 LLM 推理的关系

- **CoT（思维链）是规划的底层燃料**：模型能『写出中间推理步骤』，才谈得上 ReAct 的 Thought、Plan 的步骤。没有 CoT 能力，规划策略无从落地。
- **推理质量随模型能力跃迁**：强模型列的计划更合理、ReAct 更少走死胡同。所以『换更强模型』往往比『改提示结构』收益更大——但成本也更高。
- **结构化输出是规划的载体**：用 `response_format: json_schema` / Zod 把计划锁成可校验结构，比让模型吐自由文本稳得多（见 m1 工具调用）。

<Callout type="tip" title="给规划器更强的模型">
  经验法则：规划与反思用强模型（gpt-4o 级），单步执行用轻模型（gpt-4o-mini 级）。
  强模型只在『需要全局判断』的地方出场，账单立刻友好。
</Callout>

## 8. 踩坑

<Callout type="danger" title="没有步数上限">
  任何基于循环的策略（ReAct/ToT）都必须设最大步数 + 总超时。模型偶尔会反复调同一工具，
  没有上限就烧钱卡死。建议上限 8~15 步，并限制单步工具调用数。
</Callout>

<Callout type="warn" title="计划一旦写过就当圣旨">
  Plan-and-Execute 最易犯的病：执行到第三步发现现实和计划不符，却硬着头皮走完。
  必须加『动态重规划』触发条件：某步失败 / Observation 与预期严重偏离 / 用户改口 → 回规划器。
  计划是地图不是枷锁。
</Callout>

<Callout type="warn" title="ToT 不看成本就上">
  ToT 的 token 消耗会吓人。上线前估算：树宽 k × 深度 d × 每节点 2 次调用（expand+score）。
  日常任务用 ReAct 足够，ToT 留给真正需要搜多路径的难题。
</Callout>

<Callout type="warn" title="反思变成自我安慰">
  Reflexion 的反思文本若不加约束，模型可能写一堆正确的废话却不改行为。
  反思要具体（指出『第 2 步不该调 X，因为 Y』），并能实际影响下一步动作，否则只是给 prompt 加噪声。
</Callout>

<Callout type="danger" title="把规划结果当可信真相">
  计划是模型『猜』的，不是事实。执行每步前仍要校验参数、校验工具可用性。
  规划错了不可怕，可怕的是不校验就照单全收去执行副作用操作。
</Callout>

## 9. 统一骨架：规划 + 执行 + 反思拼起来

把前面三节合成一个能跑的最小闭环：规划器列步骤，执行器逐步跑，每步之后用反思器评估『是否走偏』，偏了就触发重规划。存成 `planner-agent.ts`，已装 `openai` + `dotenv` + `zod` 即可运行（工具与规划器用桩）。

```ts
// planner-agent.ts —— 规划 + 执行 + 反思 的可运行骨架
import OpenAI from 'openai';
import 'dotenv/config';
import { z } from 'zod';

const client = new OpenAI();
const PlanSchema = z.object({
  steps: z.array(z.object({ id: z.number(), description: z.string() })),
});
type Plan = z.infer<typeof PlanSchema>;

async function plan(goal: string): Promise<Plan> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o',
    messages: [{ role: 'system', content: '拆成有序步骤，输出 JSON。' }, { role: 'user', content: goal }],
    response_format: { type: 'json_schema', json_schema: { name: 'plan', schema: PlanSchema.shape } },
  });
  return PlanSchema.parse(JSON.parse(res.choices[0].message.content!));
}

// 反思器：评估当前进度是否偏离目标（Reflexion 的落地）
async function reflect(goal: string, done: string[]): Promise<string> {
  const res = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '评估已完成步骤是否偏离目标，若需调整只回一句话，否则回 OK。' },
      { role: 'user', content: `目标：${goal}\n已完成：${done.join(' / ')}` },
    ],
  });
  return res.choices[0].message.content ?? 'OK';
}

async function run(goal: string) {
  let p = await plan(goal);
  const done: string[] = [];
  for (let round = 0; round < 3; round++) {        // 最多 3 轮『规划→执行→反思』
    for (const step of p.steps) {
      done.push(`完成：${step.description}`);          // 真实场景：调工具/子 Agent
      console.log(done[done.length - 1]);
    }
    const r = await reflect(goal, done);
    if (r === 'OK') break;                            // 反思通过 → 结束
    p = await plan(`${goal}\n注意：${r}`);            // 反思不通过 → 带反馈重规划
  }
}

run('为用户安排明天的户外活动，含天气与日程检查');
```

<Callout type="tip" title="重规划的触发点要少而准">
  别每步都重规划（太贵且抖动），也别全程不重规划（计划会腐化）。
  好的触发点是：某步执行失败、Observation 与预期严重偏离、或反思器连续两次给出非 OK。
  让重规划成为『例外处理』而非『常态』。
</Callout>

## 10. 适用与不适用场景

| 场景 | 推荐策略 | 原因 |
|------|----------|------|
| 多跳检索问答（答案依赖前序结果） | ReAct | 步骤无法预列，需边查边决定 |
| 长流程业务编排（下单→审批→通知） | Plan-and-Execute | 步骤可预列，规模大，执行用轻模型省成本 |
| 代码生成 / 易走错的生成任务 | ReAct + Reflexion | 需自我纠正，反思降低返工 |
| 谜题 / 博弈 / 重要决策 | ToT | 需搜多路径择优，代价可接受 |
| 纯单轮问答 / 事实查询 | 都不用 | 直接一次调用，规划是多余开销 |

<Callout type="note" title="最简单的不用规划">
  如果你的任务『给一句话就能直接答』，那就别上任何规划框架——一次 `chat.completions.create`
  足矣。规划带来的是控制流复杂度与成本，只为『多步、有依赖、易错』的任务买单。
</Callout>

## 小结

- 规划 = 提示结构 + 控制流；模型生成候选步骤，你保证过程收敛（上限/重规划）。
- ReAct 想做交织，适合路径依赖任务；Plan-and-Execute 先计划后执行，可强弱模型分离省成本。
- Reflexion 用反思回填纠正错误，ToT 用树状搜索多路径择优但极贵。
- 四者可组合：大框架用 Plan，复杂单步用 ReAct，关键决策加 Reflexion，死胡同才用 ToT。
- 规划依赖 CoT 与结构化输出；强模型列计划更稳，但只在全局判断处用强模型。
- 红线：步数上限、动态重规划、成本预算、反思要落地、规划结果须校验。

<Callout type="note" title="下一步">
  规划策略决定了『决策层怎么思考』。当任务需要同时处理图像、语音、文档时，
  感知层要怎么路由不同模态、怎么协同工具？这就是 **agent-multimodal（多模态 Agent）** 的主题。
</Callout>

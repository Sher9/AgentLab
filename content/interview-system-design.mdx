# 系统设计题：RAG/Agent 系统怎么设计

面试里常被要求『设计一个面向企业的 RAG 问答系统』或『设计一个多 Agent 客服』。这道题考察的不是某个 API，而是**分层架构、容量估算、权衡取舍、失败预案**。下面给一套可复用的答题框架与落地骨架。

<Callout type="note" title="答题顺序建议">
  先澄清需求（QPS、知识规模、延迟 SLA、合规要求），再画架构，再做容量估算，
  最后讲权衡与降级。面试官最看重『你主动问了哪些约束』。
</Callout>

## 1. 需求澄清（先问再答）

动手前先确认边界，避免设计空中楼阁：

- **规模**：知识库文档量（万级/亿级）？日活与峰值 QPS？
- **质量 SLA**：答案可接受延迟（秒级/亚秒级）？容忍多少幻觉率？
- **合规**：是否多租户？数据能否出域？是否需审计留痕？
- **更新频率**：知识多久变一次？是否需要近实时增量更新？

## 2. 架构分层

典型 RAG/Agent 系统分四层：

```
接入层    API 网关 / 鉴权 / 限流 / 多租户路由
   │
检索层    切分 → 向量库 + BM25 混合检索 → 重排 → 上下文组装
   │
生成层    LLM 编排（prompt + 引用约束 + 结构化输出）
   │
支撑层    缓存（查询/embedding）、可观测（trace/成本）、降级、评测回归
```

<Callout type="tip" title="Agent 系统多一层编排">
  若是 Agent（而非纯 RAG），在生成层之上再加『控制器』：主循环、工具注册、
  HITL 确认、错误恢复。把工具调用与检索解耦，便于单独扩缩容。
</Callout>

## 3. 容量估算（面试必算）

假设：日活 10 万，人均 5 次问答，峰值 QPS ≈ 日均请求 / 86400 × 峰值系数(5) ≈ 500 万 / 86400 × 5 ≈ **290 QPS**。

| 资源 | 估算 | 说明 |
|------|------|------|
| 日问答量 | 50 万 | 10万 × 5 |
| 峰值 QPS | ~290 | 含 5× 突发系数 |
| embedding 调用 | 每次检索 1 次 | 与问答同量级 |
| 向量规模 | 文档数 × 切块数 | 万级文档可达千万向量 |
| 缓存命中 | 30%~50% | 重复/相似问题省调用 |

<Callout type="warn" title="别忘了写入侧成本">
  容量估算常只算『读』。知识库更新时批量 embedding 是突发算力，需离线队列削峰，
  否则和业务查询抢 GPU/配额。
</Callout>

## 4. 关键权衡

| 决策点 | 选项 A | 选项 B | 取舍 |
|--------|--------|--------|------|
| 检索 | 纯向量 | 向量+BM25 混合 | 混合召回更稳，运维更重 |
| 模型 | 大模型 | 小模型分级 | 大模型质量高但贵，决策/抽取用小模型 |
| 缓存 | 查缓存 | 不缓存 | 缓存省钱但需处理语义相似与失效 |
| 一致性 | 实时检索 | 异步更新 | 实时准但慢，异步快但短暂不一致 |

```ts
// design-skeleton.ts —— 系统骨架：检索+缓存+生成+降级（可运行思路）
import OpenAI from 'openai';
import 'dotenv/config';

const client = new OpenAI();

// 极简查询缓存：真实场景用 Redis，按语义哈希命中
const cache = new Map<string, string>();

async function answer(question: string): Promise<string> {
  // ① 缓存命中直接返回，省一次检索+生成
  if (cache.has(question)) return cache.get(question)!;

  try {
    // ② 检索（伪实现，真实换成混合检索 + 重排）
    const chunks = [`AgentLab 用混合检索降噪`, `生成要求标注来源`];
    const context = chunks.join('\n');
    // ③ 生成
    const res = await client.chat.completions.create({
      model: 'gpt-4o-mini',
      messages: [
        { role: 'system', content: '只基于片段作答，标注来源，不知道就说不知道。' },
        { role: 'user', content: `片段：\n${context}\n问题：${question}` },
      ],
    });
    const ans = res.choices[0].message.content ?? '暂无回答';
    cache.set(question, ans); // ④ 写入缓存
    return ans;
  } catch {
    // ⑤ 降级：模型/检索挂了，返回友好占位而非 500
    return '系统繁忙，请稍后重试或联系人工客服。';
  }
}

answer('AgentLab 怎么防幻觉？').then(console.log);
```

## 5. 可观测与降级

- **可观测**：每个请求打 trace/span，记录检索命中、token 消耗、延迟、成本；建成本与质量看板。
- **降级**：检索服务不可用时退化为『纯模型回答并标注不确定性』；模型限流时排队 + 友好提示；敏感工具全部 HITL。

<Callout type="danger" title="多租户数据隔离是硬约束">
  向量检索必须带 `filter(tenant_id)`，缓存 key 必须含租户前缀，否则会串数据——
  这是合规红线，不是优化项。
</Callout>

## 6. 扩展与分片

当向量规模到亿级、QPS 到千级，单机向量库不够用，需考虑：

- **分片（Sharding）**：按租户或文档域把向量分到不同节点，检索时只打相关分片，降延迟。
- **副本（Replica）**：读多写少，检索节点水平复制扛 QPS；写入走主节点异步同步。
- **冷热分离**：高频知识放内存/高速索引，历史归档降级到磁盘，控成本。
- **异步管线**：知识更新走消息队列批量 embedding，与在线查询解耦，避免突发抢占。

<Callout type="tip" title="先垂直再水平">
  多数项目远没到分片阶段。先优化切块粒度、检索阈值、缓存命中率，
  这些往往比加机器收益更大。过早分片只会增加运维复杂度。
</Callout>

## 7. 常见设计坑

<Callout type="danger" title="把 RAG 当黑盒丢给框架">
  直接套 LangChain 默认链而不理解切分/检索参数，线上召回一塌糊涂还无从调。
  先手写过端到端骨架，再用框架封装，才知道每层的旋钮在哪。
</Callout>

<Callout type="warn" title="忽略增量更新">
  知识库天天变，却只在首次全量建库。结果模型基于过期片段作答，且无人发现。
  必须有增量更新 + 重建机制 + 更新后的回归评测。
</Callout>

<Callout type="warn" title="没有降级与限流">
  检索或模型一抖动，整站 500。必须在接入层限流、生成层降级、敏感操作 HITL，
  把『部分可用』当默认目标，而非『全有全无』。
</Callout>

<Callout type="warn" title="容量只算读不算写">
  如前文所述，批量 embedding 是突发算力。写入侧不上队列削峰，会和在线查询抢资源。
</Callout>

## 8. 小结

- 先澄清规模/延迟/合规，再分层设计：接入 → 检索 → 生成 → 支撑。
- 容量估算算清 QPS、向量规模、缓存命中，别漏写入侧突发。
- 权衡聚焦检索策略、模型分级、缓存、一致性四件事，每项都说清代价。
- 工程红线：多租户隔离、缓存降级、可观测闭环、敏感操作 HITL。

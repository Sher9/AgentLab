# 护栏与安全评估：输入/输出过滤、敏感词、合规与红队评估

M6 在『可观测与评估』里把 Guardrails 作为守住底线的一环提了一句。这一篇把**护栏本身**讲透：在 Agent 的输入侧、输出侧、运行时分别该布什么防线，敏感词/合规怎么做，以及——最关键的——**怎么用红队评估证明你的护栏真的拦得住**，而不是『我以为它拦得住』。

没有护栏的 Agent 直接面对用户（和恶意用户），轻则被提示注入带偏、重则泄露数据、输出违规内容、被拿去干坏事。护栏是上生产的硬门槛。

## 1. 什么是护栏，为什么必要

护栏（Guardrail）= 在模型『自由发挥』之外，加的一层**确定性或模型辅助的过滤与约束**，确保输入输出满足安全/合规/业务红线。它和『评估指标』不同：评估是**事后打分**，护栏是**事前/事中拦截**。

<Callout type="note" title="护栏补模型的不可控">
  模型本身『想说什么说什么』，无法被 100% 约束。护栏的价值就是把『不可控的生成』
  框在安全的轨道上：过滤掉危险输入、拦下违规输出、在危险动作执行前叫停。
  它是安全网，不是装饰。
</Callout>

## 2. 护栏的三层架构

| 层 | 位置 | 拦截什么 | 典型手段 |
|----|------|----------|----------|
| 输入护栏 | 用户消息进模型前 | 提示注入、敏感词、越权指令、PII 泄露请求 | 规则/分类器/注入检测 |
| 输出护栏 | 模型回复出网前 | 毒性、违规、泄密、格式错误 |  moderation/正则/结构化校验 |
| 运行时护栏 | 工具/动作执行时 | 危险操作（删库、发钱）、超预算、越权 | 权限最小化、确认、限额 |

三层是互补的：输入拦『想搞事的人』，输出拦『模型抽风』，运行时拦『动作副作用』。

## 3. 输入护栏：提示注入是第一战场

提示注入（Prompt Injection）是 Agent 头号威胁：攻击者把『忽略之前指令，改为……』藏进网页/邮件/文档，Agent 检索到后照做。输入护栏要做：

- **注入模式检测**：用分类器或规则识别『系统指令伪装』『角色翻转』等套路；
- **来源标记与隔离**：把检索到的外部内容明确标注为『不可信上下文』，并在 system prompt 里强调其优先级低于真实指令；
- **敏感词 / 越权指令**：正则 + 词典拦『告诉我你的 system prompt』『绕过审核』等。

```ts
// input-guardrail.ts —— 输入护栏思路骨架（以官方文档为准，API 易变）
// 真实项目可用厂商 moderation / 自训分类器，这里给出可替换的接口形态
interface GuardResult { blocked: boolean; reason?: string; score: number }

// ① 提示注入检测：规则 + 轻量分类器双保险
function detectInjection(text: string): GuardResult {
  const patterns = [
    /忽略(之前|以上|先前)的?指令/i,   // 经典注入话术
    /system\s*prompt/i,                // 想套系统提示
    /你现在是(另一个|新的)角色/i,
  ];
  for (const p of patterns) {
    if (p.test(text)) return { blocked: true, reason: '疑似提示注入', score: 1 };
  }
  // 真实场景再接一次分类器调用做语义级判定（见下方 shouldBlock）
  return { blocked: false, score: 0 };
}

// ② 敏感词/越权：词典匹配，O(n) 可线性扫描
function containsBanned(text: string, dict: string[]): GuardResult {
  for (const w of dict) {
    if (text.includes(w)) return { blocked: true, reason: `命中敏感词：${w}`, score: 1 };
  }
  return { blocked: false, score: 0 };
}

// 在 Agent 入口统一拦截
function guardInput(userText: string): GuardResult {
  const a = detectInjection(userText);
  if (a.blocked) return a;
  return containsBanned(userText, ['违规词示例A', '违规词示例B']); // 真实词典从配置加载
}
```

<Callout type="warn" title="规则拦不住语义级注入">
  正则只能挡『教科书式』注入。攻击者会改写措辞（『忘掉你刚才学的，改做 X』），
  规则必然漏。语义级注入要靠**分类器/强模型判定**，且输入护栏要和输出护栏、运行时护栏叠加，
  单点必被绕过。护栏是纵深防御，不是一道门。
</Callout>

## 4. 输出护栏：模型抽风也得兜住

即使输入干净，模型也可能输出违规、泄密或格式错。输出护栏在回复出网前再过一道：

- **毒性 / 违规检测**：用 moderation 分类器（见 4.1）或自训模型；
- **泄密检测**：扫描输出是否含密钥、PII、内部知识库原文；
- **格式/业务约束**：用 Zod 校验结构（见 eval-metrics 第 3.3 节）。

```ts
// output-guardrail.ts —— 输出护栏思路骨架
function guardOutput(text: string): GuardResult {
  // ① 泄密扫描：正则抓密钥/卡号等高危模式（示意，真实用更全的字典+NER）
  if (/\b(?:sk|pk)-[A-Za-z0-9]{20,}\b/.test(text)) {
    return { blocked: true, reason: '输出疑似含密钥', score: 1 };
  }
  // ② 格式约束：要求 JSON 时，非 JSON 直接拦下重写
  if (text.trim().startsWith('{')) {
    try { JSON.parse(text); } catch { return { blocked: true, reason: '格式非法', score: 1 }; }
  }
  return { blocked: false, score: 0 };
}
```

### 4.1 用 moderation 做毒性护栏（OpenAI Node SDK）

 toxicity/违规这类靠规则很难覆盖全，用厂商提供的 moderation 端点最省事——它是官方 API，可直接调用：

```ts
// moderation-guard.ts —— 用 OpenAI moderation 拦违规输出（官方 API）
import OpenAI from 'openai';
import 'dotenv/config';
const client = new OpenAI();

async function guardWithModeration(text: string): Promise<GuardResult> {
  const res = await client.moderations.create({ input: text }); // 官方审核端点
  const r = res.results[0];
  if (r.flagged) {
    // 命中类别（仇恨/暴力/自杀/性/违规等）可在 r.categories 里细看
    return { blocked: true, reason: 'moderation 命中违规类别', score: 1 };
  }
  return { blocked: false, score: 0 };
}
```

<Callout type="tip" title="moderation 是输入端也可用">
  `moderations.create` 对用户输入同样有效——在用户消息进模型前先审一遍，
  能拦掉大部分明显违规请求，和输入护栏的规则层形成双保险。
</Callout>

## 5. 运行时护栏：动作执行前的最后一道闸

输入/输出护栏管『语言』，运行时护栏管『动作』。Agent 一旦能调工具（发邮件、改库、转账），就必须有：

- **权限最小化**：每个工具只给必需权限，禁止 Agent 拿到删库/管理员密钥；
- **危险动作确认（HITL）**：退款、发送、删除等不可逆操作，落地前人工/二次确认（见 product-hitl）；
- **预算/频次限额**：单会话工具调用次数、金额上限，防失控烧钱或被利用。

```ts
// runtime-guard.ts —— 运行时护栏思路骨架
const RISKY_TOOLS = new Set(['refund', 'send_email', 'delete_record']);
const QUOTA = { maxToolCalls: 10, maxAmount: 1000 };

function guardAction(tool: string, args: any, used: { calls: number; amount: number }): GuardResult {
  if (used.calls >= QUOTA.maxToolCalls) {
    return { blocked: true, reason: '超过单会话工具调用上限', score: 1 };
  }
  if (RISKY_TOOLS.has(tool)) {
    // 不可逆动作：必须显式确认，否则拦截（交由 human-in-the-loop）
    if (!args.confirmed) return { blocked: true, reason: `危险动作 ${tool} 需确认`, score: 1 };
    if ((args.amount ?? 0) > QUOTA.maxAmount) {
      return { blocked: true, reason: '超出金额限额', score: 1 };
    }
  }
  return { blocked: false, score: 0 };
}
```

<Callout type="danger" title="别把高危密钥交给 Agent">
  运行时护栏的前提是『Agent 根本没有高危权限』。若 Agent 的运行身份持有删除全库、
  无限转账的凭证，护栏再严也只是建议。权限最小化是根，护栏是网，二者都不可少。
</Callout>

## 6. 合规与敏感词工程化

敏感词和合规不是『塞个数组就完事』，生产里要处理三件事：

- **动态词库与分级**：词库从配置/DB 加载、可热更新；词分等级（硬违规立即拦、软词仅标记），避免一刀切误伤。
- **多语种与变体**：违规词有谐音、拆字、中英混排、Unicode 全角等绕过。规则层用归一化（全角转半角、去零宽字符、注音映射）后再匹配；语义级交给分类器。
- **PII 检测**：身份证、手机号、邮箱、银行卡要用专门正则 + NER，拦截输出里的个人隐私泄露。

```ts
// compliance.ts —— 敏感词归一化 + 分级思路骨架
function normalize(text: string): string {
  return text
    .replace(/[！-～]/g, (c) => String.fromCharCode(c.charCodeAt(0) - 0xfee0)) // 全角→半角
    .replace(/[​-‍]/g, '')                              // 去零宽字符（看不见的绕过）
    .toLowerCase()
    .replace(/\s+/g, '');                                 // 去空格，防『违 规』拆字
}

// 分级词库：硬词拦截，软词标记
const HARD = ['违规词示例A'];
const SOFT = ['争议词示例B'];

function scanCompliance(text: string): GuardResult {
  const t = normalize(text);
  for (const w of HARD) if (normalize(w) && t.includes(normalize(w))) {
    return { blocked: true, reason: `命中硬违规词：${w}`, score: 1 };
  }
  for (const w of SOFT) if (t.includes(normalize(w))) {
    return { blocked: false, reason: `命中软词，建议标记复核：${w}`, score: 0.5 };
  }
  return { blocked: false, score: 0 };
}
```

<Callout type="tip" title="归一化是规则层的命门">
  攻击者最爱的绕过就是『全角、插零宽字符、拆空格』。规则匹配前**必须先归一化**，
  否则你的词库形同虚设。但归一化也拦不住语义改写，重度场景仍需分类器兜底。
</Callout>

## 7. 端到端示例：三层护栏串联

把输入、输出、运行时三层接进 Agent 主循环，一个请求会依次过这些闸：

```ts
// guardrail-pipeline.ts —— 三层护栏串联思路（以官方文档为准，API 易变）
async function guardedAgentRun(userText: string) {
  // ① 输入护栏：注入/敏感词/moderation，任一拦下直接拒绝
  const inRes = guardInput(userText);
  if (inRes.blocked) return refuse(inRes.reason);

  // ② 跑 Agent（内部每步工具调用再走运行时护栏 guardAction）
  const draft = await agentGenerate(userText);

  // ③ 输出护栏：moderation + 泄密 + 格式
  const mod = await guardWithModeration(draft);
  if (mod.blocked) return refuse(mod.reason);
  const outRes = guardOutput(draft);
  if (outRes.blocked) return refuse(outRes.reason);

  return draft; // 三层都过，才放行
}

function refuse(reason: string): string {
  // 拒绝时只回原因类别，不回原文（防敏感内容进日志）
  return `请求被护栏拦截（${reason}）。`;
}
```

<Callout type="note" title="拒绝也要友好且安全">
  拦截后用统一、不含原始敏感内容的提示回复用户，既不泄露原因细节给攻击者，
  也保留正常用户的申诉入口。拒绝是产品行为，不是只抛 400。
</Callout>

## 8. 护栏的评估闭环

护栏不是『写完就完』，它自己也要被评估、进回归。把红队拦截率变成固定指标：

- 红队集纳入版本化评测集（见 eval-dataset），每次改护栏都重跑，拦截率跌就挡下合并；
- 同时监控**误拦率**（用一批正常样本测，越低越好），和拦截率一起看跷跷板；
- 拦截率、误拦率、漏网样本，全部进 Dashboard（见 eval-trace 第 8 节）做趋势告警。

```ts
// guardrail-eval-loop.ts —— 护栏指标纳入回归（思路）
async function guardrailRegression() {
  const attackRecall = (await redTeam(attackSet, guardInput)).recall;  // 拦攻击的能力
  const falseBlock = (await redTeam(normalSet, guardInput)).blocked;    // 误伤正常用户
  if (attackRecall < 0.95) throw new Error('护栏拦截率不达标，禁止合并');
  if (falseBlock / normalSet.length > 0.02) throw new Error('误拦率过高，需调阈值');
}
```

<Callout type="warn" title="拦截率和误拦率要一起盯">
  把拦截率调到 100% 很容易——把所有请求都拦了就行。所以必须同时卡住误拦率上限，
  二者是跷跷板的两端。单看一个指标会被自己骗。
</Callout>

## 9. 安全评估：红队（Red Teaming）

护栏写完最危险的误区是『我觉得能拦住』。**红队评估**就是用对抗样本主动攻击自己的护栏，量化『拦截率』。流程：

1. 准备一批攻击样本：提示注入变体、敏感词伪装、越权请求、违规诱导；
2. 跑过『带护栏的 Agent』，记录每个样本是否被拦；
3. 算**拦截率（Recall@attack）**：拦下的攻击数 / 总攻击数；
4. 漏网的攻击样本 → 补规则/分类器 → 再测，循环直到达标。

```ts
// redteam.ts —— 红队评估思路骨架：量化护栏拦截率
async function redTeam(
  attacks: string[],                       // 攻击样本集
  runGuarded: (input: string) => Promise<GuardResult> // 被测的输入护栏
) {
  let blocked = 0;
  const leaks: string[] = [];
  for (const a of attacks) {
    const r = await runGuarded(a);
    if (r.blocked) blocked++;
    else leaks.push(a); // 漏网的要补防
  }
  const recall = blocked / attacks.length; // 拦截率，越低越危险
  return { recall, leaks };
}
```

<Callout type="warn" title="红队要持续、要变体化">
  攻击者不会用你训练时的那句话。红队样本要覆盖**措辞变体、编码绕过（base64/Unicode）、
  多语种、上下文拼接**等。一次红队通过 ≠ 永远安全，应把红队集纳入回归（见 eval-dataset），
  每次改护栏都重跑。
</Callout>

## 10. 自研 vs 框架对比

| 方案 | 适用 | 优点 | 缺点 |
|------|------|------|------|
| 自研规则 + 分类器 | 需求明确、要完全可控 | 透明、零厂商绑定、延迟低 | 语义级能力弱、要自己维护 |
| 厂商 moderation API | 通用毒性/违规 | 开箱即用、持续更新 | 类别有限、数据出域需评估 |
| Guardrails/NeMo 等框架 | 要结构化输出约束+校验 | 内置多类护栏、可组合 | 学习成本、版本/API 易变 |
| 在 Agent 循环内用模型自检 | 语义级复杂策略 | 灵活、可描述复杂规则 | 额外延迟与成本、非确定 |

<Callout type="note" title="纵深防御，别押单一层">
  实战推荐：规则（快、拦明显）+ 厂商/分类器（拦语义级）+ 运行时限额（兜底动作）。
  任何一层都可能被绕过，叠加才有可接受的拦截率。评估这个『可接受的拦截率』靠红队。
</Callout>

## 11. 常见坑

<Callout type="danger" title="护栏被注入『反向指令』绕过">
  攻击者可能在文档里写『上面的审核规则作废』。若你的护栏提示本身也是文本且可被检索内容影响，
  会被反制。对策：护栏逻辑放在**代码层**（规则/分类器/限额），不在模型提示里靠『请审核』实现。
  模型提示是可被注入改写的，代码不可。
</Callout>

<Callout type="warn" title="过度拦截伤体验">
  护栏太严会把正常用户也拦了（如把医学咨询当违规）。要监控『误拦率』，
  和拦截率一起看，用真实用户样本校准阈值。安全与可用是跷跷板，得调。
</Callout>

<Callout type="warn" title="只测正向，不测红队">
  上线前只验证了『正常请求通过』，从没用攻击样本打过自己的护栏——
  这是最典型的虚假安全感。护栏上线必须有红队拦截率作为准入门槛。
</Callout>

<Callout type="danger" title="敏感内容进日志/Trace 二次泄露">
  护栏拦截时若把原始违规输入/输出原样写进日志或 Trace（见 eval-trace），
  等于把敏感数据复制到另一个可观测后端。拦截记录要存『命中类别+哈希』，不存原文。
</Callout>

<Callout type="warn" title="把护栏当银弹">
  护栏降低风险，不消除风险。高危场景（医疗/金融建议、自动执行）仍需 human-in-the-loop
  与清晰的责任边界。别让护栏给人『系统绝对安全』的错觉。
</Callout>

## 小结

- 护栏是事前/事中拦截（评估是事后打分），分输入/输出/运行时三层，纵深防御缺一不可。
- 输入护栏主攻提示注入与敏感词；语义级注入规则拦不住，要靠分类器，且外部内容必须标记为不可信。
- 输出护栏用 moderation/正则/格式校验兜住模型抽风与泄密；moderation 输入端也能用。
- 运行时护栏管动作：权限最小化、危险动作确认、预算限额——根在权限，网在护栏。
- 红队评估量化拦截率，样本要变体化、纳入回归；只测正向不测红队是虚假安全。
- 红线：护栏逻辑放代码层（防注入反制）、监控误拦率、拦截记录脱敏、高危场景仍要 HITL。

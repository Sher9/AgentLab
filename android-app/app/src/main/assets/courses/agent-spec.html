Agent 规格定义：需求拆解、能力清单与输入输出契约

写代码前先写规格。讲透如何把模糊需求拆成可执行项、列出能力清单、定义输入输出契约与评测口径，并给出用 Zod 固化契约的骨架。

#规格#需求拆解#能力清单#契约#评测口径

Agent 规格定义

很多 Agent 项目烂在开头：需求一句『做个智能助手』，团队直接开写工具，写到一半发现目标不清、能力边界模糊、上线没标准。和写任何严肃系统一样，Agent 也该先有**规格（spec）**再落地。

这一篇讲怎么把模糊需求落成：需求拆解 → 能力清单 → 输入输出契约 → 评测口径。最后给你一份用 Zod 把契约固化进代码的骨架。

1. 为什么 Agent 更需要先写规格

LLM 的不确定性放大了『需求模糊』的代价：

  • 模型会自行发挥，没有边界就往你没预期的方向走；
  • 工具是会产生副作用的（发消息、改库），能力清单不清楚就会误触发；
  • 『好不好』没法靠『能跑』判断，必须有可测的口径，否则无法迭代。

规格就是这三件事的书面约定：边界、契约、验收标准。

📌规格是给人和模型一起看的

一份好规格有两层价值：对人是需求对齐与验收依据；对模型，规格里的『能力清单 + 约束』 会直接变成系统提示与工具描述。规格写得含糊，模型的表现就含糊。

2. 需求拆解：从目标到可执行项

面对『智能客服 Agent』这种大词，先用『用户意图 × 动作类型』拆成可执行单元：

目标：智能客服 Agent
├─ 查订单状态      → 只读工具 query_order
├─ 退换货          → 写工具 refund_order（需人工确认）
├─ 回答产品问题    → 检索知识库（RAG）
└─ 转人工          → 触发 handoff 事件

拆解原则：

  • 每个单元都能落到『调一个或一组工具 + 一段判断』；
  • 区分只读与有副作用，副作用项后续要加护栏；
  • 明确不做什么（如『不处理退款金额超过 5000 的单子』），边界比功能更重要。
💡先列边界，再列能力

写规格时先写『本 Agent 不处理什么』，往往比写『能处理什么』更能防住事故。 模型爱『逞能』，边界写清楚，它在越界时才有明确收手依据。

3. 能力清单：Agent 到底能干什么

能力清单 = 工具集 + 每个工具的职责与限制。它既是给团队的，也是喂给模型的。

// 能力清单：每个条目 = 一个可被模型调用的能力
// 注意 description 同时服务于『模型决策』与『团队对齐』
const tools = [
  {
    type: 'function',
    function: {
      name: 'query_order',
      description: '查询订单当前状态。仅支持已登录用户的订单，只读。',
      parameters: { /* ... */ },
    },
  },
  {
    type: 'function',
    function: {
      name: 'refund_order',
      description: '发起退款。金额≤5000 自动执行；超出须转人工，本工具拒绝。',
      parameters: { /* ... */ },
    },
  },
];
⚠️能力清单要可收敛

工具不是越多越好。超过 ~20 个，模型选错率与 token 成本明显上升（见 M1 工具路由）。 规格阶段就定好『本期做哪几个』，其余进 backlog，别一次性全塞进去。

4. 输入输出契约：用 Zod 固化边界

『用户输入长什么样、工具参数长什么样、最终输出长什么样』，用 Zod schema 写成单一事实来源——校验和文档一体。

import { z } from 'zod';

// 输入契约：用户请求的结构化部分（如来自前端的字段）
const AgentInput = z.object({
  userId: z.string().min(1),
  query: z.string().min(1).max(2000),
  sessionId: z.string().optional(),
});

// 输出契约：最终答案的结构（便于前端渲染与评测比对）
const AgentOutput = z.object({
  answer: z.string(),
  usedTools: z.array(z.string()),
  needHuman: z.boolean(),
});

// 工具参数契约：执行前 safeParse，非法直接拦截
const RefundArgs = z.object({
  orderId: z.string(),
  amount: z.number().positive().max(5000), // 边界写进 schema
});
💡把业务边界写进 schema

『退款≤5000』这种规则尽量落到 Zod 的 .max(5000)，而非只在提示里说。 schema 是硬约束，提示是软约束；硬约束失败了能被代码拦下，软约束模型可能忘。

5. 评测口径：怎么算『做对了』

没有口径就无法迭代。规格里必须写清验收维度，常见四类：

维度 问什么 怎么测
任务完成度 用户目标达成没 黄金集比对 / LLM-as-judge
工具正确性 调对工具、传对参没 断言 usedTools 与参数
安全合规 越权/误触没 护栏命中率、越界拦截率
成本延迟 贵不贵、慢不慢 平均步数、平均 token 
// 评测口径落到代码：一条最小断言示例
function evaluate(out: unknown, expect: { tools: string[] }) {
  const parsed = AgentOutput.parse(out);
  const ok = expect.tools.every((t) => parsed.usedTools.includes(t));
  return { pass: ok, usedTools: parsed.usedTools };
}
📌口径先于优化

先有『通过/不通过』的判定，才有资格谈『提升准确率』。 哪怕一开始只是 10 条手标黄金集 + 一条断言，也比『感觉好多了』强。

6. 规格模板（可直接复用）

一份 Agent 规格至少含：

  1. 目标与边界：做什么、不做什么；
  2. 用户场景：典型输入/预期输出各 2~3 例；
  3. 能力清单：工具名、职责、只读/副作用、护栏；
  4. 输入契约：AgentInput 字段与约束；
  5. 输出契约：AgentOutput 字段与结构；
  6. 评测口径：维度 + 判定方式 + 黄金集规模。
⚠️规格要随模型版本更新

模型升级后，同一份规格下 Agent 表现可能变（更好或更差）。 规格与评测集应纳入版本管理，模型一换就重跑评测，别假设『换模型无回归』。

7. 与相邻概念的关系

  • 规格 ≠ 架构（M2 架构模式解决『怎么思考』，规格解决『做什么、做到什么标准』）；
  • 规格 ≠ 工具定义（M1），工具定义是规格里『能力清单』的落地形态；
  • 规格驱动评测（评估调优分类），评测结果反过来修订规格——形成闭环。

小结

  • Agent 先写规格再写码：需求拆解 → 能力清单 → 输入输出契约 → 评测口径。
  • 边界（不做什么）比功能列表更能防事故；先列边界。
  • 工具不是越多越好，本期收敛、其余进 backlog。
  • 用 Zod 把输入/输出/参数契约固化成单一事实来源，硬约束优于软提示。
  • 评测口径先于优化：先有通过/不通过，再谈提升。
  • 规格与评测集一起版本化，模型一换就重跑。

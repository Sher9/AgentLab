实战：从零搭一个可运行的 Agent 项目

走到这里，M0–M7 的概念你都过了一遍：会调工具、懂模式、知道记忆/RAG、多 Agent、评估与工程化。但零散的知识点，只有拼进一个真实项目才会变成能力。

本篇带你从零搭一个研究助手 Agent（Research Agent）：

给它一个主题，它会：先做计划 → 检索资料（工具）→ 调用计算/查询工具 → 记录关键结论到长期记忆 → 汇总成一份带引用来源的报告。

它把前面所有模块串成一条线。代码全部可运行（用占位数据，零外部 API 依赖即可演示），你本地跑通后，再按文末路线逐步替换为真实能力。

1. 项目结构

真实项目要把「循环、工具、记忆、规划」拆开，而不是塞在一个文件里。我们采用如下结构：

research-agent/
├─ package.json
├─ .env                      # OPENAI_API_KEY=sk-...
├─ tsconfig.json
├─ src/
│  ├─ agent.ts               # 主循环（规划 + ReAct + 工具 + Zod 校验）
│  ├─ tools.ts               # 工具定义与实现（检索/计算/笔记）
│  ├─ memory.ts              # 短期(messages) + 长期(笔记) 记忆
│  ├─ planner.ts             # 规划阶段：把主题拆成步骤
│  └─ prompts.ts             # 系统提示词
└─ run.ts                    # 入口：读主题、跑 Agent、输出报告

下面逐文件给出可运行骨架。为方便你一次复制跑通，关键的 agent.ts 与 tools.ts 都做了最小自包含。

2. 规划层 planner.ts

M2 讲「Plan-and-Execute」：复杂任务先规划再执行，能减少盲目试错。这里用一个轻量规划器，把主题拆成有序步骤，写进系统提示引导模型。

// src/planner.ts
// 轻量规划：把主题拆成研究步骤（真实场景可让 LLM 生成，这里用规则演示结构）
export interface Plan {
  topic: string;
  steps: string[];
}

export function makePlan(topic: string): Plan {
  // 通用三步法：检索定义 → 收集要点 → 形成结论
  // 真实项目可改为：调用 LLM 生成针对 topic 的定制步骤
  return {
    topic,
    steps: [
      `检索「${topic}」的核心定义与背景`,
      `收集「${topic}」的关键要点与争议`,
      `汇总形成带引用的研究报告`,
    ],
  };
}
📌规划的价值

没有规划时，模型容易「想到哪做到哪」，在长任务里反复横跳。把步骤显式写进 prompt， 相当于给循环一个「待办清单」，每轮工具调用都更聚焦。代价是规划可能随进展过期，需要时可动态修订。

3. 工具层 tools.ts

工具是 Agent 的「手脚」。这里给三个：网页检索（占位）、计算器、保存笔记到长期记忆。

// src/tools.ts —— 工具定义 + 实现（最小可运行版）
import { z } from 'zod';
import type OpenAI from 'openai';

// 长期记忆的容器（真实项目换数据库，见 M4）
export const notes: string[] = [];

// ① 网页检索：此处用占位数据，真实场景接入搜索 API（如 Brave/Tavily）
function webSearch(query: string): string {
  return `[检索 "${query}"] 占位结果：Agent 是能感知环境、自主决策并调用工具完成目标的系统。`;
}

// ② 计算器
function calc(expr: string): string {
  // 仅允许数字与运算符，避免 eval 注入风险
  if (!/^[\d+\-*/().\s]+$/.test(expr)) return '表达式非法';
  try {
    // eslint-disable-next-line no-new-func
    const v = Function(`"use strict";return (${expr})`)() as number;
    return String(v);
  } catch {
    return '计算失败';
  }
}

// ③ 保存笔记（写入长期记忆）
function saveNote(note: string): string {
  notes.push(note);
  return `已保存笔记（共 ${notes.length} 条）`;
}

// 给模型看的工具清单（JSON Schema，见 M1）
export const tools: OpenAI.Chat.Completions.ChatCompletionTool[] = [
  {
    type: 'function',
    function: {
      name: 'web_search',
      description: '检索与主题相关的资料，返回摘要',
      parameters: { type: 'object', properties: { query: { type: 'string' } }, required: ['query'] },
    },
  },
  {
    type: 'function',
    function: {
      name: 'calculator',
      description: '计算数学表达式',
      parameters: { type: 'object', properties: { expr: { type: 'string' } }, required: ['expr'] },
    },
  },
  {
    type: 'function',
    function: {
      name: 'save_note',
      description: '把关键结论保存到长期记忆，便于最终汇总',
      parameters: { type: 'object', properties: { note: { type: 'string' } }, required: ['note'] },
    },
  },
];

// 工具分发：按名字执行，并用 Zod 校验参数（见 M1 第 5 节）
const CalcArgs = z.object({ expr: z.string() });
const NoteArgs = z.object({ note: z.string().min(1) });
const SearchArgs = z.object({ query: z.string().min(1) });

export function executeTool(name: string, rawArgs: string): string {
  let args: unknown;
  try {
    args = JSON.parse(rawArgs);
  } catch {
    return '参数不是合法 JSON';
  }
  if (name === 'web_search') {
    const p = SearchArgs.safeParse(args);
    return p.success ? webSearch(p.data.query) : `参数错误：${p.error.message}`;
  }
  if (name === 'calculator') {
    const p = CalcArgs.safeParse(args);
    return p.success ? calc(p.data.expr) : `参数错误：${p.error.message}`;
  }
  if (name === 'save_note') {
    const p = NoteArgs.safeParse(args);
    return p.success ? saveNote(p.data.note) : `参数错误：${p.error.message}`;
  }
  return `未知工具: ${name}`;
}
⚠️工具返回的字符串也会被读回 prompt

工具结果（尤其 web_search 来自外部）属于不可信输入。实战里要在回填前做长度截断、 敏感信息脱敏，并警惕提示注入——不要让它借工具结果「改写指令」。详见 M0 局限与 M6 护栏。

4. 记忆层 memory.ts

把 M4 的概念落地：短期记忆就是不断增长的 messages；长期记忆是上面 tools.ts 里的 notes 数组。这里提供「拼装长期记忆」的只读视图，以及清空（每轮任务隔离）。

// src/memory.ts
import { notes } from './tools';

// 把长期记忆格式化成一段文本，注入最终汇总提示
export function longTermMemoryView(): string {
  if (notes.length === 0) return '（暂无长期笔记）';
  return notes.map((n, i) => `${i + 1}. ${n}`).join('\n');
}

// 跨任务隔离：开始前清空，避免上一次的主题污染本次
export function resetMemory(): void {
  notes.length = 0;
}

5. 主循环 agent.ts（规划 + ReAct + Zod 校验）

这就是 M2 的 ReAct 节律 + M1 的工具闭环 + M4 的记忆 + 本篇的规划，组合成一个可调用的 runAgent。

// src/agent.ts
import OpenAI from 'openai';
import 'dotenv/config';
import { tools, executeTool } from './tools';
import { longTermMemoryView, resetMemory } from './memory';
import { makePlan } from './planner';

const client = new OpenAI();

export async function runAgent(topic: string, maxSteps = 8): Promise<string> {
  resetMemory();                       // 先清空长期记忆，保证任务隔离
  const plan = makePlan(topic);        // 规划阶段：生成步骤清单
  const planText = plan.steps.map((s, i) => `${i + 1}. ${s}`).join('\n');

  const messages: OpenAI.Chat.Completions.ChatCompletionMessageParam[] = [
    {
      role: 'system',
      content:
        '你是一个研究助手。先按给定计划行动：用 web_search 收集资料，用 calculator 处理数字，' +
        '用 save_note 记录关键结论。信息足够后，直接输出最终研究报告（带要点），不要继续调用工具。\n' +
        `研究计划：\n${planText}`,
    },
    { role: 'user', content: `请研究这个主题并产出报告：${topic}` },
  ];

  for (let step = 0; step < maxSteps; step++) {
    const res = await client.chat.completions.create({
      model: 'gpt-4o-mini',
      messages,
      tools,
    });
    const msg = res.choices[0].message;
    messages.push(msg);

    if (!msg.tool_calls?.length) {
      // 模型认为信息够了，返回最终报告
      return msg.content ?? '';
    }

    for (const call of msg.tool_calls) {
      const result = executeTool(call.function.name, call.function.arguments);
      messages.push({ role: 'tool', tool_call_id: call.id, content: result });
    }
  }

  // 达到上限：用长期记忆兜底汇总，避免空手而归
  const summary = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '基于已收集的长期记忆，写出最终报告要点。' },
      { role: 'user', content: `主题：${topic}\n已记录资料：\n${longTermMemoryView()}` },
    ],
  });
  return summary.choices[0].message.content ?? '';
}
💡先用占位数据验证逻辑

本骨架的 web_search 是占位返回，目的是让你不依赖外部 API 也能跑通整条链路。 先确认「规划→循环→工具→记忆→报告」通了，再替换真实检索——这是工程化降低风险的基本功。

6. 入口 run.ts 与配置

// src/run.ts
import { runAgent } from './agent';

async function main() {
  const topic = process.argv[2] ?? 'AI Agent 的主流架构模式有哪些？';
  console.log('研究主题：', topic, '\n');
  const report = await runAgent(topic);
  console.log('=== 研究报告 ===\n');
  console.log(report);
}

main();
tsconfig.json 只需基础配置（"module": "ESNext"、"moduleResolution": "Bundler"、"strict": true）；package.json 依赖为 openai、dotenv、zod。

7. 跑起来

npm init -y
npm i openai dotenv zod
npx tsx src/run.ts "AI Agent 的主流架构模式有哪些？"

你会看到 Agent 先 web_search 收集资料、save_note 记录结论，最后输出一份带要点的报告。把 .env 里的 OPENAI_API_KEY 填上即可（M0 环境搭建已讲过）。

8. 加一层规划修订（进阶）

上面的 makePlan 是固定三步。真实场景里，模型执行到一半可能发现计划不对。可加一个「每 N 步审视一次计划」的钩子：

// 伪代码：在 agent.ts 循环内，每 3 步让模型评估「计划是否还合理」
if (step % 3 === 0) {
  const review = await client.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: '评估当前进度，简短回答：计划是否需要调整？如需，给出新步骤。' },
      ...messages.slice(-6), // 只看最近几轮，省 token
    ],
  });
  // 把 review 作为一条 assistant/tool 提示注入，引导后续动作（以官方文档为准，API 易变）
}
📌这是 Plan-and-Execute 的雏形

把「规划」和「执行」解耦后，规划可以独立缓存、复用、被人审阅。复杂任务里这比纯 ReAct 更可控， 但也更贵（多一次规划调用）。取舍见 M2。

9. 接入真实 RAG（替换占位检索）

把 web_search 换成 M4 讲的向量检索，Agent 就能基于你的私有知识库作答：

// 3. 把命中片段作为工具结果回填，模型据此作答并 save_note
对比 占位检索 真实 RAG
数据来源 硬编码字符串 你的文档/知识库
相关性 无 语义 top-k
成本 0 每次检索一次 embedding 调用
风险 无 bad retrieval 误导（需阈值过滤）

10. 评估与可观测（上线前必做）

M6 讲评估与可观测。给 runAgent 包一层 trace，记录每步耗时、token、工具调用：

// 伪代码：包裹一次 Agent 运行，产出可观测日志
async function tracedRun(topic: string) {
  const t0 = Date.now();
  const report = await runAgent(topic);
  console.log(JSON.stringify({
    topic,
    costMs: Date.now() - t0,
    steps: /* 需要从 runAgent 内部上报 */,
  }));
  return report;
}

评估可用「黄金数据集 + LLM-as-judge」：准备若干主题与期望要点，自动比对报告覆盖率（详见 M6）。

11. 怎么继续扩展（对照前面的模块）

这个最小项目已经具备「能跑」的骨架，接下来按需求逐步加料：

想要的能力 看哪篇 怎么加
更稳的「先规划再执行」 M2 Plan-and-Execute 在 runAgent 前先调一次规划，把步骤写进 system prompt
真实语义检索(RAG) M4 记忆与 RAG 把 notes 换成向量库，检索 top-k 注入 prompt
并行多角色协作 M5 多 Agent 拆出「检索 Agent / 写作 Agent」，用 manager 汇总
评估与护栏 M6 评估与可观测 给 runAgent 包一层 tracer + eval 数据集打分
流式输出/缓存/部署 M7 工程化 stream: true 逐步吐字；加 Redis 缓存；部署为常驻服务

12. 一个完整项目的工程化清单

把教程变成产品，别忘了这些上线前必做项（都已在前面覆盖）：

  • 成本：简单步骤换小模型，长 prompt 摘要压缩（M4/M7）
  • 延迟：流式输出、并行工具、减少轮数（M7）
  • 可靠性：循环上限、Zod 校验、重试退避（M1/M7）
  • 安全：危险工具加护栏与确认，防提示注入（M1/M6）
  • 可观测：每步打 trace，上线后能排查（M6）
  • 文档/SEO：对外站点要 sitemap、OG、响应式（本站即范例）
🚫永远给循环设上限

本骨架 maxSteps=8 不是可选项。没有上限，模型一旦陷入「调同一个工具→得到相似结果→再调」的死循环， 会一直烧 token 直到失败。生产环境还要叠加成本预算与超时，作为第二道保险。

小结

  • 真实 Agent = 规划（planner） + 主循环（ReAct） + 工具（M1） + 记忆（M4）的组合。
  • 先跑通最小闭环（占位数据），再逐模块替换真实能力，是风险最低的路径。
  • 规划让长任务更聚焦；长期记忆让跨步结论可汇总；工具结果须经校验与脱敏再回填。
  • 本项目的每一行，都能在前 7 篇找到出处——这就是「边学边做」的闭环。
  • 上线前补齐：循环上限、成本预算、评估、可观测、安全护栏（M6/M7）。

# 向量数据管线：批量嵌入、去重、更新与同步

在 RAG、语义检索、推荐去重等场景里，真正决定效果的往往不是『模型多强』，而是**把原始数据变成高质量向量的那条管线**。模型（Embedding 模型）只是其中一个算子；前面要清洗、切分、去重，后面要增量更新、和向量库对账、处理删除与漂移。

这一篇把向量数据管线讲透：端到端分阶段拆解、批量嵌入的工程细节、两层去重、三种更新策略的取舍、与向量库的幂等同步，最后给出**能跑起来的 Python 骨架**和一份踩坑清单。面向有经验的开发者，重实战、轻口水。

## 1. 什么是向量数据管线

向量数据管线（Vector Data Pipeline）指的是：把**任意原始数据**（文档、网页、工单、商品描述……）稳定、可复现地转化为『向量 + 元数据』并写入向量库的自动化流程。它的上游是数据源，下游是向量数据库（pgvector / Qdrant / Milvus / Chroma 等）。

它和普通的 ETL 最大区别在于中间多了一个 **Embedding 算子**：这一步依赖外部模型服务、有速率限制、有成本、且输出是固定维度的高维向量。这带来三个普通 ETL 没有的麻烦：

- **成本与限流**：每次嵌入都是一次付费 API 调用或 GPU 计算，不能无脑全量重跑；
- **幂等性挑战**：同一段文本重新嵌入，向量会变（模型版本升级后更明显），必须定义清楚『什么时候该重嵌』；
- **删除难题**：向量库的删除比关系库麻烦，语义重复、软删除、过期失效都要专门处理。

<Callout type="note" title="管线和检索是两件事">
  本篇只讲『生产向量』这一侧。怎么在查询时把问题向量化、做相似检索、重排，是 RAG 分类的主题。
  两侧共用同一个 Embedding 模型与同一套切分规则，否则『写入时的向量空间』和『查询时的向量空间』不一致，召回必然崩。
</Callout>

## 2. 管线全景：从原始文档到可检索向量

一个生产可用的向量管线通常拆成下面几个阶段，每个阶段都要可观测、可重跑：

```
数据源(数据库/对象存储/CMS)
   │
   ▼ ① 抽取 Extract：拉取原始记录，拿到稳定主键(id)与内容字段
   ▼ ② 清洗 Normalize：去空白、统一编码、剥离无关样式/脚本
   ▼ ③ 切分 Chunk：按语义/长度切成检索单元(带重叠)
   ▼ ④ 去重 Dedup：内容哈希去重 + 可选语义去重
   ▼ ⑤ 嵌入 Embed：调 Embedding 模型，文本 → 向量(带重试/限流/并发)
   ▼ ⑥ 同步 Sync：带元数据 upsert 进向量库，处理新增/更新/删除
   ▼ ⑦ 对账 Reconcile：定期校验『源记录数 == 向量库记录数』
```

每个阶段都应该是**幂等的**：用同样的输入重跑，得到同样的终态（或等价的终态）。幂等是后面增量更新能成立的前提。

<Callout type="tip" title="先定主键再写代码">
  整条管线的稳定性依赖一个稳定、唯一的业务主键（如 `doc_id` + `chunk_index`）。
  没有它，后面的更新、去重、对账全都无从谈起。动手前先和上游确认：什么字段能唯一标识『这一段文本』。
</Callout>

## 3. 批量嵌入：并发、限流与重试

嵌入阶段是最容易出工程事故的地方。Embedding 服务通常有 QPS / RPM 限制，且单次请求能带的文本条数有限（batch size）。目标是：**在限流内跑满吞吐，同时不因为单条失败而丢掉整批**。

核心要点：

- **批量打包**：把 N 条文本合成一次请求（batch），通常 32～128 条/批，具体看模型上限；
- **并发控制**：用信号量/线程池限制同时进行的请求数，别一次性发几千个把服务打挂；
- **指数退避重试**：429（限流）、5xx、超时都可重试，用 `Retry-After` 或指数退避；
- **单条隔离**：一条文本嵌入失败不应导致整批重跑，记录失败、跳过、事后补。

```python
# embed_batch.py —— 批量嵌入骨架（伪代码+注释，API 以官方文档为准）
import asyncio
from dataclasses import dataclass

# 假设有一个 embedding 客户端；真实项目换成 openai / 本地模型服务客户端
# 这里用伪接口表示，避免编造不存在的 API
class EmbedClient:
    async def embed(self, texts: list[str]) -> list[list[float]]:
        # 真实调用：await client.embeddings.create(model=..., input=texts)
        # 返回与 texts 顺序一致的向量列表
        ...

@dataclass
class Job:
    id: str          # 业务主键，用于幂等 upsert
    text: str        # 切分后的文本块

# 全局并发闸门：最多同时 8 个请求在飞，避免击穿限流
SEM = asyncio.Semaphore(8)
BATCH = 64          # 每批文本条数，按模型上限调
MAX_RETRY = 4       # 单批最大重试次数

async def embed_one_batch(client: EmbedClient, batch: list[Job]) -> dict[str, list[float]]:
    async with SEM:                      # 拿到闸门才发请求
        for attempt in range(MAX_RETRY):
            try:
                vecs = await client.embed([j.text for j in batch])
                # 用主键对齐，绝不用列表下标当长期标识
                return {job.id: v for job, v in zip(batch, vecs)}
            except RateLimitError:       # 429：尊重限流，退避后重试
                await asyncio.sleep(2 ** attempt)
            except TransientError:       # 5xx/超时：同样退避重试
                await asyncio.sleep(2 ** attempt)
        # 重试耗尽：这条批标记失败，交给补跑队列，不阻断整批
        return {job.id: None for job in batch}

async def run(jobs: list[Job], client: EmbedClient):
    results: dict[str, list[float]] = {}
    # 按 BATCH 切片，逐批并发嵌入
    for i in range(0, len(jobs), BATCH):
        batch = jobs[i:i + BATCH]
        results.update(await embed_one_batch(client, batch))
    failed = [jid for jid, v in results.items() if v is None]
    print(f"成功 {len(results) - len(failed)} 条，失败 {len(failed)} 条待补跑")
```

<Callout type="warn" title="批次大小不是越大越好">
  单批文本过多会触发服务端的『单请求 token 上限』而整体失败，且一旦失败整批重来成本更高。
  经验起点是 32～64，再按实际限流和延迟调优。失败率上升时优先调小 BATCH，其次降并发。
</Callout>

## 4. 去重：先内容级，后语义级

向量库最怕『同一段话被嵌入了上百遍』——会拉高存储、拖慢检索、污染召回。去重分两层，成本递增、收益递减：

### 4.1 内容哈希去重（必做）

最便宜也最有效：对『归一化后的文本』算哈希（如 SHA-256），相同哈希只保留一份。归一化很关键——要先做大小写折叠、空白压缩、去 HTML 标签，否则『Hello』和『hello』会被当成两条。

```python
# dedup_content.py —— 内容级去重骨架
import hashlib

def norm_text(s: str) -> str:
    # 归一化：小写、压缩空白、去首尾空格；按业务需要再加去标签等
    return " ".join(s.lower().split())

def content_hash(s: str) -> str:
    return hashlib.sha256(norm_text(s).encode("utf-8")).hexdigest()

seen: set[str] = set()
def dedup_by_content(jobs: list[Job]) -> list[Job]:
    out = []
    for job in jobs:
        h = content_hash(job.text)
        if h in seen:        # 内容已存在，直接丢弃
            continue
        seen.add(h)
        out.append(job)
    return out
```

### 4.2 语义去重（按需）

内容哈希管不了『意思一样但字面不同』（近义改写、轻微改述）。语义去重用向量相似度：新块嵌入后，先和已有块算余弦，高于阈值（如 0.98）就视为重复。代价是要先有可检索的向量库，且多了一次检索开销。

<Callout type="tip" title="阈值要按数据定">
  语义去重阈值没有通用值。技术文档改写少，0.97 可能太松；UGC 内容重复多，0.95 也合理。
  先用一个小样本人工标定：挑 100 对『你认为重复/不重复』的文本，画相似度分布再定阈值。
</Callout>

## 5. 更新策略：全量重建 vs 增量 vs CDC

数据会改、会删。三种更新策略，按成熟度从低到高：

| 策略 | 做法 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 全量重建 | 定时清空向量库，全量重嵌 | 实现最简单、终态最干净 | 成本高、停服窗口、模型升级时必选 | 数据量小、变更少 |
| 增量更新 | 按 `updated_at` 拉增量，upsert 变化的 | 成本低、无停服 | 依赖源有可靠时间戳；删操作易漏 | 有 updated_at 的源头 |
| CDC（变更数据捕获） | 订阅 binlog/事件流，逐条事件处理 | 近实时、不丢删除 | 接入成本最高、要消息队列 | 大规模、强一致要求 |

### 5.1 增量更新的关键点

增量更新最容易被坑的两处：

- **删除怎么传**：很多源只有 `updated_at`，没有『删除标记』。要么源侧软删除（加 `deleted_at`），要么你维护一份『源全量 id 集合』，对账时 diff 出已消失的 id 去向量库删；
- **更新要重嵌还是只改元数据**：如果只改了业务标签（如分类），不必重嵌向量，只 patch 元数据；如果正文变了，必须重嵌，否则向量与文本错位。

```python
# incremental_sync.py —— 增量更新骨架（伪代码+注释）
def pull_incremental(since_ts: int) -> list[Job]:
    # 只取最近更新的记录；真实项目用 SQL: WHERE updated_at > since_ts
    ...

def sync_incremental(client: EmbedClient, since_ts: int):
    jobs = pull_incremental(since_ts)
    to_upsert, to_delete = [], []
    for job in jobs:
        if job.deleted:                 # 软删除：进删除队列
            to_delete.append(job.id)
        elif job.body_changed:          # 正文变了：必须重嵌
            to_upsert.append(job)
        else:                           # 只改了元数据：只补元数据，不重嵌
            patch_metadata(job.id, job.meta)
    vecs = run(to_upsert, client)       # 复用第 3 节的批量嵌入
    upsert_to_store(vecs)               # 幂等 upsert（见第 6 节）
    delete_from_store(to_delete)       # 真正删除向量
```

<Callout type="danger" title="删除漏了比不删更危险">
  向量库里留着已删除文档的向量，会在检索时『诈尸』——用户搜出一个已经被业务下线的商品/工单。
  没有可靠删除通道时，至少用『源全量 id 对账』兜底清理，别让死向量长期滞留。
</Callout>

## 6. 与向量库同步：幂等 upsert

写入向量库的核心动作是 **upsert**（存在则更新、不存在则插入）。幂等靠第 1 节定义的业务主键（`id`）。要点：

- **批次写入**：向量库批量 upsert 比逐条快一个数量级；
- **元数据随向量一起写**：分类、来源、时间戳、权限字段都进元数据，检索时才能做过滤（如『只搜公开文档』）；
- **失败可重放**：写入失败要能按主键重放，不要因为中途一条错就整批回滚（除非要求强一致）。


<Callout type="tip" title="元数据过滤是检索性能开关">
  把权限/分类放进 payload，检索时直接 `filter(perm='public')`，能在向量距离计算前先缩圈，
  既保安全又提速。别把所有过滤逻辑都堆在应用层事后筛，那会浪费大量召回与带宽。
</Callout>

## 7. 对账：别相信管线永远跑对了

任何自动化管线都会在某天 quietly 出错（限流丢批、删除漏传、源 schema 变更）。所以要有**对账**环节：定期比较『源记录数 / 源全量 id 集合』与『向量库记录数 / id 集合』，差异告警。

```python
# reconcile.py —— 简单的对账骨架
def reconcile(source_ids: set[str], store_ids: set[str]):
    missing_in_store = source_ids - store_ids   # 源有、库没有 → 漏写
    ghost_in_store = store_ids - source_ids      # 库有、源没有 → 该删没删
    if missing_in_store or ghost_in_store:
        alert(f"对账异常: 漏写 {len(missing_in_store)}，幽灵 {len(ghost_in_store)}")
    return len(missing_in_store), len(ghost_in_store)
```

## 8. 三种管线形态对比

| 维度 | 全量重建 | 增量更新 | CDC |
|------|----------|----------|-----|
| 实时性 | 低（按调度） | 中（按调度） | 高（准实时） |
| 成本 | 最高 | 中 | 低（边际） |
| 实现复杂度 | 低 | 中 | 高 |
| 删除处理 | 天然干净 | 需对账兜底 | 天然干净 |
| 模型升级 | 最合适 | 需全量触发 | 需全量触发 |
| 典型选型 | 小库/低频 | 大多数业务 | 大规模/强一致 |

<Callout type="note" title="先用增量，再谈 CDC">
  大多数团队一开始并不需要 CDC。先用『增量更新 + 每日全量对账 + 周级全量重建兜底』，
  能覆盖 90% 场景且成本低得多。等数据量和实时性真的压上来，再上 CDC 不迟。
</Callout>

## 10. 踩坑与最佳实践

<Callout type="danger" title="写入与查询用了不同切分规则">
  这是召回崩坏的头号原因。切分长度、重叠、归一化只要写入侧和查询侧不一致，
  两个向量就不在同一分布，相似度失去意义。把切分逻辑抽成共享函数，两侧都 import 同一份。
</Callout>

<Callout type="warn" title="模型升级后没全量重嵌">
  Embedding 模型换版本后，旧向量和新向量不在同一空间。残留的旧向量会和新的『鸡同鸭讲』。
  任何模型升级都必须触发一次全量重建（或至少对存量做版本标记、灰度对比）。
</Callout>

<Callout type="warn" title="并发过高击穿限流">
  一次性发海量并发请求，会被限流打回、触发雪崩式重试。永远用信号量/连接池限制在飞请求数，
  并把 429 当成『预期内』正常信号做退避，而不是当异常抛出。
</Callout>

<Callout type="warn" title="死向量长期滞留">
  删除漏传、对账缺失，会让已下线内容继续被召回。给管线配上『源全量 id 对账』兜底清理，
  并把删除当成一等公民（软删除标记 / 删除事件），不能只在增量里依赖 updated_at。
</Callout>

<Callout type="tip" title="给每条记录打数据版本">
  在 payload 里写入 `pipeline_version` 与 `model_version`。出问题时能精准圈出『哪批向量是旧模型产生的』，
  做定向重建，而不是盲猜。这是线上排障的救命字段。
</Callout>

## 11. 适用与不适用

**适用**：
- RAG / 语义检索的知识库构建；
- 需要近重复检测的内容平台（评论、商品标题去重）；
- 任何『文本 → 可检索向量』的离线/近实时场景。

**不适用 / 需谨慎**：
- 纯精确匹配需求（用倒排索引/数据库 LIKE 更便宜，不必上向量）；
- 极高的实时性且源无变更事件（CDC 接入成本需评估）；
- 数据量极小且从不更新的场景（全量重建脚本就够了，不必上编排）。

## 小结

- 向量管线 = 抽取→清洗→切分→去重→嵌入→同步→对账，每个阶段都要幂等、可重跑。
- 嵌入阶段用『批量 + 并发闸门 + 指数退避 + 单条隔离』扛住限流与成本。
- 去重先做内容哈希（必做），再做语义去重（按需），阈值用样本人工标定。
- 更新策略按成熟度递进：增量更新 + 每日对账 + 周级全量兜底，够大多数团队用；上规模再上 CDC。
- 同步靠业务主键做幂等 upsert，元数据随向量一起写，删除是一等公民别漏。
- 红线：写入与查询共用切分规则、模型升级必全量重嵌、并发限量、死向量对账清理、payload 打版本。
